# 工作流编排

在会话里输入 `/skill:工作流编排`，再描述要设计的流程、要运行的任务或要查询的运行。

## 搭建一个流程

1. 从侧栏打开「工作流中心」。点击「新建」可使用规划、实施、审查、测试、验收、结果整理的模板。旁边的空白工作流按钮适合从零搭建。
2. 把每一步写成一个节点，明确输入、要做的事和期望产出。选择节点后在「属性」中填写 Prompt。普通步骤用「任务」，复核步骤用「审查」，最终交付用「结果」。只有需要按裁决返工时才添加「验收 gate」。在工作流设置里写上适用场景和输入提示，方便后续启动时识别。
3. 点源节点上的连线箭头，再点目标节点。依赖边决定谁先执行、谁可以读到哪一步的产物。多个分支仍按依赖串行执行。用「自动排版」整理节点，用「适应全图」查看整体。拖动后会保留手动排版，点击「保存」保存修改。
4. 先用一条小输入试运行。确认节点来源、模型和权限符合当前任务。每个节点可以继承当前角色，也可以选择已配置的自定义子智能体。运行问题可在相应节点或工作流的属性中查看。

### 示例一　把会议纪要整理成三步

在空白工作流里按表格顺序创建三个节点，连成 `n1 → n2 → n3`。`n1` 和 `n2` 是按顺序新建时分配的 ID。使用现有定义时，以节点属性里显示的实际 ID 为准。

| 节点 | 类型 | Prompt |
| --- | --- | --- |
| 提取要点 `n1` | 任务 | 从 `{{input}}` 提取主题、结论和待确认事项。用项目符号输出。 |
| 核对待办 `n2` | 审查 | 根据 `{{n1}}` 列出待办、负责人和截止日。原文没给的信息标为待确认。 |
| 整理纪要 `n3` | 结果 | 把 `{{n1}}` 的结论和 `{{n2}}` 的待办写成可转发的 Markdown 纪要。 |

`{{input}}` 是运行时填写的任务输入。`{{n1}}` 引用一个能沿依赖边到达当前节点的祖先产物。直接前驱的产物也会自动附到节点消息中。体积较大的产物可能用预览和文件引用传递。

### 示例二　验收有一次返工机会

把「起草 `n1` → 验收 `n2` → 交付 `n3`」连成依赖链，给 `n2` 设置「验收 gate」。在「属性」的工作流设置里启用返工，入口选 `n1`，验收选 `n2`，最大轮数填 `2`。这个上限包含首轮，因此还可以返工一次。虚线显示的是返工区间，普通依赖保持为无环图。

- `n1` 用 `{{input}}` 写草稿。把 `{{retry_feedback}}` 放进提示词，请节点按反馈修订。首轮没有反馈，`{{attempt}}` 从 `1` 开始。
- `n2` 检查 `{{n1}}`，仅返回一个 JSON 对象。通过时用 `{"verdict":"pass","reason":"待办均有明确状态"}`。要返工时用 `{"verdict":"retry","reason":"补充未确认事项的状态"}`。
- 通过后执行 `n3`。到达轮数上限仍收到 `retry`，这次运行标为「未通过」，交付节点跳过。无法解析验收结果时，在运行历史查看该节点的转写。

## 在会话里运行和查询

使用工作流工具前，确认会话绑定了目标工作区。角色设置的「扩展能力 → 工作流编排」开启后，模型才可调用这组工具。用户也可直接在工作流中心点「运行」，填写输入并确认。

- 用户明确要求启动已保存流程时，先调用 `workflow_list` 获取 ID、精确名称、适用场景和可运行状态。同名时使用 ID。多个匹配且无法确定时，先让用户选定。缺少定义或草稿不可运行时，引导用户在工作流中心搭建或修复后保存。
- 调用 `workflow_run` 时传精确的 `workflow` ID 或名称，把本次任务原文或明确的任务说明放入 `input`。默认任务可以传空字符串。受理后回复工作流名和 `runId`，让用户在会话运行条或「运行历史」看进度。工具受理后，节点在后台执行，本回合无需等待或轮询。
- 用户问「上次验收为什么没过」时，调用 `workflow_status`。查指定运行传 `run_id`，省略时查本会话最近一次。用状态、验收原因和产物引用回答。全文、逐节点转写及历史轮次在工作流中心的「运行历史」中可读。
- 状态为「待确认」时，请用户在所属会话的运行条定位权限请求。要停止运行，在运行条或「运行历史」点「停止」。按回执报告实际状态，受理状态表示运行已排入后台。
