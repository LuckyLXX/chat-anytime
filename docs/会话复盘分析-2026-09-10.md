## 三、发现的优化点（按影响排序）

### P0-1　中止判定仍有 4 次漏网：stopReason=error 却带着中止原文

**现象**：近 3 天出现 4 次 `stopReason:"error"` 但 `errorMessage:"This operation was aborted"` 的组合：

- `2026-09-08 14:01`（cloudhub skill 调试）
- `2026-09-08 16:51`（自动化跨角色切换修复）
- `2026-09-09 09:14`（oil-icon 安装）
- `2026-09-09 17:11`（MCP 编辑优化）

**根因**：`src/main/run-outcome.ts` 的 `isAbortedMessage` 只认 `stopReason === "aborted"`，而中止语义的判定实际上分两条路径——`resolveRunOutcomeStatus(abortRequested, messages)` 靠 `abortRequested` 标记兜底（用于侧栏圆点），但 `message-normalize.ts:122` 计算气泡 `error` 字段时只看 `isAbortedMessage(message)`，**没有 `abortRequested` 这一路兜底**。所以当用户点停止、Pi 却落了 `stopReason:"error"` 时（网络层被中断、provider 返回中止态而非 abort 态），圆点正确显示中止，气泡却把 `This operation was aborted` 原样爆红展示。

这正是 08-18 那次「中止不再爆红」修复的残余缺口：修的是 `aborted` 分支，漏了 `error` + 中止文案分支。

**建议**：在 `run-outcome.ts` 增加 `isAbortText(errorMessage)`（匹配 `abort`/`Request aborted` 等 SDK 原文，与现有注释「绝不能靠匹配英文文案判定」的原则**不冲突**——原则针对的是「把英文文案当作中止的**唯一**依据」，这里是用它做 `error` 分支下的**补充**判定，且只在已有 error 时降级为中止，不改变 `aborted` 的权威判定）。`message-normalize.ts` 改用 `aborted = isAbortedMessage(m) || (m.errorMessage && isAbortText(m.errorMessage))`，`error` 字段相应置空。

### P0-2　automation 运行记录状态被 finally 块错判

**现象**：`runs.jsonl` 近 8 条全部 `status:"ok"`，但会话 JSONL 里 `2026-09-08 09:00` 的日报会话明确出现过 `stopReason:"error"` + `Stream ended without finish_reason`（流被截断，卡片渲染残缺）。

**根因**：`pi-runtime.ts:659-710` 用 `succeeded` 标志位判定——`await record.session.prompt()` **不抛异常**就置 `succeeded = true`。而 Pi 的 `prompt()` 在 provider 返回流式错误时可能正常返回（错误写进了消息列表而非抛出）。`finally` 里虽然有 `abortedRun` 兜底，但那只判中止，不判真实错误，于是 `succeeded ? "completed" : "failed"` 走到 completed。

**影响**：无人值守的自动化任务是最需要准确失败信号的场景——用户早上 9 点不看屏幕，靠的就是运行记录页的红点。

**建议**：`finally` 中的结算改为复用 `resolveRunOutcomeStatus(false, messages)` 的完整三态（`aborted` / `failed` / `completed`），而不是 `succeeded` 布尔量；`afterAutomationRun` 写入 store 的 `status` 同步为三态。同时把 `errorMessage` 落进运行记录，让「失败」可诊断。

### P1-1　browser_screenshot 110 秒超时集中复发

**现象**：6 次全部为 110s 超时，时间集中在两簇：

- `09-08 18:35 / 18:37`（2 次）
- `09-09 09:41 / 09:43 / 09:45 / 09:48`（4 次，连续 4 次）

**矛盾点**：`09-09 10:28` 刚提交了 `fix(browser): 隐藏标签截图不再悬挂 110s——截图前自动揭示标签+专用 30s 超时`，但失败全部发生在 **09-09 09:41~09:48，即修复落地前 40 分钟**。所以这 6 次属于已被修复的问题，不是新回归。

**仍值得做的**：`ensureTabRenderable` 现在失败时是「快速失败 + 可操作原因」，但模型侧连续 4 次重试同一操作、每次都耗掉一个 LLM 回合。建议在工具回执的错误文案里直接给出「连续失败 N 次，建议改用 browser_snapshot 取文本或先 browser_tabs 检查标签状态」的降级指引，减少无效重试回合。

### P1-2　bash 长命令缺少进度可见性

**现象**：`ask_question` 中位等待 79 秒、最长 226 分钟（用户离开）；`bash` p95 28 秒、最长 397 秒（`grep -rn listAll node_modules`）。单会话 `2026-09-08 14:01` 跑了 94 次 bash、耗时 56 分钟。

**观察**：`ask_question` 的 226 分钟等待说明一个问题被挂起后，整个会话处于不可用的僵死状态——没有超时、没有提醒。虽然 `QuestionBroker.reset(sessionId)` 在会话销毁时会取消，但会话还活着时用户忘了答就永久阻塞。

**建议**（低风险、可选）：给 `ask_question` 增加一个软提醒——挂起超过 N 分钟后在侧栏会话项上显示「等待回答」状态（复用现有 `runStatus` 机制加一个 `waiting` 态即可，不改协议核心），避免用户完全遗忘。

### P1-3　重复用户消息 = 会话分叉的静默产物

**现象**：3 个会话出现完全相同的用户消息：

- `2026-09-09 16:26`（安装 oil-icon）：「请安装这个 Skill」×2、「rolldek 技能支持选择生图模型吗」×**3**
- `2026-09-07 19:57`（三屏原型）：「做一个三屏原型」×2

**根因**（已从 JSONL 的 parentId 链确认）：这不是 UI 重复提交的 bug，而是**会话分叉（branch）**。JSONL 中两条相同 user 消息拥有**同一个 parentId**（分别是 `da8a9e3f` 和 `d0ce2ae8`）——即同一父节点的两个兄弟分支。触发条件是：助手回合失败（`stopReason:"error"`，429/524）→ 用户点重新生成或重发 → Pi 从父节点开新分支。

**问题不在正确性，在可读性**：渲染端按线性列表展示，用户看到的是「同一句话发了 3 遍」，且分叉前的兄弟分支内容被隐藏，无法判断哪条是当前有效路径。

**建议**：这是 Pi 的线性时间线模型与树状存储的不匹配。最小改动是在渲染端对「同 parentId 的兄弟 user 消息」标记分叉角标（如「重新生成」徽标），并把非当前分支的历史消息折叠。属于体验优化，改动面较大，建议单独立项。

### P2-1　模型能力参数不兼容导致整轮报废

**现象**：`2026-09-09 16:26` 会话出现 `Unexpected reasoning effort high. Supported types are xhigh (default), medium, and low.` —— 切换模型后 `thinkingLevel:"high"` 不被新模型支持，整轮失败。同一会话还叠了 4 次 429。

**背景**：`pi-runtime.ts:136` 默认 `thinkingLevel = "medium"`，但用户可在 UI 调到 `high`；换模型时 `applyModelOverrides` 只处理 contextWindow/maxTokens，**不校验 thinkingLevel 是否被目标模型支持**。

**建议**：`switchSessionModel` / `createAgentSession` 换模型时，若目标模型声明了受支持的 thinking 档位且当前档位不在其中，静默降级到最接近的档位并在状态行提示一行，而不是让第一次请求直接 400。

### P2-2　skill 执行效率：cloudhub-weekplan-reader 单次抓取 4 分钟

**现象**：`2026-09-08 14:01` 会话 94 次 bash 中，38 条是同一条 `fetch_dept_weekplan.py` 命令；用户明确反馈「现在抓取一次要快 4min 有点久」。单次执行 211s / 227s。

**性质**：这是外部 skill 的性能问题，不是 PiDesktop 的缺陷。但暴露了一个平台侧机会——**长命令缺少阶段性输出回显**。当前 bash 工具是「跑完一次性返回」，4 分钟内模型完全看不到进度，也无法提前判断方向错了。

**建议**：可参考已实现的 `runtime-shell-kill.ts` 模式（按命令终止），给 bash 工具增加「超时前回传已有 stdout」的能力，让长命令在中途可见。改动面较大，作为独立候选。

## 六、风险与边界
