# 自定义通道对接说明

> 给**内网工作软件**（钉钉类、企业 IM、工单系统、自己写的服务）用的一条通用接入点：
> 你的脚本把消息推进来，PiDesktop 在本地会话里跑完任务，答案再回到你的脚本。
> 官方通道（飞书长连接）不需要看这份文档；本页只讲自定义通道。
>
> 版本：2026-11-12（IM 通道 P2）。代码：`src/main/im-custom-channel.ts`；
> 面板：设置 → 消息通道 → 自定义通道。

## 0. 一句话版本

```bash
# 1) 推一条消息进去（等价于「有人给我发了消息」）
curl -X POST http://127.0.0.1:8787/v1/messages \
  -H "Authorization: Bearer <你的 Token>" \
  -H "content-type: application/json" \
  -d '{"peerId":"zhangsan","text":"帮我看下今天发了什么版","replyUrl":"http://127.0.0.1:8799/reply"}'

# 2) 答案会 POST 回 replyUrl；不想开回调服务就轮询：
curl "http://127.0.0.1:8787/v1/replies?since=0&token=<你的 Token>"
```

## 1. 前提

| 条件 | 说明 |
| --- | --- |
| PiDesktop 正在运行 | 端点属于桌面应用：**应用关闭 = 连接被拒绝**，没有常驻服务 |
| 总开关 + 通道开关都打开 | 设置 → 消息通道 → 「启用 IM 通道」和该通道的「启用这个通道」 |
| 已保存接入 Token | 面板里「生成」一个 32 位令牌，或自己填；没 Token 通道不会启动 |
| 白名单非空 | 空白名单 = 不服务任何消息（拒绝优先）。填脚本会用的 `peerId` |
| 监听地址 | 缺省 `127.0.0.1`（只本机）；脚本在别的机器上就选 `0.0.0.0`，自行确认网络边界 |

端口在面板上显示的实际地址里（`http://127.0.0.1:<port>/v1`）。填 `0` 表示每次启动随机，
脚本不方便写死，**建议填一个固定端口**（如 `8787`）；端口被占用时通道会显示「启动失败：
监听 127.0.0.1:8787 失败：端口已被其他程序占用」，换个端口即可。

**注意两个端口不是一回事**：面板里填的是 PiDesktop 的监听端口（脚本往里推消息），
脚本自己的回调服务（示例里的 `replyUrl` 端口 `8799`）是脚本在监听。两者写成同一个端口时，
后起来的那个会 `EADDRINUSE`——通道就会「启动失败」。

## 2. 鉴权

三条路由都要带 Token，三种放法任选一种：

- 请求头 `Authorization: Bearer <token>`（推荐）
- 请求头 `X-PiDesktop-Token: <token>`
- 查询参数 `?token=<token>`（只建议给 `GET` 用；`POST` 用头更安全）

Token 不对统一 `401`，并带 `WWW-Authenticate: Bearer`。Token 与飞书 App Secret 走同一条
系统加密存储（`credentials.json`），**不会**写进 `settings.json`、也不会出现在日志里。

## 3. 推消息：`POST /v1/messages`

请求体（JSON，≤256KB）：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `peerId` | ✅ | 发送人标识（账号/工号/openId 都行，≤120 字）。**一个 peerId 对应一条 PiDesktop 话题** |
| `text` | ✅ | 消息文本（≤20,000 字符，超出截断）。支持 `/status`、`/stop`、`/new`、`/help`、`/allow <码>`、`/deny <码>` 指令 |
| `messageId` | 可选 | 上游消息 id。**同一条消息重投（同 id）只处理一次**；不传则每次生成新的 |
| `replyUrl` | 可选 | 答案回调地址（`http(s)://`）。不传就只能轮询 |

响应：

| 状态码 | 体 | 含义 |
| --- | --- | --- |
| `202` | `{"ok":true,"messageId":"…","peerId":"…"}` | 已收下，后台开始处理 |
| `400` | `{"ok":false,"error":"缺少 peerId（发送人标识）"}` | 请求体不合法（错误信息直接可读） |
| `401` | `{"ok":false,"error":"token 不正确…"}` | 鉴权失败 |
| `413` | `{"ok":false,"error":"请求体超过 262144 字节"}` | 太大（别把文件塞进来） |
| `404` | `{"ok":false,"error":"未知路由…"}` | 路径写错 |

`202` 只代表**收下了**，不代表任务成功：任务结果通过回调或轮询回来。任务失败也会回一条
带原因的文本（例如模型报错、审批超时）。

## 4. 收答案

### 4.1 回调（推荐）

推消息时带上 `replyUrl`，我们每产生一条出站文本就 `POST` 一次：

```json
{ "channelId": "custom-ab12cd", "peerId": "zhangsan", "messageId": "上游消息 id", "text": "…答案…", "at": 1794457411825 }
```

- 超时 8 秒，**只投递一次**，失败不重试（失败原因记在面板的诊断行里）；
- 因此生产环境建议「回调 + 轮询」都用：回调即时，轮询兜底；
- 我们不向对方发送任何凭据（请用 URL 里的随机段或你自己的网关校验来源）；
- 一条长答案可能分多条回调（按 20,000 字符 / 28KB 切片），按到达顺序拼接即可。

### 4.2 轮询

```
GET /v1/replies?since=<游标>&token=<token>[&peerId=<id>][&limit=1..50]
```

```json
{
  "ok": true,
  "items": [{ "seq": 12, "peerId": "zhangsan", "text": "…答案…", "at": 1794457411825 }],
  "next": 12
}
```

- `since` 传上次拿到的 `next`（首次传 `0`）；`items` 只含 `seq > since` 的条目；
- 队列最多保留最近 200 条（落后太多会丢最旧的，回调不受影响）；
- 单次最多 50 条，来得及就按固定间隔（1–2 秒）轮询，不要空转。

### 4.3 探活

```
GET /v1/health?token=<token>
→ {"ok":true,"channelId":"custom-ab12cd","endpoint":"http://127.0.0.1:8787/v1","listening":true,"outbox":0,"cursor":12}
```

面板上的「检查」按钮走同一条判定：Token 在、服务在监听就显示 `服务已监听 http://…`。

## 5. 指令与审批

- 消息文本以 `/` 开头时按指令处理：`/status` 看会话状态、`/stop` 停当前生成、`/new` 开新话题、`/help` 看帮助；
- 工具需要确认时（`accessMode` 决定哪些要确认），我们会回一行：

  ```text
  需要确认：bash — rm -rf build
  发送 /allow ABCD2345 允许一次，或 /deny ABCD2345 拒绝。
  ```

  把 `/allow 码` 当成普通消息发进来即可（走同一个 `POST /v1/messages`）；超时（缺省 10 分钟，
  可配）自动拒绝。自定义通道没有卡片，所以**只有文本审批这一条路**。

## 6. 安全与边界

- **只收文本**。图片/文件请脚本先存到工作区，再把路径写进 `text`（例如「看下 /d/ws/a.png」）。
- 默认只监听 `127.0.0.1`。选 `0.0.0.0` 时任何人只要能连上端口、拿到 Token 就能让 AI 在你工作区里干活，
  请自行加网络边界（内网 ACL / 反向代理鉴权）。
- 白名单是第二道门：`peerId` 不在名单里时不会建会话、不会跑任务，只会回一条带 `peerId` 的提示
  （每人 10 分钟最多一次，防刷）。
- 会话权限用通道上的「会话权限」：`read-only` / `workspace`（推荐）/ `ask` / `full`。
- 去重表是 500 条 LRU（按 `messageId`），足够覆盖平台重投；别用递增计数器假装 messageId。
- 通道跟着应用生命周期：应用重启后自动按绑定路径重开话题，未取走的答案会丢（轮询队列只在内存里）。

## 7. 示例脚本

仓库里有一份可直接跑的 Node 脚本：`docs/im-channel-bridge-example.mjs`。

```bash
# 终端 A：起示例（它自己开一个回调服务器 8799，然后推一条消息进去）
PIBASE=http://127.0.0.1:8787/v1 PITOKEN=<token> node docs/im-channel-bridge-example.mjs "帮我看下今天发了什么版"

# 只想看轮询这条腿：
PIBASE=http://127.0.0.1:8787/v1 PITOKEN=<token> node docs/im-channel-bridge-example.mjs --poll
```

脚本干的三件事就是全部对接工作：`POST /v1/messages`、`POST` 回调里收答案、`GET /v1/replies` 兜底。

## 8. 排查清单

| 现象 | 先看哪里 |
| --- | --- |
| `ECONNREFUSED` | 应用没运行，或通道没启用/启动失败（面板里的红字） |
| `401` | Token 与面板里保存的不一致（改过就重新保存一次） |
| `400` | 看返回的 `error`：常见是漏 `peerId`、`text` 不是字符串 |
| `202` 但一直没有答案 | ① 白名单为空/不含该 `peerId`（会收到一条提示文本）；② 模型还在跑（面板「最近消息事件」有时间）；③ 回调地址不通（诊断行里有 `回调 … 失败`） |
| 只收到半截答案 | 长答案会分多条（回调多条 / 轮询多条），按顺序拼 |
| 重启后丢了答案 | 轮询队列在内存里；重要场景请开回调 |
