# A1 浏览器页面弹窗自动处理（P0）

> 来源：`docs/GenericAgent借鉴分析.md` 第六节 A1；本条已登记在 `docs/迭代记录.md` 待办区。
> 优先级 P0（缺陷：不修会持续烧掉模型往返）。规模 S。

## 背景与目标

PiDesktop 全仓库无 `javascriptDialog` 处理（grep 为空）。页面执行 `alert/confirm/prompt`
或触发 `beforeunload` 时，浏览器会**暂停该标签页的 JS 执行**等待用户应答：

- CDP `Runtime.evaluate` 永不 settle → 主进程 `withOpTimeout`（`browser-automation.ts:543`，
  `MAIN_OP_TIMEOUT_MS` 默认 110s，紧贴 utility 侧 120s RPC 看门狗）才会超时；
- 模型白等近两分钟，只拿到一句笼统的「浏览器操作超时」，**无法判断是页面弹窗还是页面卡死**，
  通常会重试或换方案，代价进一步放大；
- 与「可达即操作」的既有设计相悖：本项目已有「可行动错误」纪律
  （见 `browser_*` 的 busy 重试、截图可见性前置条件），弹窗这块是唯一的漏洞。

**目标**：自动化操作遇到页面弹窗时，① 自动应答使操作继续；② 把弹窗内容**回传给模型**，
让它知道页面弹过什么（否则模型会在错误假设上继续决策）。

## 关键事实（已核实，实施时可直接引用）

| 事实 | 位置 |
|---|---|
| CDP 封装是惰性 attach：`if (!contents.debugger.isAttached()) contents.debugger.attach("1.3")` | `browser-automation.ts:807-810` |
| 所有操作最终都走这个 `cdp()` | 同上 |
| 主进超时 110s | `browser-automation.ts:543-558` `withOpTimeout` |
| 标签页在 main 进程由 `BrowserPreviewController` 持有，自动化通过 `webContentsFor(tabId)` 拿 WebContents | `browser-preview.ts:40-70` |
| 控制器已有「按标签页存状态」的先例：`tabRefs`（引用签名）、`automationEndedAt`、`busy` 锁 | `browser-automation.ts` 内 |
| `BrowserAutomationData` 是成功载荷的联合类型，新增字段需同步协议 + utility 侧回执文案 | `src/shared/protocol.ts:729-743` |
| 现有事件监听范式：`contents.debugger.on("message", ...)` 在 Electron 的 `Debugger` 类型上可用（`WebContents.debugger` 是 EventEmitter） | 待实施时确认 TS 类型 |

## 实施步骤

### 步骤 1：控制器内新增弹窗状态与监听

文件：`src/main/browser-automation.ts`

1. 新增模块级常量与类型：

```ts
/** 自动化期间自动应答页面弹窗时，回传给模型的提示（per-tab 待读队列）。 */
export interface DialogNote {
  type: string;      // alert / confirm / prompt / beforeunload
  message: string;
  /** 是否被自动接受（true）或取消（false）。 */
  accepted: boolean;
}
```

2. 在 `BrowserAutomationController` 类内加字段：

```ts
/** 每个标签页待读的弹窗记录：下一次操作回执里附上并清空。 */
private readonly pendingDialogs = new Map<string, DialogNote[]>();
/** 已注册 Page.enable + 弹窗监听的标签页（避免重复注册）。 */
private readonly dialogWatchTabs = new Set<string>();
```

3. 新增私有方法 `ensureDialogWatch(tabId, contents)`：

```ts
private async ensureDialogWatch(tabId: string, contents: WebContents): Promise<void> {
  if (this.dialogWatchTabs.has(tabId) || contents.isDestroyed()) return;
  this.dialogWatchTabs.add(tabId);
  await this.cdp(contents, "Page.enable");
  contents.debugger.on("message", (_event, method, params) => {
    if (method !== "Page.javascriptDialogOpening") return;
    const type = String((params as { type?: unknown })?.type ?? "alert");
    const message = String((params as { message?: unknown })?.message ?? "");
    void this.autoAcceptDialog(tabId, contents, type, message);
  });
}
```

4. 新增自动应答：

```ts
private async autoAcceptDialog(tabId: string, contents: WebContents, type: string, message: string): Promise<void> {
  // 自动化期间一律接受：beforeunload 的离站确认不应拦住 AI 导航；
  // confirm/prompt 的默认“取消”会让页面走另一条分支，与模型预期不符。
  try {
    await this.cdp(contents, "Page.handleJavaScriptDialog", { accept: true });
    const notes = this.pendingDialogs.get(tabId) ?? [];
    notes.push({ type, message: message.slice(0, 200), accepted: true });
    this.pendingDialogs.set(tabId, notes);
  } catch { /* 弹窗可能已被页面自行关闭；忽略 */ }
}
```

5. 在 `execute()`（或现有 `cdp()` 调用前的统一入口）里，**每次操作前**调用
   `ensureDialogWatch(tabId, contents)`。注意：不能在 `cdp()` 内部调用（会递归/每命令都 await），
   应在每次 op 开始处调用一次。

6. **取出待读弹窗**：在 op 返回结果前，读出并清空：

```ts
private takeDialogNotes(tabId: string): DialogNote[] {
  const notes = this.pendingDialogs.get(tabId) ?? [];
  this.pendingDialogs.delete(tabId);
  return notes;
}
```

7. **清理**：在 `releaseSession` / 标签页关闭路径里一并
   `this.pendingDialogs.delete(tabId); this.dialogWatchTabs.delete(tabId);`
   （与现有 `tabRefs.delete` 同处），避免泄漏。
   注意 `contents.debugger` 的监听器随 WebContents 销毁自动失效，无需手动 off。

### 步骤 2：协议与回执

文件：`src/shared/protocol.ts`、`src/main/browser-automation.ts`、`src/main/runtime-browser.ts`

1. 协议：给需要回传弹窗的操作结果加可选字段。**最小侵入方案**——不改每个 case，
   而是在 `BrowserAutomationResult` 的成功分支加一个可选旁路：

```ts
export type BrowserAutomationResult =
  | { ok: true; data: BrowserAutomationData; dialogs?: BrowserAutomationDialogNote[] }
  | { ok: false; error: string };
```

   其中 `BrowserAutomationDialogNote` 为步骤 1 的 `DialogNote` 的共享层定义
   （放 `protocol.ts`，避免 main 与 utility 各定义一份）。

2. `browser-automation.ts` 每个 op 返回前 `const dialogs = this.takeDialogNotes(tabId);`
   并挂进结果（为空则不带该字段，保持字节兼容）。

3. `runtime-browser.ts` 的 `run()` 之后统一追加文案。**推荐做法**：加一个
   `appendDialogNotes(text, result)` 纯函数（放在 `runtime-browser.ts` 内或
   `browser-automation.ts` 的共享导出），在需要文本回执的工具里调用：

```
⚠ 页面弹出了 confirm：「确定要删除吗？」（已自动确认，未阻塞操作）
```

   实现要点：凡是返回 text 的工具（snapshot/click/type/press/scroll/select/upload/eval/wait/get）
   都在其文本尾部拼这段。为避免逐个改，可在 `run()` 的调用点后做一次
   `withDialogNotes(result)` 包装——**具体落点由实施者按现有代码结构选择，
   原则是「每处回执都能看到弹窗提示」**。

### 步骤 3：测试

文件：`src/main/browser-automation.test.ts`

现有测试是纯函数级（不起 Electron）。因此：

1. **纯函数单测**：`appendDialogNotes` / 弹窗记录队列（take 语义：取出即清空、
   多次弹窗累积、无弹窗时零变化）——提取成可测的纯函数或轻量类。
2. **集成验证（手动/脚本）**：起真实页面 `data:text/html,<script>confirm("hi")</script>`
   或用本地静态页，通过 `browser_navigate` + `browser_snapshot` 观察：
   - 操作在远小于 110s 内返回（关键断言）；
   - 回执含 `⚠ 页面弹出了 confirm：「hi」`。

## 验证方式

1. `npm test` 全绿（新增纯函数用例）。
2. `npm run build` 全绿。
3. 真机冒烟（重启应用后，用内置浏览器）：
   - 打开一个会弹 `confirm` 的本地页面 → 调 `browser_snapshot`；
     期望：秒级返回 + 回执带弹窗提示（**不是 110s 超时**）。
   - 打开 `beforeunload` 页面（表单有未保存内容）→ `browser_navigate` 离开；
     期望：正常导航完成，回执提示 beforeunload 已被自动确认。
4. 回归：不弹窗的普通页面，回执与现状逐字一致（无新增文案）。

## 风险与假设

| 风险 | 说明与对策 |
|---|---|
| `Page.enable` 的开销 | 每个标签页一次，可忽略。**不要在 `cdp()` 里调**，否则每条命令都 `Page.enable` |
| 一律 accept 是否会做危险操作 | `confirm` 被接受 = 同意。但**自动化本来就是 AI 在驱动页面**，AI 点下去的按钮本来就该按它的意图走；拒绝反而让页面走「取消」分支，与模型看到的 DOM 不一致，更难排查。**若日后要更保守**：`beforeunload` 接受、`confirm`/`prompt` 记录后**接受但把 message 回传**（本计划已是这个形态，策略集中在 `autoAcceptDialog` 一处，易改） |
| 弹窗记录被误当用户输入 | 不涉及——记录只进回执文本，包在不可信内容标记之外，且**不执行**其中任何内容 |
| `beforeunload` 依赖浏览器默认行为 | Electron 对 `beforeunload` 的拦截由 CDP dialog 事件覆盖；若实测未被接管，退回在 `will-navigate` 阶段处理（现有 `contents.on("will-navigate")` 已有钩子） |
| 类型 | `contents.debugger.on` 的签名需确认（Electron 的 `Debugger` 继承 EventEmitter）；若 TS 报错，用 `(contents.debugger as unknown as { on: (e: string, cb: (...a: unknown[]) => void) => void })` 并加注释说明理由 |
