# B3 CDP 批处理原语（先用于 upload）（P1）

> 来源：`docs/GenericAgent借鉴分析.md` 第六节 B3；本条已登记在 `docs/迭代记录.md` 待办区。
> 优先级 P1（缩短瞬态元素时间窗）。规模 M（含一个必须做的降级路径）。

## 背景与目标

`upload()`（`browser-automation.ts:948-975`）当前需要 **3 次独立 CDP 往返**：

```
Runtime.evaluate({ returnByValue: false })   → 拿 .objectId（第 1165 行的远程对象）
DOM.requestNode({ objectId })                → 拿 nodeId
DOM.setFileInputFiles({ files, nodeId })     → 真正上传
```

GA 的实测经验（`memory/tmwebdriver_sop.md`，文件上传章节）：

> 瞬态 input 的核心是**缩短发现 → setFileInputFiles 的时间窗**：优先同 batch 完成；
> 再不行用 DOM 事件监听；猴子补丁仅作兜底思路。
> 典型文件上传：`getDocument(**depth:1**)` → `querySelector(input[type=file])` → `setFileInputFiles`

许多站点的 file input 是**点击「选择文件」后才挂载**的（React 组件的瞬态节点）。
三个独立往返之间元素可能已被卸载 → `DOM.requestNode` 报错或 `setFileInputFiles` 打到旧节点。

GA 的解法是 `{cmd:'batch', commands:[...]}`：一次 WS 往返执行多条 CDP 命令，
并用 `$N.path` 语法引用第 N 条结果的字段（`background.js:handleBatch` 的
`JSON.stringify(params).replace(/"\$(\d+)\.([^"]+)"/g, …)`）。

**目标**：控制器内加一个轻量批处理原语，把 upload 的 3 次往返降到 1 次。
**注意**：Electron 的 `webContents.debugger.sendCommand` 本身就是一条 CDP 连接上的串行命令，
「3 次往返」的代价主要在 **JS 侧 await 与 IPC 调度**（以及其间页面可能变化的时间窗），
所以本项收益**不是网络往返**而是**时间窗收窄 + 出错面减少**。
预期收益中等，不要夸大——但实现成本也低。

## 关键事实（已核实）

| 事实 | 位置 |
|---|---|
| `cdp()` 封装：惰性 attach + `sendCommand` | `browser-automation.ts:807-810` |
| upload 的三步实现 | `browser-automation.ts:948-975` |
| 上传上限：单次 20 文件、单文件 20MB（`MAX_UPLOAD_FILE_BYTES`） | `browser-automation.ts:46, 952-953` |
| `COLLECT_CORE` 收集的是元素数组，`Runtime.evaluate` 用 `(${COLLECT_CORE})[${index}]` 取第 index 个 | `browser-automation.ts:963` 附近 |
| debugger 绑定不随命令 detach（惰性 attach 后保持），故「懒 attach 复用」已天然成立 | `browser-automation.ts:807-810` |
| GA 自己也警告：**前序命令失败时 `$N` 引用会静默变 undefined** | `memory/tmwebdriver_sop.md` |

## 设计决策（先定，再实现）

1. **只做内部原语，不暴露成工具。**
   理由：`$N` 引用语法一旦交给模型，写错就是静默传 `undefined`（GA 实测的坑）。
   模型侧继续用 `browser_upload` 这类语义化工具，**批处理的复杂度留在实现里**。
2. **必须有降级**：批处理任一步失败 → 记录原因 → **回退逐步调用**（保持现有行为可用）。
3. **不做 `$N` 通用插值引擎**（那是 GA 为「让模型编排命令」设计的）。
   我们只需要 upload 这一条固定链路，**直接写死三步**更安全、更易测：

   —— 因此本项的实际形态调整为：**新增 `uploadFast()` 单一函数**，
   用 `Runtime.evaluate` 在**一次页面脚本执行内**完成「找元素 + 设文件」。
   见下方「方案 A/B 对比」。

### 方案对比

| | 方案 A：通用 `cdpBatch` + `$N` 插值 | 方案 B：单次 `Runtime.evaluate` 完成上传 ⭐ 推荐 |
|---|---|---|
| 实现 | 需插值解析器 + 引用失败检测 | 页面内一次脚本，用 `DataTransfer` 直接给 `input.files` 赋值 |
| 往返 | 1 次（但仍是 3 条 CDP 命令） | **1 次**，且只有 1 条命令 |
| 前提 | 无需页面配合 | 需要 `DataTransfer` API（Chromium 全支持） |
| 风险 | `$N` 静默 undefined（GA 的坑） | `DOM.setFileInputFiles` 的**真实文件**语义：某些站点读 `input.files[0]` 的 `path` 属性会拿不到（浏览器安全限制，两种方案都有此问题） |
| 可测性 | 需 mock CDP | 脚本字符串可单测（构建产物断言） |

**推荐方案 B**，理由：GA 的 SOP 里其实明确写了这条更优路径——

> 文件上传：⭐首选 **DataTransfer API**（纯 JS，无 CDP 依赖）：
> `new File([content],name,{type}) → new DataTransfer().items.add(file) → input.files=dt.files → dispatch input+change`；
> CDP `DOM.setFileInputFiles` 在 tmwd 桥环境 nodeId 跨调用失效，**不推荐**

**但注意**：GA 不推荐 `setFileInputFiles` 的原因是「**tmwd 桥的 nodeId 跨调用失效**」——
那是它自己扩展环境的限制。**Electron 里 `DOM.requestNode` 返回的 nodeId 在单次调用内有效**，
我们现有实现可用（只是要 3 步）。且 `DataTransfer` 方案要求**把文件内容读进页面**
（`File([content])` 需要内容），而我们的文件在工作区、可能很大（上限 20MB）——
**把 20MB 通过 `Runtime.evaluate` 的 expression 传进页面是不可接受的**。

**所以最终结论（修正推荐）**：
- **方案 B 变体**：用**一次** `Runtime.evaluate` 完成「定位元素 + 返回 objectId」的**合并**——
  这本来就是一步，无法再合并；
- 真正的收益点在于**合并 `DOM.requestNode` 与 `DOM.setFileInputFiles`**：
  `DOM.setFileInputFiles` 其实**同时接受 `objectId`**（CDP 规范：`nodeId`/`backendNodeId`/`objectId` 三选一）。
  **若 Electron 的 CDP 透传支持 `objectId`，则 3 步可省为 2 步，且跳过 `DOM.requestNode` 这一最易失效的环节。**

→ **本项的实际第一步是验证这件事**（详见下方步骤 1）。这是低成本、高确定性的改进。

## 实施步骤

### 步骤 1（前置验证，必须先做）：`setFileInputFiles` 是否接受 `objectId`

写一次性探针（临时 `.mts` 脚本，用 `npx tsx` 跑，或直接在应用里临时改一行加 `console.log`）：

```ts
const remote = await this.cdp(contents, "Runtime.evaluate",
  { expression: `(${COLLECT_CORE})[${index}]`, returnByValue: false });
const objectId = remote.result?.objectId;
// 关键：直接用 objectId，跳过 DOM.requestNode
await this.cdp(contents, "DOM.setFileInputFiles", { files, objectId });
```

**分支**：
- **成功** → 采用（少一步、少一个易失效环节）；
- **报错 `Invalid parameters`** → 退回 `DOM.requestNode`（现状），本项只保留「失败原因更明确」的改进，
  即把 `upload()` 的错误信息从「无法定位上传控件」细化为「页面可能已变化 / 该元素不是 file input」；
- **若方案 A（通用 batch）仍有必要**（例如未来要接 `Page.printToPDF` 之类的多步链），
  再单独立任务，不在本轮做。

### 步骤 2：实现（按步骤 1 结果）

文件：`src/main/browser-automation.ts` 的 `upload()`

1. 若 `objectId` 可行，`upload()` 简化为两步，并在 `DOM.setFileInputFiles` 失败时
   **回退**到 `DOM.requestNode` 路径：

```ts
private async setFileInputFiles(contents: WebContents, objectId: string, files: string[]): Promise<void> {
  try {
    await this.cdp(contents, "DOM.setFileInputFiles", { files, objectId });
    return;
  } catch (error) {
    // 某些 Electron/CDP 版本不接受 objectId：回退到 requestNode（现状路径）。
    // 这是降级而非失败——两条路径的语义完全一致。
    const node = await this.cdp(contents, "DOM.requestNode", { objectId });
    if (!node?.nodeId) throw error;
    await this.cdp(contents, "DOM.setFileInputFiles", { files, nodeId: node.nodeId });
  }
}
```

2. **时间窗收窄**：现在的顺序是「定位（evaluate）→ 校验签名 → requestNode → setFileInputFiles」。
   把 `verifyRef` 挪到**最靠近** `setFileInputFiles` 的位置（它本身只是内存比较，无往返），
   确保「定位 → 设文件」之间没有多余 await。
3. **错误信息细化**（无论步骤 1 结果如何都做）：
   - 元素不存在 → 「上传控件已从页面移除（页面可能已变化，请重新 browser_snapshot）」；
   - 元素存在但不是 file input → 「@eN 不是文件上传控件（该元素是 <tag type=...>），请 snapshot 后选择 input[type=file]」。
     判据：`el.tagName === 'INPUT' && el.type === 'file'` 可在 `buildLocateScript` 之外单独查，
     或在 evaluate 里一并返回 `isFileInput` 布尔。
4. **保留并强化重试语义**：若 `setFileInputFiles` 报「元素已失效」类错误，
   可**重新执行一次完整链路**（重新定位 + 设置），因为瞬态元素可能在点击后重新挂载。
   上限 1 次重试（避免无限循环），并在回执里说明「已重试一次」。

### 步骤 3：测试

`src/main/browser-automation.test.ts`：

1. `buildLocateScript` 产物含 `isFileInput` 判定（若采用）；
2. 错误信息分支（纯字符串/逻辑层）；
3. **降级路径**：mock 一个「`setFileInputFiles` 首次抛错、`requestNode` 成功」的假 CDP，
   断言最终调用成功且 `DOM.requestNode` 被调用过（这条最有价值，防止降级被静默删掉）。

> 现有测试不起 Electron，故步骤 3 的第 3 条需要把 `setFileInputFiles` 的**降级逻辑提为可注入的纯函数**
> （接受一个 `cdp: (method, params) => Promise<unknown>` 参数），这样无需 Electron 即可单测。
> **这是本项的主要设计约束：把三段 CDP 调用抽成 `uploadViaObjectId(cdp, files, objectId)` 之类的纯函数。**

## 验证方式

2. `npm run build` 全绿。
3. 真机冒烟（**必须用真实上传场景**，最好是「点击后才出现 input」的站点）：

## 风险与假设

| 风险 | 对策 |
|---|---|
| `objectId` 不被接受 | 步骤 1 前置验证；失败则保留 `requestNode` 路径，本项退化为「错误信息细化 + 重试」 |
| 降级路径被后续重构删掉 | 专门的降级路径单测（步骤 3 第 3 条） |
| 收益被高估 | 本项**如实标注为中等收益**；如果实测时间窗收窄不明显，可在迭代记录里写「收益有限，主要价值是错误信息细化」 |
| 重试造成重复上传 | 重试上限 1 次；且 `setFileInputFiles` 是**幂等**的（设置同一批文件），重复调用不会上传两次 |
| 把批处理暴露给模型 | **明确不做**（GA 自己的坑）；若未来要做，必须单独立项 + 风险评审 |
