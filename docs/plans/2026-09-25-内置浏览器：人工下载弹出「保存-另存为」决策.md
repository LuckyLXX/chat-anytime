# 内置浏览器：人工下载弹出「保存 / 另存为」决策

## 背景与目标

现状（`src/main/browser-downloads.ts` 头注释 + `browser-preview.ts:handleDownload`）：内置浏览器的下载只有两种命运——
AI 自动化会话绑定且 `browser_navigate` 带过工作区的标签页 → 静默落盘到 `<工作区>/.pidesktop/downloads/`；**其余（用户自己浏览的标签）一律 `item.cancel()`，一个字节都不落盘**。用户在右侧预览面板里手动点「下载图片 / 导出文件」等于什么都没发生。

本次目标：人工下载时**弹出应用内决策卡片**，提供
- **保存**：存到配置好的默认下载目录；
- **另存为…**：打开系统保存窗口，可自选目录与文件名；
- **取消**：放弃这次下载。

默认目录与「是否每次询问」在**浏览器面板内**可配置（用户已确认：默认目录初始值 = 系统下载目录 `app.getPath("downloads")` = `C:\Users\li857\Downloads`；询问开关默认开启；60 秒无响应自动按默认目录保存并提示「已自动保存」；AI 自动化触发的下载保持现状静默落盘、绝不弹窗）。

## 关键技术事实（本次真机探针实测，决定实现路线）

探针资产（保留在 `.pidesktop/`，不入库）：`.pidesktop/browser-probe/p8-download-decide.mjs`、`p8b-done-event.mjs`、`p8c-download-staging.mjs`（用现成 `run.mjs` + harness + 独立 userData/downloads 跑，Electron 43.2.0，结果在 `.pidesktop/browser-probe/results/p8*.json`）：

1. **`item.setSavePath()` 必须在 `will-download` 回调里同步调用。** 不在 `will-download` 里定路径的下载**永不 finish**：字节全部到齐、文件停在 `<downloads>/<uuid>.tmp`、`state` 一直 `progressing`，直到连接断开才变 `cancelled`（p8b：2MB 全到、12 秒无 done）。
2. **下载启动后再改路径无效**（p8c `set-pause-change-path`）：`will-download` 里同步 `setSavePath(c1)`，1.5 秒后改 `setSavePath(c2)` 并 `resume()`，`getSavePath()` 返回 `c2`，但**实际文件落在 `c1`**。→ 「先暂停、等用户选完再定路径」这条最直觉的路**走不通**。
3. **`pause()` + 稍后 `resume()` 本身是可靠的**（p8c `set-then-pause-resume`：同步 pause，1.5 秒后 resume → `done: completed`、文件完整 2MB）。但既然路径必须同步定死，暂停就没有必要，反而多占连接。
4. 同步 `setSavePath(不存在但会 mkdir 的目录)` + 正常下载 → `done: completed`、文件完整（p8c `sync-set`）。
5. 探针里 `cancel()` 后 300ms 内 `downloadURL()` 重发没能触发第二次 `will-download`（p8c `cancel-then-redownload` 只有一次 will/done）——**放弃「取消后重发」方案**（对 POST/一次性 URL 也不安全）。

**因此采用方案 S（直接落默认目录 + 另存为时搬移）**：
`will-download` 里同步 `setSavePath(<默认目录>/<清洗后的唯一文件名>)`（与现有代码同一套 `mkdirSync` + `sanitizeDownloadName`，新增同名递增），让下载正常跑到 `done`；同时把「待决策」信息推给渲染端弹卡片。用户点「保存」= 什么都不用做（文件已在默认目录）；点「另存为」= 弹系统保存窗口，拿到路径后把文件搬过去（下载未完成则等 `done` 再搬）；点「取消」= `item.cancel()`（未完成）或删文件（已完成）。60 秒超时 = 保持默认目录 + 推一条「已自动保存」提示。

## 实施步骤

### 1. 新增纯逻辑模块 `src/main/browser-manual-download.ts`（+ 单测）

不依赖 Electron，可直接单测：
- `resolveDownloadDir(configured: string | undefined, fallback: string): string` —— 配置为空/非字符串 → fallback（`app.getPath("downloads")` 由调用方传入）。
- `uniqueDownloadName(dir: string, filename: string, isTaken?: (path: string) => boolean): string` —— `photo.png` 已存在 → `photo-1.png`（沿用 `browser-save-image.ts:saveImageBytes` 的命名口径：`base-N.ext`，默认 `existsSync`）。
- `moveDownloadedFile(from: string, to: string): Promise<"moved" | "same" | "failed">` —— 同路径返回 `same`；`rename` 失败（跨盘 `EXDEV`）回退 `copyFile` + `unlink`；失败返回 `failed`（调用方据此提示）。
- `type ManualDownloadPrefs = { dir: string; ask: boolean }`、`normalizePrefs(raw, fallbackDir)`。
- 单测 `src/main/browser-manual-download.test.ts`（复用 `browser-downloads.test.ts` / `browser-save-image.test.ts` 的 tmp 目录风格）。

### 2. settings：`BrowserSettings` 扩两个字段

`src/shared/protocol.ts`：`interface BrowserSettings { enabled: boolean; downloadDir?: string; downloadAsk?: boolean }`（`downloadAsk` 缺省视为 `true`）。

`src/main/settings.ts`：
- `normalizeBrowser` 保留并校验新字段（`downloadDir` 只接受 trim 后非空字符串，`downloadAsk` 只接受 boolean；坏值丢弃而不是丢弃整条）。
- 新增导出纯函数 `mergeBrowserSettings(next: BrowserSettings | undefined, current: BrowserSettings | undefined): BrowserSettings | undefined`——**只从 `next` 取 `enabled`，`downloadDir`/`downloadAsk` 一律保留 `current` 的值**。理由：设置页（`GeneralSettings`）提交的是渲染端本地 `settings.browser` 整体对象，它不知道我们在预览面板里改过的下载配置；不设防就会被「保存通用设置」静默抹掉（与 Jev 丢失同型的坑）。
- `migrateSettings` 的读回、`settings-store.test.ts` 的顶层键契约不受影响（顶层键 `browser` 已存在），但要跑一遍确认。

`src/main/index.ts` 与 `src/main/pi-runtime.ts` 两处 `settings.save` 镜像改用 `mergeBrowserSettings(command.settings.browser, settings.browser)`；`settings-save-contract.test.ts` 的三处镜像契约应保持绿（键集合未变）。

### 3. 主进程：`BrowserPreviewController` 的下载分流与决策

`src/main/browser-preview.ts`：

- 扩展策略类型（保持向后兼容，现有 `{ dir }` 语义不变，自动化测试无需改）：
  ```ts
  export type PreviewDownloadPolicy = "cancel" | { dir: string; ask?: boolean };
  ```
- 构造参数追加一个可选的 hooks 包（避免第 7、8、9 个散装参数）：
  ```ts
  export interface ManualDownloadHooks {
    prefs: () => ManualDownloadPrefs;                                   // 读设置（含唯一文件名解析不在此）
    setPrefs: (patch: { dir?: string; ask?: boolean }) => ManualDownloadPrefs;
    chooseDirectory: () => Promise<string | undefined>;                 // 系统「选择文件夹」
    chooseSavePath: (defaultPath: string) => Promise<string | undefined>; // 系统「另存为」
  }
  ```
- `handleDownload` 分流（**所有分支都先同步动作、绝不 await**）：
  1. `policy === "cancel"` 或拿不到 tab → 现状：`item.cancel()` + 上报（不动）。
  2. `{ dir }` 且 `ask !== true` → 现状：静默落盘（自动化路径，不动）。
  3. `{ dir, ask: true }` → 人工询问分支：
     - 计数超 `MAX_TAB_DOWNLOADS`（20）→ 直接 `cancel()` 并上报（防恶意页面刷 20+ 张卡片；真人不会连点 20 次）。
     - `safeName = uniqueDownloadName(dir, sanitizeDownloadName(item.getFilename()))`；
     - `mkdirSync(dir, { recursive: true })` → `item.setSavePath(join(dir, safeName))`；失败 → `cancel()` + `prepare-failed`（沿用现有分支）。
     - 建 `PendingManualDownload` 记录：`{ id, tabId, item, filename, url, source(host), directory, filePath, totalBytes, downloaded: false, relocateTo?: string, cancelled: false, timer }`，存 `Map<id, record>`，并 `setTimeout(60_000)` 到自动保存。
     - `item.on("done")`：`downloaded = true`；若 `relocateTo` 已定 → `await moveDownloadedFile(filePath, relocateTo)` 并推 notice；若记录已被取消 → 删文件。
     - **推送状态**：把 `pendingDownloads` 写进 tab 的 `BrowserPreviewState` 并 `publish(state, tabId)`（沿用现有 state 更新 + publish 模式）。
- 新命令处理（`handle`）：
  - `{ type: "download-prefs" }` → 刷新 `state.downloadPrefs`（读 hooks.prefs()）。
  - `{ type: "download-prefs-set"; ask?: boolean; chooseDir?: boolean; dir?: string }` → `chooseDir` 时 `await hooks.chooseDirectory()`（用户取消则不改），否则用传入字段 → `hooks.setPrefs(patch)` → 写回 state 并 publish（**设置值由主进程落 settings，不经过渲染端全局 settings**）。
  - `{ type: "download-decision"; id: string; action: "save" | "save-as" | "cancel" }`：
    - `save`：清 pending（文件已在目标位），移出 map + 清定时器。
    - `save-as`：`await hooks.chooseSavePath(filePath)`；取消 → 保持 pending 不动；确认 → 记录未完成则 `relocateTo = chosen`，已完成则立即 move + 清 pending + notice（成功给路径、失败给原因）。
    - `cancel`：`item.cancel()`（未完成）或 `unlink` 已落盘文件（已完成），清 pending + 定时器。
  - 超时回调：视作 `save` + notice「已自动保存到 <目录>」，清 pending。
- 清理：`closeTab` / `dispose` / 标签销毁时清掉该 tab 的 pending 定时器与记录（下载进行中的由 Chromium 随 contents 取消；已落盘文件保留，语义等价于「保存」）。
- `DownloadInfo` / `onDownload`（自动化回执通路）**不动**：`handleDownload(info)` 已按「有会话绑定该标签」过滤，人工下载不会污染 AI 回执。

`src/main/index.ts` 接线：
- `downloadPolicy` 回调改为组合：自动化策略非 `"cancel"` → 用它；否则返回人工策略：
  ```ts
  const browser = settings.browser;
  const dir = resolveDownloadDir(browser?.downloadDir, app.getPath("downloads"));
  return { dir, ask: browser?.downloadAsk !== false };
  ```
- 注入 `ManualDownloadHooks`：
  - `prefs` / `setPrefs`：读/写 `settings.browser.downloadDir|downloadAsk`，通过现有 `updateSettings` 落盘（保持 settings 写入纪律：走同一个持久化入口，不另开写盘路径）。
  - `chooseDirectory`：`dialog.showOpenDialog(win, { title: "选择下载保存位置", properties: ["openDirectory", "createDirectory"], defaultPath: prefs.dir })`。
  - `chooseSavePath`：`dialog.showSaveDialog(win, { title: "另存为", defaultPath, filters: [...] })`（与现有 `index.ts` 的 dialog 用法一致，无窗口时退回无父窗口调用）。

## 风险与假设

- **依赖 `setSavePath` 同步调用**这条实测结论：探针 p8b/p8c 已四路验证（不设路径永不 finish、启动后改路径无效、同步设路径正常完成）。实施后 p8d 会再端到端复验一次。
- **另存为的搬移是普通 fs 操作**：同盘 `rename` 瞬时；跨盘 `copyFile + unlink`（大文件会慢，运行时给「正在保存…」的 notice，不留假成功）。
- **同名冲突**：默认目录已有同名文件时按 `-1/-2` 递增，绝不覆盖（与 `browser_save_image` 同口径）。
- **AI 绑定过的标签页，用户手动下载仍静默落工作区**（Electron 无法区分手势来源）：保持现状，作为已知边界写进迭代记录；如需改变，只能按「该标签页当前是否有自动化操作在进行」近似，本次不做。
- **设置页不会丢下载配置**：靠 `mergeBrowserSettings` 在两侧镜像兜底，而不是依赖渲染端同步（渲染端只在 popover 内使用 prefs，不动全局 settings store）。
- **不动的东西**：自动化下载的落盘位置与回执通路（`DownloadInfo`/`onDownload`）、`browser_save_image`、每标签 20 上限、`sanitizeDownloadName` 的既有行为。
