# B1 `type()` 的键盘事件语义实测与补齐（P1）

> 来源：`docs/GenericAgent借鉴分析.md` 第六节 B1；本条已登记在 `docs/迭代记录.md` 待办区。
> 优先级 P1（**待实测项**：先证伪，再决定是否改）。规模 S。

## 为什么这条必须先实测

GA 的 `memory/tmwebdriver_sop.md` 记录了：「`insertText` 快但无 key 事件；受控组件需补 dispatch `input` 事件」。
初版分析据此判断 PiDesktop 的 `type()` 可能有静默失败。但逐行读码后，**结论需要修正**：

1. `buildTypeScript`（`browser-automation.ts:325-354`）在 `mode="fill"` 时**已经**用原生 setter 清空
   并派发 `input` + `change`（第 332-333 行）——清空这一步对受控组件是安全的；
2. 而**写入**用 `Input.insertText`（`browser-automation.ts:890`）。CDP 的 `insertText`
   语义是「插入不属于按键的文本」，**它会产生 `input` 事件**（因此 React 的 `onChange` 通常会触发）；
   但它**不产生 `keydown`/`keypress`/`keyup`**。
3. 所以「React/Vue 受控组件会不会同步」这个初步问题，**大概率答案是不会出问题**；
   真正可能出问题的是**监听键盘事件的代码**：自动补全（keyup 触发）、表单校验（keydown 触发）、
   搜索防抖（keyup）、以及「输入后按 Enter 提交」这类依赖按键的交互。

**因此本项的正确形态是**：先写探针**分别**验证「input 事件是否触发」与「keydown 是否触发」，
再只针对后者决定是否补键盘事件。**不许凭推断直接改代码**。

## 探针设计（第一步，实施者照做）

用一个**自建静态页**（放工作区 `outputs/` 或 `.pidesktop/`，用 `browser_navigate` 以
`file:///` 打开即可——本项目支持本地文件映射到回环静态服务）：

```html
<!doctype html>
<meta charset="utf-8">
<body>
  <input id="controlled" placeholder="受控输入">
  <input id="plain" placeholder="裸输入">
  <pre id="log"></pre>
  <script>
    const log = (s) => { document.getElementById('log').textContent += s + "\n"; };
    // 1) input 事件（React onChange 同源）
    document.getElementById('controlled').addEventListener('input', (e) => log('input:' + e.target.value));
    // 2) keydown / keypress / keyup（insertText 疑似不触发）
    ['keydown', 'keypress', 'keyup'].forEach((t) =>
      document.getElementById('controlled').addEventListener(t, () => log(t)));
    // 3) 用原生 setter 模拟 React 受控组件：值由 state 回写
    let state = '';
    const el = document.getElementById('controlled');
    el.addEventListener('input', () => { state = el.value; });
    window.__probe = () => ({ state, dom: el.value, events: document.getElementById('log').textContent });
  </script>
</body>
```

**执行与断言**：

| 步骤 | 操作 | 期望观察 |
|---|---|---|
| 1 | `browser_type @e1 "hello"`（fill 模式） | 页面 log 出现 `input:hello` |
| 2 | `browser_eval` 读 `window.__probe()` | `state === 'hello'`（受控组件同步）；`events` 是否含 `keydown` |
| 3 | 同上，用 append 模式再输入 | 值正确累加，`state` 同步 |

**分支决策**：

- **情况 A：`state` 同步、无 keydown** → 受控组件没问题；只补「键盘事件」这一薄层。
- **情况 B：`state` 不同步** → 受控组件确实失效，需补 `input` 派发（但第 1 步的 log 若显示
  `input:hello`，说明事件已触发，则该结果**不可能**出现；若出现则说明 `insertText`
  在本环境不产生 input，需按情况 C 处理）。
- **情况 C：完全没有 `input` 事件** → 必须在 `type()` 里补派发（见方案二）。

## 实施方案（按探测结果选择）

### 方案一（情况 A，推荐前置）：仅补 keydown/keyup

在 `type()`（`browser-automation.ts:886-895`）的 `Input.insertText` **之后**补一对键盘事件：

```ts
await this.cdp(contents, "Input.insertText", { text });
// insertText 只产生 input 事件、不产生按键事件；依赖 keyup 的自动补全/防抖逻辑需要这一对。
// 用 Enter 之外的通用键值会误导页面，故补「不可打印键之外」的最小语义：
// 这里补 keydown/keyup 各一次，key 取文本末字符对应的键（无法映射时用 'Unidentified'）。
await this.cdp(contents, "Input.dispatchKeyEvent", { type: "keyDown", key, code, ... });
await this.cdp(contents, "Input.dispatchKeyEvent", { type: "keyUp", key, code, ... });
```

**⚠ 关键判断：这一步有真实风险，可能弊大于利。**
- 合成 keydown/keyup 的 `key`/`code` 只能是猜的（一整段文本没有对应按键），
  页面若据此做逻辑（如「按了哪个键」的快捷键处理）会收到**错误信息**；
- `isTrusted` 方面 CDP 事件为 true，页面无法区分，所以错误信息会被当真；
- 部分站点的自动补全会因为收到一个不匹配的按键而**误触发或清空**。

**因此我给出的实施建议是：先做探针；若探针显示没有 keydown 但实际任务也未受影响（绝大多数站点
用 input/change 即可），则本项判定为「不需要改代码」，只把结论写进踩坑记录。**
只在**确有任务因缺 keyup 而失败**时，才做方案一，并且**只对显式请求的场景生效**——
即新增一个可选参数而非改变默认行为：

```
browser_type({ ref, text, mode, dispatchKeys?: boolean })  // 缺省 false = 现状
```

这样既保留兼容性，又给需要的人一条路。**不要默认开启**（会改变所有既有行为）。

### 方案二（情况 C）：补 input + change 派发

若探针显示 `insertText` 完全不产生 `input`（情况 C），则在 insertText 后用
`buildTypeScript` 里已有的同款模式派发：

```ts
await this.evaluate(contents, `(() => {
  const el = ${COLLECT_CORE}[${index}];
  if (!el) return false;
  el.dispatchEvent(new Event('input', { bubbles: true }));
  el.dispatchEvent(new Event('change', { bubbles: true }));
  return true;
})()`);
```

这与 `mode="fill"` 清空时的事件派发**同源同风格**，是本项目已有做法，无新风险。

## 验证方式

1. 探针三步（上表）跑完，把**原始 log 文本**记进迭代记录——这是本项的核心交付物。
2. 若改了代码：
   - `npm test`：`browser-automation.test.ts` 补 `buildTypeScript` 的 `dispatchKeys`
     或事件派发断言（纯字符串/逻辑层可测）；
   - `npm run build` 全绿；
   - 真机复测探针，确认「原先缺的事件现在有了，且没有引入重复触发」
     （重复触发的判据：log 里出现**两次** `input:hello`）。
3. **回归**：默认参数下（不传 `dispatchKeys`）行为与现状**逐字一致**。

## 风险与假设

| 风险 | 对策 |
|---|---|
| 凭 GA 的 SOP 直接改代码 | **本项纪律：先探针，后决策**。GA 的环境（Chrome 扩展 + 真实浏览器）与 Electron CDP 不完全可比 |
| 合成按键给出错误 key | 只在显式 `dispatchKeys: true` 时启用；默认不改行为 |
| 重复触发 input | 情况 C 的方案要断言「不出现两次」；情况 A 不派发 input 故无此风险 |
| 测试无法覆盖真实事件语义 | 探针必须是**真机 + 真实页面**；单测只覆盖代码分支，不冒充行为验证 |
