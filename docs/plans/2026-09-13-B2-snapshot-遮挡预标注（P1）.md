# B2 snapshot 预标注「可见但被遮挡」（P1）

> 来源：`docs/GenericAgent借鉴分析.md` 第六节 B2；本条已登记在 `docs/迭代记录.md` 待办区。
> 优先级 P1（省一次「点击才发现白点」的往返）。规模 S，但有一个必须绕开的陷阱（见「关键约束」）。

## 背景与目标

现状：遮挡检查**只在点击时**发生。`buildLocateScript`（`browser-automation.ts:306-324`）：

```ts
const top = hitTest(el);
if (top && top !== el && !el.contains(top)) return { ok: false, error: '元素被遮挡，无法点击（请先关闭遮挡层或滚动后重试）' };
```

后果：`browser_snapshot` 报告 @e7 可交互 → 模型 `browser_click @e7` → 报「元素被遮挡」→
模型重新 snapshot / 想办法关遮挡层。**一次甚至多次白轮**。

GA 的做法（`simphtml.py` 的 `handleOverlayContainer`）是**在读取阶段就把几何真相算清**：
用 `document.elementFromPoint(视口中心)` 反查「浏览器认为谁在最上层」，
把被覆盖的兄弟标成 `R:covered` 并在返回给模型前删掉。

**目标**：snapshot 阶段就标出「可见但点不到」的元素，让模型**第一次**就知道要换目标或先关遮挡层。

## 关键事实（已核实）

| 事实 | 位置 |
|---|---|
| **遮挡检查已存在**，函数名 `hitTest`，且**已考虑 root 空间差异**（iframe 文档的 `elementFromPoint` 用自己的局部坐标、ShadowRoot 用顶层视口坐标） | `browser-automation.ts:201-206` `HIT_TEST_FN` |
| 目前 `HIT_TEST_FN` 只被 `buildLocateScript` 使用（点击路径） | `browser-automation.ts:310, 318` |
| snapshot 脚本 `buildSnapshotScript` 逐元素产出 `SnapshotElement`，字段含 x/y/checked/selected/expanded 等 | `browser-automation.ts:266-303` |
| 行格式化是**纯函数** `formatSnapshotLine(item, index)` | `browser-automation.ts:436-451` |
| **元素签名** `elementSignature(item)` = 若干字段 join("|")，**click/type 会校验它** | `browser-automation.ts:454-458` + `verifyRef` |
| 上限：`MAX_SNAPSHOT_ELEMENTS = 200` | `browser-automation.ts:29` |

## ⚠ 关键约束（本项最大的坑，务必遵守）

`elementSignature` 是**快照与点击之间的一致性凭据**：snapshot 时记住签名，
click/type 时重新定位并比对，不一致就报「页面已变化，请重新 snapshot」。

**因此：「遮挡状态」绝对不能进签名。**
理由：遮挡是**随滚动/悬停/动画变化的瞬时状态**。若把 `obstructed` 纳入 `elementSignature`，
那么「snapshot 时被遮挡 → 用户滚了一下 → click 时不再被遮挡」会被判定为
**「页面已变化，引用失效」**，把一个本可成功的点击变成强制重新快照——**比现状更糟**。

**结论**：新增字段必须
1. 加进 `SnapshotElement`（供格式化用），
2. **不加进** `elementSignature` 的字段数组（`browser-automation.ts:455-457`），
3. 并在 `elementSignature` 函数上方加一行注释说明「遮挡状态刻意不入签名，因为它是瞬时状态」。

## 实施步骤

### 步骤 1：snapshot 脚本内做遮挡判定

文件：`src/main/browser-automation.ts`，`buildSnapshotScript`（266-303）

1. 在脚本头部注入 `HIT_TEST_FN`（与 `buildLocateScript` 同样方式，第 310 行是现成范例）：

```ts
export function buildSnapshotScript(cap: number, pageTextCap: number): string {
  return `(() => {
   ${VIEWPORT_POSITION_FN}
   ${PAGE_TEXT_FN}
   ${HIT_TEST_FN}
   const collectInteractiveElements = ${COLLECT_CORE};
   ...
```

2. 在 `.map((el) => {...})` 里加遮挡判定。**性能控制**：只对前 `OBSTRUCTION_PROBE_LIMIT`
   个元素探测（建议 60；`elementFromPoint` 单次很便宜，但 200 次 × 每次 snapshot 仍应设闸），
   且只在元素**已判定可见**时探测（被 `COLLECT_CORE` 的 `isVisible` 过滤过的才进来，故此处都可探）：

```ts
const OBSTRUCTION_PROBE_LIMIT = 60;

// 在 map 内：
const probe = idx < ${OBSTRUCTION_PROBE_LIMIT};   // idx 为 map 的第二参数
let obstructedBy = null;
if (probe) {
  const top = hitTest(el);
  if (top && top !== el && !el.contains(top)) {
    obstructedBy = top.tagName.toLowerCase()
      + (top.id ? '#' + top.id : '')
      + (typeof top.className === 'string' && top.className.trim() ? '.' + top.className.trim().split(/\\s+/)[0] : '');
  }
}
```

   注意 `.map((el) => ...)` 需改为 `.map((el, idx) => ...)`。
   同时把 `el.closest('[aria-modal="true"],[role="dialog"]')` 之类的**遮挡层语义**可选地记下来——
   **本计划不做**（无必要复杂度），只记遮挡者本身。

3. 返回值新增字段：

```ts
return { /* ...现有字段... */, obstructedBy };
```

### 步骤 2：类型与格式化

1. `SnapshotElement`（`browser-automation.ts:56-77` 附近）加：

```ts
/**
 * 元素在视口内可见、但中心点被另一元素挡住时的遮挡者描述
 * （如 `div.modal-mask`）。仅前 OBSTRUCTION_PROBE_LIMIT 个元素会探测，
 * 超出者为 null。**刻意不参与 elementSignature**：遮挡随滚动/动画变化，
 * 纳入签名会让「滚动后遮挡消失」被误判为引用失效。
 */
obstructedBy: string | null;
```

2. `formatSnapshotLine`（436-451）在 states 之后追加：

```ts
const obstructed = item.obstructedBy ? `（被 ${item.obstructedBy} 遮挡，点击会失败）` : "";
return `@e${index + 1} <${item.tag}${attrs}>${label ? ` ${JSON.stringify(label)}` : ""}${states.length > 0 ? ` [${states.join("、")}]` : ""}${obstructed}`;
```

   注意放在**行尾**（行首放会干扰模型对 `@eN` 的扫描，且现有格式以 `@eN` 开头最易解析）。

3. `elementSignature`（454-458）**不动**，只加注释；

4. `snapshot()` 里 `this.tabRefs.set(...)` 存的是 `{ signature, url }`，不涉及新字段，无需改。

### 步骤 3：工具描述

`runtime-browser.ts` 的 `browser_snapshot` description 现提到「@eN 引用…」。
建议加半句：

> 「行尾出现『被 X 遮挡』的元素点击会失败，请先关闭遮挡层（如弹窗/浮层）或改点其他元素。」

**只加这半句**（description 是每请求前缀成本，遵守 prompt-diet）。

### 步骤 4：测试

`src/main/browser-automation.test.ts`（纯函数层）：

1. `formatSnapshotLine`：`obstructedBy: "div.modal-mask"` → 行尾含 `（被 div.modal-mask 遮挡，点击会失败）`；
2. `formatSnapshotLine`：`obstructedBy: null` → 输出与**改造前逐字一致**（防回归，这条必须有）；
3. **`elementSignature` 不受遮挡影响**（关键回归）：
   两条 `SnapshotElement` 仅 `obstructedBy` 不同 → `elementSignature` 结果**相同**。
   这条测试直接钉住上面「关键约束」，防止后来者手滑把它加进签名数组。
4. `buildSnapshotScript` 产物字符串含 `hitTest` 与 `obstructedBy`（防止模板拼接漏掉 `HIT_TEST_FN`）。

> 现有 `browser-automation.test.ts` 里的 `SnapshotElement` 字面量需要同步补 `obstructedBy`
> 字段（TypeScript 严格模式下必填会报错）。**若改用可选字段 `obstructedBy?: string | null`
> 则可避免大面积改测试**——**推荐可选**，语义上「未探测」与「无遮挡」也确实不同。

## 验证方式

1. `npm test` 全绿（新增 4 例 + 修既有字面量）。
2. `npm run build` 全绿。
3. 真机冒烟（关键，必须真页面）：
   - 造一个「按钮被半透明遮罩盖住」的本地页（`position:fixed; inset:0` 的遮罩 + 底下一个 button）；
   - `browser_snapshot` → 被盖的 button 行尾应出现「被 div.mask 遮挡，点击会失败」；
   - **回归**：不带遮罩的普通页，snapshot 输出与改造前逐字一致；
   - **性能**：在元素密集页（>60 个交互元素）测 snapshot 耗时，与改造前对比增幅应 <20%。
4. 交叉验证（呼应「两套实现应当有差异」纪律）：确认标注**确实**能预测点击失败——
   对被标注的元素执行 `browser_click`，应得到「元素被遮挡」；对未标注的元素点击，应成功。

## 风险与假设

| 风险 | 对策 |
|---|---|
| **遮挡状态污染签名**（最严重） | 明确不入 `elementSignature` + 专门回归测试（步骤 4 第 3 条） |
| 探测开销 | 限前 60 个元素；真机测耗时（验证方式 3） |
| 瞬时遮挡（动画中）导致误标 | 文案用「点击会失败」而非绝对断言；且因为不入签名，误标**只影响提示不影响可用性**（模型仍可尝试点击，若成功则成功） |
| `hitTest` 在 iframe/Shadow 下的坐标系 | **已有实现已处理**（`HIT_TEST_FN` 注释明确说明 root 空间差异），直接复用即可，不要另写一套 |
| 可选字段 vs 必填字段 | 推荐可选（`obstructedBy?: string | null`），避免测试字面量大面积改动 |
