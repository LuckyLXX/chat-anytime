# C1 自动化运行记录补 `skipped` 态与跳过可见性（P2）

> 来源：`docs/GenericAgent借鉴分析.md` 第六节 C1；本条已登记在 `docs/迭代记录.md` 待办区。
> 优先级 P2（防错 + 可观测性）。规模 M（协议 + 调度 + 渲染三处联动）。

## 背景与目标

GA 的 `reflect/scheduler.py` 有 `max_delay_hours`（默认 6）：**超过计划时间 N 小时后不再触发**，
目的是「机器休眠/关机错过时间点后，不要执行一个早已过时的任务」（如「早 8 点生成昨日日报」下午 3 点才开机）。

**现状核对（已核实，与初版分析有差异，以此为准）**：

`automation-scheduler.ts` 的 `tick()` 用「`cronMatches(cron, now)` + `minuteKey` 防重 + 队列去重」驱动，
cron 是**分钟级精确匹配**，所以**错过的分钟天然不会被补跑**——
即 GA 想防的「重复/过时执行」在 PiDesktop 上**不会发生**。这项不是缺陷。

**真正的缺口是「可观测性」**：用户发现「今天的日报没跑」，打开运行记录却是一片空白，
**无法区分三种情况**：
1. 应用当时没开（错过了）；
2. 任务被暂停了（`enabled: false`）；
3. 上一轮还在跑，本轮被队列去重挡掉（`queue.some(...)`，`automation-scheduler.ts:66-68`）。

GA 的 `health_check()` 返回 `HEALTHY/OVERDUE/DISABLED/NEVER_RUN/ERROR` 五态，
其中 `OVERDUE`（超期未运行）与 `NEVER_RUN`（从未运行）正是这种**计划维度**的状态，我们没有。

**目标**：
1. 运行记录新增 `skipped` 状态（与既有的 `ok`/`error`/`aborted` 并列，语义中性，不是失败）；
2. 调度器在「本该运行但没运行」时写入一条 `skipped` 记录并带原因；
3. 渲染端三处识别该状态（筛选、图标、文案），并且**不与「失败」混淆**。

**明确不做**：`catchUpMinutes`（补跑）——见本文末「后续（需用户决定）」。

## 关键事实（已核实）

## 设计决策（先定，再实现）

1. **`skipped` 只进运行记录（`runs.jsonl`），不写 `task.lastRun`。**
   理由：`lastRun` 语义是「上一次**实际运行**」，被 skip 覆盖会让「上次成功时间」丢失，
   而调度与用户判断都依赖它。→ **`AutomationRunInfo.status` 的联合类型不扩**，
   只扩 `AutomationRunRecord.status`。这样改动面更小、语义更稳。

2. **`sessionId` 放宽为「`skipped` 时可选」。**
   `normalizeAutomationRun` 现在把它当必填。方案：改为
   `if (run.status !== "skipped" && !str(run.sessionId)) return undefined;`
   ——**向后兼容**（旧记录全有 sessionId，且旧记录不会有 skipped 状态）。
   同时 `AutomationRunRecord.sessionId` 类型改为 `sessionId?: string`。

3. **渲染端「查看会话」入口对 `skipped` 隐藏**（没有会话可看）。
   核对 `AutomationRuns.tsx` 里打开会话的按钮，加 `run.status !== "skipped" && run.sessionId` 条件。

4. **调度器保持纯净**：不引入存储依赖，改为新增 dep 回调 `onSkip?`，
   由 `pi-runtime` 侧负责落盘（与现有 `runTask`/`onError` 同模式）。

## 实施步骤

### 步骤 1：协议（`src/shared/protocol.ts`）

```ts
export interface AutomationRunRecord {
  // ...
  /** skipped = 本轮本该运行但被跳过（应用未运行/被暂停/上一轮未结束）；此时无会话。 */
  status: "ok" | "error" | "aborted" | "skipped";
  /** 跳过原因（仅 skipped）；同时作为 UI 上的说明文案。 */
  skipReason?: string;
  /** 回看入口；skipped 记录没有会话，故可选。 */
  sessionId?: string;
}
```

**不要**把 `skipped` 加进 `AutomationRunInfo`（决策 1）。

### 步骤 2：记录归一化（`src/main/automation-runs.ts`）

1. `normalizeAutomationRun`：

```ts
if (run.status !== "ok" && run.status !== "error" && run.status !== "aborted" && run.status !== "skipped") return undefined;
if (run.status !== "skipped" && !str(run.sessionId)) return undefined;  // skipped 允许无会话
```

2. `str(run.sessionId) ? { sessionId: run.sessionId } : {}` 改为条件携带；
3. 新增 `...(str(run.skipReason) ? { skipReason: run.skipReason } : {})`。

> ⚠ `normalizeAutomationRun` 的必填校验是第一道防线，**放宽它的同时必须补测试**：
> 「status=skipped 且无 sessionId」通过、「status=ok 且无 sessionId」仍被丢弃（防止放宽过度）。

### 步骤 3：调度器回调（`src/main/automation-scheduler.ts`）

1. deps 新增：

```ts
/** 本轮命中 cron 但未执行时回调（原因用于运行记录的 skipped 条目）。 */
onSkip?: (task: AutomationTask, reason: string) => void;
```

2. 队列去重处：

```ts
if (queue.some((candidate) => candidate.id === task.id)) {
  deps.onSkip?.(task, "上一轮尚未结束，本轮已跳过（串行队列避免并发）");
  lastFiredMinute.set(task.id, key);   // 已 skip 也算本分钟处理过，避免同分钟反复回调
  continue;
}
```

3. **启动时的「错过」扫描**（本项的可观测性主价值）：
   新增一个方法 `reportMissed(now)`，在 `start()` 里调用一次（并且建议**只在启动时**做，
   不要每分钟扫描）：

```ts
/**
 * 启动时扫描：今日已过去的 cron 命中分钟里，最后一次命中至今没有对应运行记录
 * 的启用任务 → 通知 onSkip（原因「应用启动时发现今日已错过该时间点」）。
 * 判据用「最后一次命中分钟」而非逐分钟，避免重复报告。
 */
```

实现要点：
- 对每个 `enabled` 任务，从今日 00:00 逐分钟（≤ 1440 次 `cronMatches`，成本可忽略）
  找到**最后一个** ≤ now 的命中分钟（注意时区：用任务自己的 `schedule.timezone`；
  `cronMatches` 已支持 tz，但「逐分钟」需要构造对应时区的时刻——
  **建议直接对本地时刻逐分钟调用 `cronMatches(expr, d, tz)`**，与我们 tick 的口径一致）；
- 若 `lastMatch` 距今超过 2 分钟（给正常触发留缓冲），且**没有** `startedAt >= lastMatch`
  的运行记录 → `onSkip(task, "应用未在计划时间运行（今日已错过）")`；
- **只报最后一次命中**（不是每一次），避免刷屏；
- 需要读运行记录来判断「是否已跑过」——调度器是纯模块，**这个判断放在 `pi-runtime` 侧**
  （`onSkip` 的消费者），或把「是否已跑过」作为一个 dep 传入。

  **推荐实现**：给 `onSkip` 的消费者（pi-runtime）传完整信息，由它决定是否落盘：

```ts
onSkip: (task, reason, at) => recordSkippedRun(task, reason, at)
```

  并在 `recordSkippedRun` 内检查 `readAutomationRuns(getAgentDir())` 是否已有
  `taskId` 相同且 `startedAt >= at` 的记录 → 有则不重复写。
  **这样调度器保持零存储依赖**（符合模块现状）。

### 步骤 4：落盘（`src/main/pi-runtime.ts`）

新增 `recordSkippedRun`：

```ts
function recordSkippedRun(task: AutomationTask, reason: string, at: number): void {
  // 已有该时间点之后的记录 → 说明已正常运行过，不重复记
  const existing = automationRuns.some((run) => run.taskId === task.id && run.startedAt >= at);
  if (existing) return;
  const agent = resolveAutomationAgent(task.agentId);   // 已有函数，注意 archived 也要能记
  automationRuns = appendAutomationRun(getAgentDir(), {
    id: randomUUID(),
    taskId: task.id,
    taskName: task.name,
    agentId: task.agentId,
    agentName: agent?.name ?? task.agentId,
    startedAt: at,
    durationMs: 0,
    status: "skipped",
    trigger: "cron",
    skipReason: reason
  });
  emitAutomationRuns();
}
```

要点：
- **不写 `lastRun`**（决策 1）；
- **不发 `automation-run` toast 推送**（跳过不需要打扰用户）；
- `agentName` 取不到时退化为 agentId（archived 角色的任务也应可记录）。

接线：`createAutomationScheduler({...})`（`pi-runtime.ts:2810`）加 `onSkip`。

   - **「查看会话」入口对 `skipped` 隐藏**（决策 3）。
2. `AutomationSettings.tsx:259`：任务行 `lastRun` 文案——**因为决策 1 不改 `lastRun`，
   此处无需改**。确认一次即可。
3. `App.tsx`：toast 不涉及 `skipped`（不发推送），**无需改**。确认一次。

### 步骤 6：测试

1. `automation-runs.test.ts` 补 4 例：
   - `skipped` + 无 `sessionId` → 通过，`skipReason` 保留；
   - `skipped` + 有 `skipReason` → 往返一致；
   - `ok` + 无 `sessionId` → **仍被丢弃**（防放宽过度）；
   - 混合列表（含 skipped）读写往返。
2. `automation-scheduler.test.ts` 补 3 例（用现成的 `tick(now)` 注入时刻）：
   - 同任务已在队列 → 触发一次 `onSkip`（且**同分钟只触发一次**）；
   - 正常触发路径**不**调 `onSkip`（防误报）；
   - 启动错过扫描：构造「今日 09:00 已过、now=10:00、无运行记录」→ `onSkip` 被调用，
     原因含「今日已错过」；已存在运行记录 → **不**调用。

## 验证方式

1. `npm test` 全绿（新增约 7 例）。
2. `npm run build` 全绿。
3. 真机冒烟（需要造时间条件）：
   - 建一个每天触发一次的任务，把系统时间/或直接在 `tick(now)` 单测层面覆盖（推荐单测覆盖，
     真机造时间成本高且不可靠）；
   - **界面验证**：设置页「运行记录」子页出现「已跳过」筛选，选中后能看到记录与原因，
     且**没有**「查看会话」按钮；
   - 常规运行（ok/error/aborted）的记录展示与现状逐字一致（回归）。
4. 跨重启：跳过记录能存活（写在 `runs.jsonl` 内，`MAX_RUNS` 裁剪不影响）。

## 风险与假设

| 风险 | 对策 |
|---|---|
| 放宽 `sessionId` 必填导致后续代码假设它存在 | **必须核对所有读 `AutomationRunRecord.sessionId` 的位置**（`automation.run.open` 那条命令最关键）：`skipped` 记录不可作为 `run.open` 的目标，需在入口显式拒绝并给出中性提示 |
| 启动扫描刷屏（多任务多角色） | 只报「最后一次命中」；每任务最多一条；`recordSkippedRun` 内有去重检查 |
| 把「跳过」显示成失败 | 中性图标 + 中性色 + 文案用「已跳过」，**不要**用 danger 色；toast 完全不发 |
| 时区处理 | 逐分钟调用 `cronMatches(expr, d, tz)`，与 tick 口径一致；测试必覆盖带 `timezone` 的任务 |
| `runs.jsonl` 200 条上限 | `MAX_RUNS=200`，跳过记录会挤占空间。**注意**：若某任务被高频跳过，可能挤掉有价值的历史。对策：`recordSkippedRun` 前置去重（同任务同一时间点只记一次）已能大幅缓解；若仍担心，可对 `skipped` 单独设更严的去重窗口（如同一任务 1 小时内最多 1 条 `skipped`）——**建议实施时加上这个窗口** |

## 后续（需用户决定，不在本项范围）

**`catchUpMinutes`（补跑语义）**：GA 的 `max_delay_hours` 表达的是相反需求——
「允许补跑，但设一个过期上限」。若用户希望「错过 8:00 但在 8:30 前打开电脑就补跑」：

- 需给 `AutomationTask` 加可选 `catchUpMinutes?: number`（缺省不补跑 = 现在的行为，向后兼容）；
- `tick` 里对每个任务检查「最后一次计划时间点是否落在 `now - catchUpMinutes` 内」，
  是则**补跑**（而非记 skipped）；
- 需处理「同一 tick 内多任务补跑」的排队（现有串行队列已能兜住）；
- 需与 `skipped` 记录协调（补跑成功 → 记 ok；超期 → 记 skipped 并说明超期）。

**建议先落地本项（可观测性），观察一段时间后再决定是否需要补跑。**
