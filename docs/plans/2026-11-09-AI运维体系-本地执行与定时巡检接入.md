## 一、背景：PiDesktop 在体系里的唯一位置

架构运维组有 6 个系统，职责边界是「谁能给什么」。PiDesktop 的定位只有一句话：

> **唯一碰得到现场的地方**：SSH 只读核对、桌面/浏览器操作、截图留痕、定时巡检、个人入口。

它**不是**知识中枢，也**不是**第二个 ArchOps。具体地：

| 该做 | 不该做 |
|---|---|
| 窗口日上机核对（只读）+ 截图 | 沉淀团队知识（知识只在 ArchOps 长） |
| 定时巡检、到点提醒 | 出审查结论（结论由 ArchOps 的 Agent 给） |
| 离线/断网时的临时分析 | 发链接（LanPages 负责） |
| 个人草稿 | 直接改生产（写操作一律回人工） |

### 当前问题

1. **变更窗口全靠人记**：T-1 该核对的清单有没有填齐、SQL 有没有校验过，没人自动查。
2. **执行核对没留痕**：上了机器看一眼就完了，事后复盘问「当时版本号是多少、磁盘用了多少」答不上来。
3. **复盘靠回忆**：窗口结束后几天才写复盘，细节已经丢了。

### 目标

三条定时任务 + 一份只读命令清单 + 一次技能复制，把「窗口前 / 窗口中 / 窗口后」串起来。

## 二、跨系统契约（你要消费的东西）

### 2.1 变更主档（ArchOps 侧，只读）

- 路径（ArchOps 容器内）：`/app/workspace/_shared/changes/<change_id>/change.json`
- 结构（关键字段）：

```json
{
  "change_id": "CHG-20261109-001",
  "title": "基金代销系统 3.2.1 版本投产",
  "system": "基金代销",
  "window": "2026-11-09 22:00-24:00",
  "risk": "中",
  "artifacts": {
    "review":    { "verdict": "通过", "url": "http://pages.corp.local:8080/s/chg-20261109-001/", "kb_refs": [] },
    "checklist": { "platform_id": 128, "verdict": "", "items_failed": null },
    "sql":       { "job_id": "", "rules_hit": null, "blocking": null },
    "verify":    { "recorded_at": "", "items": [] }
  },
  "decisions": []
}
```

### 2.2 ArchOps 的查询端点

```http
GET http://<archops-host>:8000/api/v1/changes?date=2026-11-09      # 当日变更列表（P3 的 A8 项）
GET http://<archops-host>:8000/api/v1/changes/CHG-20261109-001     # 单条主档
GET http://<archops-host>:8000/api/v1/health                       # 存活探针
（均无鉴权，内网）
```

> ⚠️ `A8` 端点由 ArchOps 侧 P3 实现。**若尚未就绪**：任务里的第一步改成「向用户要当日变更单号」，其余步骤不变——不要自己去翻文件系统猜路径。

### 2.3 回传方式（二选一）

| 方式 | 怎么做 | 前提 |
|---|---|---|
| **A（推荐，零新增）** | 核对记录写成 Markdown + 截图，在 ArchOps 新建会话里交给 `review_agent`，让它用 `change-pack` 技能写入 `artifacts.verify` | ArchOps 侧 P1 已完成（`change-pack` 技能可用） |

**方式 A 是默认**：PiDesktop 只做「采集 + 整理 + 交给人/Agent」，不直接写云端文件。

## 三、改造项

### P1 三条定时任务（核心）

在 PiDesktop 里用「自动化任务」建（界面：顶栏 `⏰` → 新建；或直接对当前会话说「建一个定时任务…」，Agent 会调 `automation_create`）。

三条任务的公共参数：

| 参数 | 值 | 理由 |
|---|---|---|
| `target` | `background` | 后台新会话执行，不打断当前对话 |
| `accessMode` | `full` | 无人值守时权限确认会挂起，必须 full |
| 模型 | 沿用 Agent 默认 | 这类任务不需要最强模型 |

---

#### 任务 1：T-1 变更齐套巡检（每天 18:00）

```json
{
  "name": "T-1 变更齐套巡检",
  "cron": "0 18 * * *",
  "target": "background",
  "accessMode": "full",
  "prompt": "执行每日变更齐套巡检，步骤如下：\n1. 取当天变更清单：curl -s 'http://<archops-host>:8000/api/v1/changes?date=<今天>'。若接口不可用（404/连不上），直接输出「ArchOps 统计端点不可用，请手工提供当日变更单号」并结束，不要猜。\n2. 对每条变更，检查 change.json 的三件事：\n   - artifacts.review.verdict 是否为空（方案审查是否完成）\n   - artifacts.checklist.platform_id 是否为空、items_failed 是否 > 0（清单是否填报、有失败项）\n   - artifacts.sql.blocking 是否为 null（SQL 是否校验过）、是否 > 0（有阻塞项）\n3. 输出一张 Markdown 表：变更单号 | 系统 | 窗口 | 风险 | 审查 | 清单 | SQL | 缺什么。\n   缺项用「❌ 待补：<具体项>」标出，齐备用「✅」。\n4. 结尾给一句结论：今天有几条变更、其中几条齐备、几条有阻塞。\n不要修改任何文件，不要发链接。"
}
```

**为什么 18:00**：变更多在 20:00 之后开始，18:00 出结果还来得及补材料。

---

#### 任务 2：窗口日执行核对（每天 21:30）

```json
{
  "name": "窗口日执行核对",
  "cron": "30 21 * * *",
  "target": "background",
  "accessMode": "full",
  "prompt": "执行窗口前只读核对，严格只读，禁止任何写操作（不改配置、不重启服务、不发版）。步骤：\n1. 取当日变更为「今天窗口」的条目（GET /api/v1/changes?date=<今天>，筛 window 含今天）。若没有可执行核对的目标，输出「今日无待核对变更」并结束。\n2. 对每条变更，按系统名找到对应 SSH 主机（ssh_hosts 列出已配置主机），依次执行以下只读命令并记录输出：\n   - uptime\n   - df -h\n   - free -m\n   - 当前发布版本（按系统实际路径，见下方配置表）\n   - 关键进程是否存活（systemctl is-active <服务名> 或 ps -ef | grep <关键字>）\n3. 把结果整理成 Markdown：变更单号 / 主机 / 命令 / 结果摘要。异常项（磁盘>85%、内存剩余<10%、进程 not-active、版本与变更单不符）用 ⚠️ 标出。\n4. 把这份 Markdown 保存到工作区 outputs/verify-<change_id>.md，并在结尾提示「请把本文件与截图交给 ArchOps 的 review_agent 写入 artifacts.verify」。\n绝不执行任何写入类命令；拿不到密码/连不上就如实报告，不要换命令绕过。"
}
```

配套需要准备（一次性配置）：

- **SSH 主机**：在 PiDesktop 的 SSH 面板里为每个系统建一台主机（地址/端口/用户名），密码由用户在终端密码卡片里输入（**不要写进 prompt、不要进对话记录**）。
- **每系统的「版本查询命令」表**（写在本文件附录 A，任务执行时读它）。
- **服务名清单**（同上）。

---

#### 任务 3：T+1 复盘草稿（每天 09:00）

```json
{
  "name": "T+1 复盘草稿",
  "cron": "0 9 * * *",
  "target": "background",
  "accessMode": "full",
  "prompt": "为昨日窗口的变更生成复盘草稿。步骤：\n1. 取昨日窗口的变更（GET /api/v1/changes?date=<昨天>）。没有就输出「昨日无窗口变更」并结束。\n2. 对每条，收集：变更结论（artifacts.review.verdict）、清单失败项（items_failed 与明细）、SQL 命中（rules_hit / blocking）、执行核对记录（读工作区 outputs/verify-<change_id>.md，若存在）。\n3. 输出复盘草稿 Markdown，固定四段：\n   ## 一、变更概况（单号/系统/窗口/风险/参与人）\n   ## 二、执行过程（时间线：方案审查→清单→SQL→发布→上机核对，每步结论）\n   ## 三、问题与偏差（没有就写「无」，不要编）\n   ## 四、改进项（每条写：改什么、谁负责、什么时候验证）\n4. 明确标注「本稿由 AI 起草，未经人工确认，不得直接入库」。\n不要调用 review_agent 的写库能力，不要发链接。"
}
```

**为什么是草稿**：体系里定了「AI 产出默认是草稿，人工确认后才入库」。这条不能破。

### P2 复制三个技能到本地（与 ArchOps 同源）

体系里 ArchOps 有三个技能：`change-pack` / `lanpages-publish` / `sql-validator-check`（+ `checklist-bridge`）。PiDesktop 作为个人入口，本地也放一份，**内容必须与 ArchOps 侧逐字一致**。

放置位置（选一个，推荐用户级）：

```
C:\Users\<你>\.agents\skills\change-pack\SKILL.md
C:\Users\<你>\.agents\skills\lanpages-publish\SKILL.md
C:\Users\<你>\.agents\skills\sql-validator-check\SKILL.md
C:\Users\<你>\.agents\skills\checklist-bridge\SKILL.md
```

复制来源：`D:\架构运维工作\skills\<name>\`（含 `scripts/` 子目录一起复制）。

**同步纪律**（写进本文件，避免两边漂移）：
- 改动只在一处发生：**先在 ArchOps 改**，然后复制过来；
- 复制后对比：`diff -r D:/架构运维工作/skills/change-pack ~/.agents/skills/change-pack`；
- 不要本地改完再反向同步——PiDesktop 是消费者的角色。

> `change-pack` 的脚本默认从 `$PI_WORKSPACE_ROOT` 或仓库根找 `workspace/`；在 PiDesktop 上**必须显式传 `--root`**（指向本地工作区），否则会写错位置。这一点要写进本地 SKILL.md 的「本机差异」小节。

### P3 把变更单号变成会话命名（可选，但很省事）

约定：在 PiDesktop 里处理某条变更时，会话标题用 `[CHG-20261109-001] <主题>`。

这样：
- 侧栏能按单号搜到历史会话；
- 和 ArchOps 的会话命名一致，交接时不用解释；
- 复盘时翻会话就能还原过程。

不需要改代码，靠习惯 + 本文件约定。

| # | 步骤 | 谁做 | 验证 |

## 六、风险与边界

| 风险 | 处理 |
|---|---|
| **误执行写命令** | 任务 prompt 三次强调「只读」；命令是固定白名单（附录 A）；发现越界立即停用任务并复盘 |
| 密码泄露 | 只用终端密码卡片人工输入；**绝不写进 prompt、不写进文件、不进对话记录** |
| 定时任务在无人时权限挂起 | `accessMode=full`；但**仍不放开写操作**（靠 prompt 约束 + 人工抽查） |
| ArchOps 端点未就绪 | 任务降级为「向人要单号」；不要自己翻文件系统猜路径 |
| 技能两边漂移 | 只允许「ArchOps → PiDesktop」单向复制，复制后 `diff` |
| 任务跑飞、反复重试 | 每条任务都是幂等的（只读 + 生成文件），重跑不产生副作用 |
