# A3 下载被静默取消——显式化并给自动化放行通道（P0）

> 来源：`docs/GenericAgent借鉴分析.md` 第六节 A3；本条已登记在 `docs/迭代记录.md` 待办区。
> 优先级 P0（**静默失败**：模型拿到「成功」回执，文件却不存在）。规模 S（第一步）~ M（第二步）。

## 背景与目标

**核实结论（与初版分析的判断不同，以此为准）**：不是「未处理下载」，而是**主动取消全部下载**。

`src/main/browser-preview.ts:218-221`：

```ts
if (!this.downloadGuardSessions.has(contents.session)) {
  this.downloadGuardSessions.add(contents.session);
  contents.session.on("will-download", (_event, item) => item.cancel());
}
```

这是**预览标签页的正确安全设计**（不让网页往磁盘写文件）。但对浏览器自动化是**静默失败**：

1. 模型点击「导出 CSV」→ CDP 点击成功返回 → 回执是「已点击 xxx」；
2. 下载被 cancel，文件不存在；
3. 模型无从得知，可能继续 `bash ls` 找不到文件、或对用户报告「已导出」。

本项目工作区场景里「导出/下载」是高频动作（报表、图片、附件），因此这条的**实际危害高于 A1**
（A1 是慢且报错，A3 是快且撒谎）。

**目标**（分两步，第一步必做，第二步可选）：
- **第一步（兜底可见）**：下载被取消时，把「本该下载的文件名 + URL」回传给模型，
  让它知道发生了什么并自行改道（用 `browser_eval` 取数据后写文件）。
- **第二步（能力放行）**：自动化会话绑定期间，把下载**定向到工作区**并回执工作区相对路径，
  使导出类任务真正可用。

## 关键事实（已核实）

| 事实 | 位置 |
|---|---|
| 下载守卫按 **session**（不是 tab）注册一次，回调 `item.cancel()` | `browser-preview.ts:218-221` |
| `BrowserPreviewController` **没有 workspace 概念** | 全文件 grep `workspace` 无结果 |
| 自动化控制器**知道会话**（`sessionTabs: sessionKey → tabId`），且 `browser_navigate` 请求带 `workspace` 字段（本地文件导航用） | `browser-automation.ts:576` / `protocol.ts:714` |
| `browser_navigate` 的 workspace 已用于静态服务挂载，说明「会话 → 工作区」信息在 navigate 时曾经手自动化控制器 | `browser-automation.ts` navigate 分支 |
| 标签页清理收口点（现有 `tabRefs`/`tabLastActiveAt` 同处清理） | `browser-automation.ts:648-652` `closeAutomationTab` |
| 最近一次自动化结束的时间窗（用于区分 AI 触发 vs 用户触发） | `browser-preview.ts:45` `automationEndedAt` + `isRecentAutomationPick` |

> **Electron 签名要点**：`session.on("will-download", (event, item, webContents) => …)`
> —— 第三个参数 `webContents` 能定位到具体标签页，这是实现「按标签页策略」的关键
> （现有代码把第三个参数丢掉了 `(_event, item)`）。**实施前请先用 `console.log` 验证一次
> `webContents` 非空**，这是本计划的唯一技术不确定点。

## 实施步骤

### 步骤 1：策略钩子（让预览控制器可被外部问「这个标签页该怎么办」）

文件：`src/main/browser-preview.ts`

1. 给 `BrowserPreviewController` 构造参数加一个可选钩子（现有第 4 个参数之后）：

```ts
/**
 * 下载策略：返回 "cancel" 取消（预览页默认，安全底线）；
 * 返回 { dir } 则把下载定向到该目录（自动化会话绑定期间用）。
 * 缺省 = 全部取消（保持现有行为，向后兼容）。
 */
private readonly downloadPolicy?: (tabId: string) => "cancel" | { dir: string },
```

2. 改造 `will-download` 注册（保留 `downloadGuardSessions` 的「每 session 只注册一次」语义）：

```ts
if (!this.downloadGuardSessions.has(contents.session)) {
  this.downloadGuardSessions.add(contents.session);
  contents.session.on("will-download", (event, item, webContents) => {
    const tabId = webContents ? this.tabIdFor(webContents) : undefined;
    const policy = tabId ? this.downloadPolicy?.(tabId) : undefined;
    if (policy && policy !== "cancel") {
      event.preventDefault();
      const name = sanitizeDownloadName(item.getFilename());
      item.setSavePath(join(policy.dir, name));
      this.onDownload?.({ tabId: tabId!, filename: name, url: item.getURL(), saved: true });
      return;
    }
    // 保守路径：仍然取消，但把「本该下载什么」报出去（本计划的核心修复）
    event.preventDefault();
    item.cancel();
    this.onDownload?.({ tabId: tabId ?? "", filename: item.getFilename(), url: item.getURL(), saved: false });
  });
}
```

3. 新增 `private tabIdFor(contents: WebContents): string | undefined`
   （遍历 `this.tabs` 找 `view.webContents === contents`）；
4. 新增构造参数 `onDownload?: (info: DownloadInfo) => void`，`DownloadInfo`
   `{ tabId, filename, url, saved }` 定义在 `protocol.ts` 或 `browser-preview.ts` 内导出。

**注意**：`sanitizeDownloadName` 必须实现（**防路径穿越**）：
去掉 `..`、路径分隔符、控制字符；空名退化为 `download-<时间戳>`。
这是第二道防线——`setSavePath` 的目录由我们自己给，但文件名来自页面，**必须清洗**。

### 步骤 2：自动化控制器提供策略 + 收集回执

文件：`src/main/browser-automation.ts`

1. 新增字段：

```ts
/** tabId → 该标签页的下载目录（自动化会话绑定时按其工作区解析）。 */
private readonly downloadDirs = new Map<string, string>();
/** 每个标签页待读的下载事件：下一次操作回执里附上并清空。 */
private readonly pendingDownloads = new Map<string, DownloadInfo[]>();
```

2. 工作区来源：**优先复用已有信息**——`browser_navigate` 的请求带 `workspace`
   （`protocol.ts:714`），navigate 分支里把 `request.workspace` 连同 tabId 记下来。
   若会话在工作区确定前就触发下载，则该次走「取消 + 报告」路径（安全兜底）。
3. 实现策略函数并传给预览控制器：

```ts
/** 自动化绑定的标签页：下载定向到工作区 .pidesktop/downloads/；其余一律取消。 */
const policy = (tabId: string) => {
  const dir = this.downloadDirs.get(tabId);
  return dir ? { dir: join(dir, ".pidesktop", "downloads") } : "cancel";
};
```

   目录创建用 `mkdir recursive`（在 `onDownload` 收到 `saved:true` 前先确保存在；
   或在策略函数里同步 `mkdirSync`——**建议在策略函数内 `mkdirSync(..., {recursive:true})`**，
   因为 `setSavePath` 要求目录已存在，这是 Electron 的既有约束）。
4. `onDownload` 回调把事件压入 `pendingDownloads`，并在回执里取用/清空
   （与 A1 的 `takeDialogNotes` **完全同构**，可共用一个「待读通知」机制——
   建议把 A1/A3 的队列统一为 `pendingNotices: Map<tabId, Notice[]>`，两处都在回执尾部渲染）。
5. 清理：`closeAutomationTab`（`browser-automation.ts:648`）里一并
   `downloadDirs.delete(tabId); pendingDownloads.delete(tabId);`。

### 步骤 3：回执文案

在操作回执尾部追加（与 A1 的弹窗提示同一位置）：

- **被取消**（`saved: false`）：
  `⚠ 该操作触发了下载（a.csv），但内置浏览器已取消下载（预览页不向磁盘写文件）。如需文件内容，请用 browser_eval 取数据后由 bash/写入工具保存到工作区。`
- **已保存**（`saved: true`）：
  `⬇ 已下载 a.csv 到 \`.pidesktop/downloads/a.csv\`（工作区内，可用 read/bash 读取）。`

**文案要求**：必须给出**改道指引**（第一句），否则模型只知道失败不知道怎么做。

### 步骤 4：保留与清理

`.pidesktop/downloads/` 的保留策略：**建议不做自动删除**（下载物是用户/模型的**交付产物**，
删掉可能破坏任务结果）。改为：
- 在 AGENTS.md 的存储布局描述里登记该目录；
- 若要控制增长，用「单目录上限 200 个、超限仅记日志不删」——**不要静默删用户文件**。

这与截图（`.pidesktop/screenshots/`，保留 20）的取舍**不同**，理由：截图是过程产物、下载是结果产物。

### 步骤 5：测试

1. **纯函数单测**：`sanitizeDownloadName`（≥6 例）——`../../etc/passwd`、`a/b.txt`、
   含控制字符、空名、超长名、Windows 保留名（`CON`/`NUL`）；
2. `browser-automation.test.ts`：`downloadDirs` 未设置时策略返回 `"cancel"`、
   设置后返回目录；回执队列 take 语义（取出即清空）；
3. **不做**真实下载的自动化测试（需要真 Electron + 网络），靠真机冒烟覆盖。

## 验证方式

0. **前置验证（必做）**：确认 `will-download` 回调的第三个参数 `webContents` 非空
   （临时 `console.log` 或 `app.on("web-contents-created")` 探针）。**若为空**，
   退化为「全局取消 + 报告文件名」（仍能获得本计划 80% 的价值，即消除静默失败）。
1. `npm test` 全绿（新增约 10 例）。
2. `npm run build` 全绿。
3. 真机冒烟：
   - 打开一个带下载链接的页面（可用本地静态服务造 `data:` 或 `<a download>`），
     `browser_click` 点它 → 回执出现「已取消下载」提示（**第一步验收点**）；
   - 在已 `browser_navigate` 过带 workspace 的场景重试 → 文件出现在
     `<workspace>/.pidesktop/downloads/`，回执给出工作区相对路径（**第二步验收点**）；
   - 用户手动在预览页点下载 → 仍被取消且**无** AI 回执（不污染 AI 视角）。
4. 安全：构造一个 `Content-Disposition: attachment; filename="../../../evil.txt"` 的响应 →
   文件**必须**落在 downloads 目录内（用 `realpath` 断言）。

## 风险与假设

| 风险 | 对策 |
|---|---|
| `will-download` 第三参数不可用 | 前置验证（见验证方式 0）；退化为全局取消 + 报告 |
| 文件名路径穿越 | `sanitizeDownloadName` + 目录由代码给定；测试必覆盖 `../` |
| 页面触发**大量**下载（恶意） | 每标签页每轮设上限（建议 20 个），超限仅报告不再 `setSavePath`；这与 `browser_upload` 的 20 文件上限口径一致 |
| 静默放行下载的安全姿态 | **只对「AI 会话已绑定且 navigate 过 workspace」的标签页放行**；用户自己浏览的预览页仍全取消，保持原设计 |
| 与 A1 改同一段回执逻辑 | 建议 A1/A3 **统一「待读通知」队列**（`pendingNotices`），一次改造两处受益；若分开做，A3 后做时顺手合并 |
| 大文件占用磁盘 | 不自动删（结果产物）；可在回执里带上大小，让模型/用户自行判断 |
