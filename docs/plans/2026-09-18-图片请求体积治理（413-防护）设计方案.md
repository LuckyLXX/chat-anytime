# 图片请求体积治理（413/`payload_too_large` 防护）设计方案

> 日期：2026-09-18 · 状态：**待用户批准** · 规模：M（新增 1 个纯函数模块 + 1 个主进程接线点 + 测试）
> 来源：用户反馈「较多图片处理的任务偶发 413 报错」，真机会话库复现并量化（见第 1 节）。
> 前置讨论：用户已确认「先出详细设计文档再定」；参数取「图片总量预算 6MB + 单图 ≤1.5MB」；**不做** 413 后自动裁剪重试的自愈机制（先预防）。

---

## 1. 背景与真机证据

### 1.1 报错形态

上游中转网关返回：

```
413: {"message":"请求体超过 8 MB 上限：请压缩内容（精简上下文或附件），或在管理端「设置 → 上游配置 → 请求上限」调大 server.max_body_mb 后重试","type":"invalid_request_error","code":"payload_too_large"}
```

这是网关的**请求体字节上限**（8MB），与 token 无关。当前会话模型若支持图片输入，历史中的**所有图片 base64 随每次请求全量上送**，随轮次线性膨胀直到撞线。

### 1.2 真机会话库统计（`<agentDir>/chatanytime-sessions/**/*.jsonl`，实测）

全库 501 张图片、100 个会话含图；其中 **3 个会话共 9 次** `payload_too_large` 失败（其余出现为模型复述报错文本，非真实失败）：

| 会话 | 失败次数 | 失败时前缀内图片 | 关键事实 |
|---|---|---|---|
| 有解App 原型图（09-15） | 4 | 首次 59 张 / 6.5MB，随后 82/13MB、98/19.8MB、123/24MB | 全场 148 张图，**全部来自 AI `read` 自己生成的截图**；每失败一次用户手动 `/compact`，压完继续读图继续爆 |
| 贴纸生成 ①（09-17） | 3 | 首次 18 张 / 7.9MB；/compact 后 9 张 / 9.9MB、8 张 / 7.9MB **仍被拒** | 18 张中 2 张单图 1.9MB |
| 贴纸生成 ②（09-17） | 2 | 首次 **5 张 / 7.9MB**；/compact 后 7 张 / 8.7MB 仍被拒 | 1 张用户附件 3.3MB + 4 张 AI 读图 1.0~1.3MB |

三个结论文本外的事实（写进设计依据）：

1. **图片主要来源不是用户附图，而是 AI 在同一轮里反复 `read` 自己生成的图**。会话 A 用户消息仅 4 条（带图 1 条），图片总数 20 张；会话 C 用户消息 20 条（**0 条带图**），图片总数 148 张。
2. **单图上限形同虚设**：Pi 内建图片压缩只保证「单张 ≤4.5MB / ≤2000px」（`utils/image-resize-core.js` 的 `DEFAULT_MAX_BYTES = 4.5MB`），没有总量概念——实测 **5 张图（7.9MB）就已被拒**。
3. **自动压缩救不了**：Pi 的上下文估算对每张图只按固定 4800 字符折算（`pi-agent-core` `ESTIMATED_IMAGE_CHARS`），18 张图 ≈ 2.2 万 token，远低于任何压缩阈值；手动 `/compact` 后「保留最近」窗口里仍留有 8~9 张图（8~10MB），**压缩完立即再爆**。

### 1.3 现状代码路径

- 图片进入历史：用户附件（`preparePromptPayload`，`pi-runtime.ts:3133`）、`read` 读图（Pi 内建，压缩到 ≤4.5MB 后作为 image part 进历史）、`browser_screenshot` / `browser_screenshot_full` / `computer_screenshot`（工具直接在 `content` 里返回 image part，`runtime-browser.ts:519/544`、`runtime-computer.ts:470`）。
- 图片离开请求（仅文本模型）：`wrapModelRuntimeForVision`（`pi-runtime.ts:1585`）包装共享 `ModelRuntime` 的 `streamSimple`，对无图片输入的模型调用 `runtimeVision.stripContextImages(context)` 全量剥离并留一句占位文本。
- **支持图片输入的模型当前不做任何体积处理**——这就是 413 的入口。

## 2. 目标与非目标

**目标**

1. 支持图片输入的会话，在上游请求前做**字节预算裁剪**：图片总量超过预算时，从最旧图片开始降级为**稳定占位符文本**，使请求体不再随轮次滚雪球。
2. 单张图片先降采样（≤1.5MB / ≤1600px）再参与预算，解决「单图 3.3MB」「5 张就爆」这类单点问题。
3. 降级占位符**字节稳定**（同一张图每次渲染同一串文本），使前缀缓存绝大部分可复用（见第 6 节）。
4. 占位符**可恢复**：携带工作区相对路径（能解析到时），模型可自行 `read` / `recognize_images` 回看；不能解析时至少携带像素尺寸与短哈希。
5. 只改「发往上游的副本」，**不动**会话转录、JSONL、界面渲染：用户仍然看到完整图片气泡，回滚/重放/导出不受影响。

**非目标**

- 不做「413 后自动裁剪上下文并重试」的自愈机制（用户已定：先预防；且该行为依赖上游错误文案匹配，误判代价高）。
- 不改 Pi 内建 `read` / 内建图片压缩的既有行为（4.5MB / 2000px 保持不动，我们的 1.5MB 预算在其之上叠加）。
- 不做「按相似度去重」「图片内容摘要化」等激进方案。
- 不调整用户附件入口的 20MB / 5 个限制（属另一话题；且预算裁剪已能兜住）。

## 3. 方案总览

在**唯一的 LLM 请求咽喉**（`wrapModelRuntimeForVision` 包装的 `streamSimple`）叠加三层处理，按顺序执行：

```
streamSimple(model, context)
  │
  ├─ ① 模型不支持图片输入 → 走既有 stripContextImages（不变）
  │
  └─ ② 模型支持图片输入 → 预算裁剪（本次新增）
        ├─ 2a 单图降采样：>1.5MB 的 image part 用 resizeImage 压到 ≤1.5MB / ≤1600px（结果确定、可缓存）
        ├─ 2b 总量预算：从最新图片往旧累加，超 6MB 的图片整块替换为占位符文本
        └─ 失败一律降级为「原样发送」（fail-open），绝不因裁剪让请求失败
```

**为什么放在 `streamSimple` 而不是别处**（关键决策，实施者务必理解）：

| 候选位置 | 结论 | 原因 |
|---|---|---|
| `streamSimple` 包装（选定） | ✅ | 唯一咽喉，主会话与子代理共用；`context.messages` 是**引用**，逐条替换 image part 不触发整包复制 |
| 扩展 `context` 事件 | ❌ | Pi 的 `emitContext` 开头就 `structuredClone(messages)`（`extensions/runner.js:793`）——对 12MB 的请求体做整树深拷贝，内存与延迟都不可接受；且部分调用路径（压缩摘要、视觉识别）不经过它 |
| `convertToLlm` / `transformContext` | ❌ | 在 agent-core 内层，改造成本高且要动 Pi 内部调用链；`transformContext` 还会对**所有**请求生效，包括不需要的摘要请求 |
| 图片落盘时预处理 | ❌ | 治不了「历史累积」这个主因（历史里的旧图仍在）；且要动多个工具实现 |

## 4. 详细设计

### 4.1 新模块 `src/main/request-image-budget.ts`（纯函数 + 注依赖）

纯函数化，photon/文件系统全部依赖注入，单测不需要真实图片处理。

```ts
import type { Context, ImageContent } from "@earendil-works/pi-ai";

/** 预算默认值（可被 settings 覆盖，见 4.4）。 */
export const IMAGE_TOTAL_BUDGET_BYTES = 6 * 1024 * 1024;   // 请求内图片 base64 总量上限
export const IMAGE_PER_IMAGE_BYTES = 1.5 * 1024 * 1024;    // 单张压缩目标
export const IMAGE_MAX_DIMENSION = 1600;                    // 单张压缩目标（长边像素）
export const IMAGE_DOWNSAMPLE_MIN_BYTES = 1.5 * 1024 * 1024; // 低于此值不触发压缩（省 CPU）

/** base64 字符串的近似字节数（3/4 还原）。 */
export function base64Bytes(data: string): number;

/** image part → 占位符文本（见 4.3 格式）。 */
export function placeholderText(image: ImageContent, info: PlaceholderInfo): string;

export interface BudgetDeps {
  /** 压缩单张（缺省实现：Pi 导出的 resizeImage；测试注入假件）。返回 undefined 表示压实失败。 */
  downsample: (image: ImageContent) => Promise<{ data: string; mimeType: string } | undefined>;
  /** 从消息里解析「这张图对应的可回看路径」（details.savedPath / 配对 toolCall 的 args.path），解析不到返回 undefined。 */
  pathForImage: (messageIndex: number, toolCallId: string | undefined, image: ImageContent) => string | undefined;
  warn: (message: string) => void;
}

export interface BudgetResult {
  context: Context;
  stats: {
    totalBytesBefore: number;
    totalBytesAfter: number;
    imagesTotal: number;
    imagesDownsampled: number;
    imagesPlaceholdered: number;
  };
}

/** 核心入口：对 Context 做预算裁剪；无图片或未超预算时原样返回（引用相等）。 */
export async function applyImageBudget(context: Context, deps: BudgetDeps): Promise<BudgetResult>;
```

**核心算法（`applyImageBudget`）**

1. 收集所有图片引用：遍历 `context.messages`，记录 `(messageIndex, partIndex, toolCallId, image)`；`message.content` 非数组或不是 user/toolResult 的跳过（assistant 消息按 Pi 约定无 image part，防御性跳过）。
2. 总量 `totalBytesBefore` = Σ `base64Bytes(image.data)`（**用 base64 长度而非解码后长度**，因为请求体的膨胀源就是 base64 文本）。
3. 若 `totalBytesBefore <= IMAGE_TOTAL_BUDGET_BYTES` → 直接返回原 context（**零开销热路径**：不超预算的绝大多数请求不做任何复制）。
4. 否则：
   a. **从新到旧**（消息数组倒序）遍历图片；对每张先判断 `base64Bytes(data) > IMAGE_DOWNSAMPLE_MIN_BYTES` → 调 `downsample`（带 4.4 的缓存）；压实失败则保持原样、不计降级。
   b. 用「压缩后」的字节数从新到旧累加进预算；一旦累计超预算，**当前及更旧的图片**全部标记为占位符（替换为 text part）。
   c. 只对**发生变化的** message 生成新对象（`{...message, content: [...]}`），未变化的 message 保持引用——保证「不超预算的热路径」与「未受影响的旧消息」零拷贝。
5. 返回新 Context（`{...context, messages}`）与统计。

**边界规则**

- **整块替换语义**：一张图的 image part 要么保留（可能是压缩后的），要么被替换为一个 text part（占位符），不产生半个图片。
- **不裁剪 `assistant` 消息**：Pi 的 assistant 消息不携带 image part；万一遇到（第三方扩展），按 user/toolResult 同规则处理即可，不特判。
- **文本部分不裁剪**：工具输出文本已由 Pi 的截断机制控制（单个工具结果 ≤50KB 量级），不属本方案范围。
- **顺序即优先级**：「从新到旧」同时承担两件事——最新的图片（最可能是当前操作对象）优先保留；超预算时最先牺牲最旧的图片。用户附件与工具结果图片**同权**（见第 9 节开放问题 1）。

### 4.2 单图降采样实现（`downsample` 缺省实现）

直接复用 Pi 已导出的 `resizeImage`（`export { resizeImage } from "./utils/image-resize.ts"`，`@earendil-works/pi-coding-agent` 包根导出，已实测可用）：

```ts
import { resizeImage } from "@earendil-works/pi-coding-agent";

const result = await resizeImage(Buffer.from(image.data, "base64"), image.mimeType, {
  maxWidth: IMAGE_MAX_DIMENSION,
  maxHeight: IMAGE_MAX_DIMENSION,
  maxBytes: IMAGE_PER_IMAGE_BYTES
});
```

实测结论（本机探针，`outputs/probe/probe-*.mjs`，实施时建议复跑）：

- 2.28MB PNG → 850ms 产出 386KB（1586×992 → 1500×938），**两次调用输出字节完全一致**（sha256 相同）→ 压缩结果确定性成立，可缓存、可进入稳定前缀。
- 3.9KB 小图 → 77ms，`wasResized: false` 且输出与输入相同（未超限走短路，开销可接受）。
- 内部走 worker 线程（`image-resize.js`），不阻塞主线程；失败（photon 不可用、编码失败）返回 `null`，按「fail-open 保留原图」处理。

**缓存（必须做，否则每轮重复压缩）**：按 `sha256(原图 base64)` 做内存 LRU（容量建议 64 项或 32MB，取先到者），命中直接返回压缩结果。同一张图在会话生命周期内只压缩一次；`resizeImage` 的确定性保证缓存命中结果与重算结果字节相同。

### 4.3 占位符格式与路径解析

**格式**（单行，`\n` 分隔可多行；保持中英混排下可读）：

```
〔图片已省略（历史图片，共 N 张被省略）· 1586×992 · .pidesktop/downloads/1789653507_xxx.png · 如需查看请 read 该文件或调用 recognize_images〕
```

字段与来源：

| 字段 | 来源 | 说明 |
|---|---|---|
| 「共 N 张被省略」 | 本预算统计 | 让模型知道被省略的规模；N 每次请求同值（预算内不变） |
| 像素尺寸 | 压缩前解析（PNG IHDR / JPEG SOF；解析失败省略） | 让模型判断细节量级；解析器约 30 行纯函数，放本模块 |
| 路径 | ① `toolResult.details.savedPath`（截图三工具带，实测存在）→ ② 配对 `toolCall.arguments.path`（`read` 工具；扫描同 Context 中 `assistant` 消息的 toolCall，按 `toolCallId` 匹配）→ ③ 无 | 工作区相对路径时直接可读；绝对路径（如 `read` 读的 `D:\...`）也给出——`read` 工具支持绝对/相对路径，注意别把「工作区外」误说成「工作区内」 |
| 短哈希（解析不到路径时用） | `sha256(data)` 前 8 位 | 稳定标识，供模型在多张被省略图之间指代（如「重新看 fdd6ab05 那张」）；也留给未来的「按哈希取图」扩展 |

**为什么占位符必须字节稳定**：同一张图，在不同请求（不同轮次）里渲染出的文本必须逐字节一致，否则前缀缓存每轮都整段失效。因此：

- 不写「第几次请求」「当前时间」等易变信息。
- 「共 N 张被省略」虽随预算变化（新增图片可能挤掉旧图），但它只在**发生了新的省略**时才变化（被省略的图一旦省略就保持省略，N 单调不减），变化频率 = 每张新图从「保留」转「省略」的瞬间，最多每图一次。
- 短哈希与尺寸都由图片内容决定，天然稳定。

### 4.4 传输层接线（`pi-runtime.ts`）

当前实现（`pi-runtime.ts:1585`）：

```ts
function wrapModelRuntimeForVision(runtime: ModelRuntime): ModelRuntime {
  return new Proxy(runtime, {
    get(target, property) {
      if (property === "streamSimple") {
        return (model, context, options) => {
          const effectiveModel = applyModelOverrides(model);
          return target.streamSimple(effectiveModel, hasImageInput(effectiveModel) ? context : runtimeVision.stripContextImages(context), options);
        };
      }
      if (property === "completeSimple") { /* 视觉识别：绝不能裁剪，保持不变 */ }
      ...
    }
  });
}
```

**改造为异步预算裁剪**，同时保持「同步返回流」的契约（Pi 的调用方同步消费 `AssistantMessageEventStream`）：

```ts
if (property === "streamSimple") {
  return (model: Model<Api>, context: Context, options?: ModelsSimpleStreamOptions) => {
    const effectiveModel = applyModelOverrides(model);
    // 文本模型：既有剥离逻辑保持同步返回（剥离是纯内存操作）。
    if (!hasImageInput(effectiveModel)) return target.streamSimple(effectiveModel, runtimeVision.stripContextImages(context), options);
    // 多模态模型：先同步返回一个流，预算裁剪在异步 setup 里完成后转发（与 Pi 自身 ModelRuntime.streamSimple 的 lazyStream 同款语义）。
    return lazyStream(effectiveModel, async () => target.streamSimple(effectiveModel, await cappedContext(context), options));
  };
}
```

要点：

1. `lazyStream` 从 `@earendil-works/pi-ai` 包根导出（`export * from "./api/lazy.ts"`），与 Pi 内部 `ModelRuntime.streamSimple` 用的是同一函数——语义完全一致，`setup()` 抛错会以 error event 结束流，不会静默丢请求。
2. `cappedContext(context)` = `applyImageBudget` 的包装：**内部 catch 一切异常 → `deps.warn(...)` → 返回原 context**（fail-open）。413 已经够糟，不能因为裁剪器自身故障让请求再挂一次。
3. `completeSimple` 分支**保持原样**：视觉识别工具调它时只带一张目标图，如果也被预算裁剪，识别工具会拿不到图。
4. 记一条 `warn` 级日志（节流：同一会话同一图片集合只记一次，避免日志刷屏），形如：
   `图片预算裁剪：20 张 → 压缩 2 张、省略 6 张，请求体图片体积 12.3MB → 5.8MB`。
   这是**唯一的可见性来源**（无 UI 改动），出问题时可从日志回溯。

### 4.5 是否进设置页？（本次不做）

预算常量（6MB / 1.5MB / 1600px）先做成模块常量，不进设置页。理由：

- 用户已定参数，先跑一轮收集真实效果再决定是否暴露；
- 加设置项要走「protocol + settings 迁移 + 设置页 + 双写镜像」的全链路（`vision`/`computer` 的同款纪律），成本远大于收益；
- 若后续要暴露，`IMAGE_*` 常量已集中定义在 `request-image-budget.ts` 顶部，扩展为 `settings.imageBudget` 是机械工作。

## 5. 参数与常量

| 常量 | 值 | 说明 |
|---|---|---|
| `IMAGE_TOTAL_BUDGET_BYTES` | 6MB | 图片 base64 总量预算；网关上限 8MB，留 2MB 给文本 + JSON 结构（实测文本部分 0.2~1.5MB，最坏情况会顶到边缘，出问题优先下调此值到 5MB） |
| `IMAGE_PER_IMAGE_BYTES` | 1.5MB | 单图目标；实测 1500px 宽的界面截图压到 300~400KB，1.5MB 足以覆盖细节图 |
| `IMAGE_MAX_DIMENSION` | 1600px | 长边上限；比 Pi 内建的 2000px 更保守，因为多图场景要的是「看得见」而不是「看得清」 |
| `IMAGE_DOWNSAMPLE_MIN_BYTES` | 1.5MB | 低于此值不触发压缩（避免无意义 CPU） |

## 6. 缓存影响（必须如实告知）

上游的 prompt 前缀缓存按**字节前缀**命中。本方案的影响：

- **保留的图片**：压缩结果确定性 → 同一张图每轮字节一致 → 不影响缓存。
- **降级为占位符的图片**：替换发生在「该图从保留转为省略」的那一次请求，此后占位符字节稳定 → **每张图最多破坏一次缓存**，位置在该图所在消息处，其后的前缀失效一次。
- **总量不超预算时**：零改动，零影响（`applyImageBudget` 原样返回）。
- 与用户提供方案的差异：原方案按「轮次」保留（当前轮全保留），在本项目实际用法（AI 一轮读几十张图）下，当前轮图片本身就会超限；本方案按「字节预算」保留，**超预算时当前轮的旧图同样降级**——这正是它能在 8MB 硬限内活下来的原因。

## 7. 测试计划（`npm test`）

新增 `src/main/request-image-budget.test.ts`，纯函数级（注入假 `downsample`，不跑 photon）：

1. **热路径**：无图片 / 未超预算 → 返回同一 context 引用（`toBe`），`downsample` 零调用。
2. **单图超限**：1 张 3MB 图 → 调 `downsample`；压缩结果进入结果；`imagesDownsampled: 1`。
3. **总量超预算**：8 张 1MB 图（8MB）→ 保留最新 N 张至 ≤6MB，其余替换为占位符；顺序断言「新保留、旧省略」。
4. **占位符稳定**：同一输入两次调用，占位符字符串逐字节相同；不同图片占位符不同（含短哈希）。
5. **路径解析优先序**：`details.savedPath` > `toolCall.arguments.path` > 无路径（短哈希兜底）。
6. **fail-open**：`downsample` 抛错 → 该图按原样保留，不抛异常，其余图片照常处理；整体仅记 warn。
7. **completeSimple 不受影响**：接线层测试（仿 `runtime-shell-kill.test.ts` 的 `vi.mock` 模式）确认 `completeSimple` 的 context 未被裁剪。
8. **非图片消息零拷贝**：超预算时，未含图片的 message 与未受影响的图片 message 保持原引用（`toBe`）。
9. **像素解析**：PNG / JPEG 头部解析的 3~4 例（含解析失败兜底）。

另有接线层测试建议放在 `pi-runtime` 之外的独立测试文件，用假 `ModelRuntime` + 假 photon，断言「同步返回流、异步裁剪后转发、失败 fail-open」。

## 9. 风险与开放问题

**风险**

1. **模型看不到历史图片细节** → 缓解：占位符携带路径 + `recognize_images` 提示；这是「能跑通」对「看得全」的合理取舍（现状是直接失败）。
2. **文本部分膨胀**：极端纯文本会话（1.5MB 工具输出文本 + 6MB 图片）可能顶到 8MB 边缘 → 缓解：预算为常量，必要时下调；后续可对文本部分做同类预算（不在本次范围）。
3. **压缩耗时**：每张 >1.5MB 的图首次压缩 ~0.8s，多张并行会叠加 → 缓解：LRU 缓存 + 只在超限会话触发（实测会话中 >1.5MB 的图占比低：18 张里 2 张、59 张里 0 张）。
4. **占位符变体差异**：不同 provider 的 toolResult 结构一致（实测），但若未来有 provider 把 image 转 base64 塞进文本，本方案不覆盖 → 不影响正确性，仅影响效果。

**开放问题（实施前可再确认，当前建议已给出）**

1. **用户附件是否应比工具结果图有更高保留优先级？** 当前同一套「新→旧」规则。更精细的策略（用户图优先保留）复杂度上升，建议先观察一轮。
2. **预算常量是否需要按 provider 区分？** 8MB 是本机网关的值；其他网关可能更小（如 4MB）。当前单一常量，后续若遇到更小上限的网关再考虑。
3. **是否把「优化 413 错误提示」列入后续？** 现在用户看到的还是网关原文（含「调大 server.max_body_mb」指导），对用户其实算清晰的；暂不改。
