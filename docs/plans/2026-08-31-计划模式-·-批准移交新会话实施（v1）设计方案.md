# 计划模式 · 批准移交新会话实施（v1）设计方案

> 状态：设计方案（待实施）。行号以 2026-08-31 main 工作区为准，实施时以函数名定位为准。

## 一、背景与目标

现状：`exit_plan_mode` 的批准出口只有一个——本会话退出计划模式，由**同一个模型**继续实施（`src/main/runtime-plan-tools.ts`）。缺口场景：用户用强模型（贵、慢、聪明）完成规划，想让弱模型（便宜、快）执行实施。

有利条件（基础设施全部就绪，本需求基本是"新出口 + 编排接线"）：

- 计划文档在批准时已由应用侧落盘 `<workspace>/docs/plans/YYYY-MM-DD-<title>.md`（`plan-store.ts saveApprovedPlan`），天然是一份可移交的正式产物（one home per fact）；
- 多会话运行时支持并发会话、parking 忙会话、会话级模型；
- 自动化模块已为 `createSession` 增加 `modelOverride` 参数（`pi-runtime.ts` `runAutomationTask` 先例），程序化"建会话 + 套模型 + 发 prompt"的模式已经存在。

**目标**：计划审查面板新增第二个批准出口「批准计划，移交新会话实施」——批准时选定实施模型，由 utility 进程在同一 Agent、同一工作区下新建前台会话，以所选模型按计划文档开始实施；原规划会话简短收尾。

**配套目标（用户强调，本设计的硬性要求）**：计划必须**自包含**。计划模式指引与工具描述明确要求：计划文档必须假设"由一个没有任何本会话上下文的新会话、仅凭这份文档实施"——背景、现状勘察结论、已定决策与理由、步骤、验证方式全部写进文档本身，禁止以"如前所述"指代会话内讨论。

**非目标（v2 再议）**：

- 跨 Agent / 跨工作区移交（v1 拒绝并给出诚实错误，见 §七-4）；
- 移交后自动归档 / 置顶规划会话；
- 用 `delegate_agent` 子智能体作为移交目标——子会话不可见、无浏览器工具与钩子扩展、父会话（强模型）仍要持续编排并付费，与"长时间、可见、可中断的实施工作"形态不符。

## 二、关键决策（可调整）

| 维度 | 决策（v1 默认） | 备注 |
|---|---|---|
| 出口形态 | 审查单选增加第三项「批准计划，移交新会话实施」，点选后**两段式**：先在面板内选实施模型，确认后才提交 | 选项顺序：本会话实施（保留第一位与（推荐）标注）/ 移交新会话 / 不批准 |
| 模型选择时机 | 必须在批准时刻、面板内选定，随 `question.resolve` 一起回传 | **本需求最关键的坑**：新会话的默认模型链会解析 Pi 持久化默认（`~/.pi/agent/settings.json`，每次切模型都被重写，等效"上次使用模型"= 规划用的强模型，`pi-runtime.ts` `piPersistedDefaultModel` 分支）。不显式指定就静默用强模型，"弱模型实施"意图失败 |
| 编排位置 | 全部在 utility 进程内完成：`exit_plan_mode` 的 execute 经注入的 `handoff` 依赖调用 `pi-runtime.ts` 的编排函数 | 复用 `runAutomationTask` 模式（快照守卫 → `SessionManager.create` → `createSession(modelOverride)` → prompt）；**不新增上行消息、不经 main**（会话运行时本来就住在 utility 进程） |
| 新会话形态 | 同 Agent、同规划会话工作区；**前台激活**（不 `skipActivate`）；有人值守（不用 `unattended`/`noGenerationGuard`，权限门与 `ask_question` 照常）；计划模式关；todo / checkpoint / 记忆快照各自全新初始化 | 与自动化后台会话形成对照：那是 skipActivate + unattended |
| 首条消息 | 引用落盘路径为主（"先完整阅读 docs/plans/xxx.md 再实施"）；留档失败时内联计划全文兜底 | 文件是计划唯一正式副本；实施模型自己读文档，也符合"实施前先通读"的质量要求 |
| 会话命名 | 以计划首个 `# ` 标题作为新会话标题（现有 `session.rename` 同语义 `appendSessionInfo`），失败只记日志不阻塞 | `planFileName` 已有同款标题提取，抽 `planHeading` 共用（§五-5） |
| 原会话收尾 | 移交批准同样关闭计划模式 + 留档；工具返回「已移交，请简短总结收尾，不要开始实施」 | 强模型低成本结束回合；会话 parked 后台收尾（侧栏黄点，现有语义） |
| 批准判定纪律 | `parsePlanReview` 对移交选项**精确匹配**出第三种 status；自定义输入仍一律视为拒绝反馈 | 维持"恰好选中才批准"的既有纪律；移交提交的答案恒为选项原文（自定义输入与移交互斥，§四） |

## 三、协议变更（`src/shared/protocol.ts`）

```ts
/** ask_question 的单个问题；type=single/multiple 时附带选项，渲染端另提供自定义输入。 */
export interface QuestionItem {
  text: string;
  type: "text" | "single" | "multiple";
  options: string[];
  /** 可选 markdown 详情（如计划审查展示计划全文），渲染在题目文本与选项之间；缺省不渲染。 */
  detail?: string;
  /**
   * 移交出口（计划审查专用）：值为 options 中某一选项的原文。渲染端点选该选项时
   * 不立即提交，而是先展开实施模型选择，确认后连同 question.resolve.model 一起提交。
   * ask_question 永不设置该字段。
   */
  handoffOption?: string;
}
```

`RuntimeCommand` 的 `question.resolve` 增加可选字段：

```ts
| { type: "question.resolve"; id: string; answers?: string[]; /** 移交出口选定的实施模型（handoffOption 流程携带；ask_question 忽略）。 */ model?: { provider: string; id: string } }
```

说明：

- `handoffOption` 放在 `QuestionItem` 而不是新增题型——渲染端只需在点选时识别这一个出口，其余渲染路径（分页、序列化、键盘导航）全部不变。
- 模型下拉数据**不新增推送**：渲染端 store 已有 catalog 的 `ModelOption[]`（`models` + `providers`），面板直接消费，口径与 composer 模型菜单一致（`enabled !== false`，按供应商分组显示）。
- `question.resolve` 从渲染端经 main 到 utility 是逐字转发（`pi-runtime.ts` `handleCommand` 的 `case "question.resolve"` 直接调 broker），新增可选字段不需要改 main 进程。

## 四、交互设计（`src/renderer/src/components/QuestionPanel.tsx`）

### 选项与两段式流程

审查问题选项变为三项（`planReviewQuestion` 产出）：

1. 批准计划，开始实施（第一位，自动带（推荐）标注，点选即提交——现状不变）
2. **批准计划，移交新会话实施**（`item.handoffOption === 该选项` 时走两段式）
3. 不批准，继续完善计划（现状不变）

两段式状态机（面板内新增局部 state，不改 store）：

```
点选移交选项
  └─ 不 resolve；清空该题自定义输入，展开「实施模型」选择行：
       ┌────────────────────────────────────────────┐
       │ 实施模型   [ ▾ 按供应商分组的模型下拉 ]      │
       │ （新会话将以所选模型严格按计划文档实施）       │
       │            [返回]  [移交实施]               │
       └────────────────────────────────────────────┘
  ├─ 「移交实施」（模型已选才可用）→ resolve([PLAN_HANDOFF_OPTION], model)
  └─ 「返回」/ Esc → 收起选择行，回到选项列表（问题仍挂起）
```

- **预选模型**：当前 Agent 的默认模型（`AgentProfile.defaultModel`），无则回落全局默认 `settings.model`；下拉列表与 composer 模型菜单同口径（`enabled !== false`，供应商分组，复用 `composer-menu-group` 的分组渲染方式）。
- **自定义输入与移交互斥**：打开模型选择即清空自定义输入；移交提交的答案**恒为选项原文**，保证 `parsePlanReview` 精确匹配（若沿用 `singleSelectionAnswer` 的"自定义优先"逻辑，用户残留的输入文本会被误判为拒绝反馈——这是必须防住的坑，见记忆库 ask_question 取消误判教训同源风险）。
- 键盘：选择行展开时聚焦下拉；Enter 确认移交、Esc 返回；选项列表的 ↑↓/回车/空格导航对移交选项同样进入两段式（`toggleOption` 内分支）。
- 题干文案更新（`planReviewQuestion`）：说明移交会先选模型——"（点选项即提交；「移交新会话实施」会先让你选择实施模型；如需修改，请在输入框中写下意见。）"

### 样式与主题

- 新增 `question-handoff-row` / `question-handoff-select` / `question-handoff-actions` 等类，全部位于 `data-pane="question-panel"` 区域内，**不新增主题结构钩子**（主题对该区域已有整体样式权）。
- 分屏下 QuestionPanel 本就是每格独立渲染（`ConversationPane.tsx`），移交后 `activeRuntime` 切到新会话、焦点格跟随切换，原格继续显示规划会话的收尾流——均为现有行为。

## 五、工具层改动（`src/main/runtime-plan-tools.ts`）

### 1. 常量与问题构造

```ts
export const PLAN_HANDOFF_OPTION = "批准计划，移交新会话实施";

export function planReviewQuestion(plan: string): QuestionItem {
  return {
    text: "请审查这份计划：批准后我将退出计划模式并严格按计划开始实施。（点选项即提交；「移交新会话实施」会先让你选择实施模型；如需修改，请在输入框中写下意见。）",
    type: "single",
    options: [PLAN_APPROVE_OPTION, PLAN_HANDOFF_OPTION, PLAN_REVISE_OPTION],
    detail: plan,
    handoffOption: PLAN_HANDOFF_OPTION
  };
}
```

### 2. 审查结果解析（`parsePlanReview`）

签名增加可选 model（来自 `QuestionOutcome.model`，形状已在 broker 侧校验）：

```ts
export type PlanReviewOutcome =
  | { status: "approved" }
  | { status: "approved-handoff"; model: { provider: string; id: string } }
  | { status: "rejected"; feedback: string }
  | { status: "cancelled" };

export function parsePlanReview(answers: string[] | undefined, model?: { provider: string; id: string }): PlanReviewOutcome
```

- `answers[0]` 精确等于 `PLAN_HANDOFF_OPTION` 且 model 形状完整（provider/id 均非空字符串）→ `approved-handoff`；
- model 缺失/不完整 → 同样返回 `approved-handoff` 但不带 model，由 execute 按"模型无效"降级处理（正常 UI 下不会发生：确认按钮在选中模型前禁用）；
- 其余分支语义不变（精确匹配 `PLAN_APPROVE_OPTION` 批准；其他任何作答含自定义文本均为拒绝反馈）。

### 3. 新增 handoff 依赖（`PlanToolDeps`）

```ts
export interface PlanToolDeps {
  // …现有五项不变…
  /**
   * 批准并移交：在规划会话所属 Agent + 工作区下新建前台会话，以所选模型
   * 按计划文档开始实施（utility 侧由 pi-runtime.ts 实现）。
   * planPath 为留档相对路径；留档失败时为 undefined（prompt 内联计划全文兜底）。
```

### 4. `exit_plan_mode` execute 的移交分支

在现有 approved 分支之后增加（顺序重要，见 §六）：

1. **先校验**：`approved-handoff` 但 model 缺失 → `errorResult("移交所需的实施模型无效（未选择或字段不完整）。本会话仍处于计划模式；请重新调用 exit_plan_mode 提交审查，用户将重新选择。")`——计划模式保持开启，未做任何状态变更；
2. `deps.setEnabled(false)`（与普通批准同语义：移交也是批准，规划阶段结束）；
3. `deps.savePlan(plan)`（先留档，再移交——实施会话读文件的前提）；
4. `await deps.handoff(...)`，成功返回：
   `计划已批准并移交新会话实施（模型：${model.id}；新会话：「${title}」，已开始按计划实施）。本会话无需实施：请用一两句话总结移交结果并结束。`
5. handoff 抛错（模型失效、Agent/工作区不一致、建会话失败等）→ `isError` 诚实降级：
   `计划已批准并留档（${savedPath}），但移交新会话失败：${原因}。本会话已退出计划模式，但请不要开始实施；请告知用户可手动新建会话实施（计划在 ${savedPath}），或重新提交计划再次尝试移交。`（留档也失败时文案相应去掉路径引用）。

### 5. 首条消息模板（纯函数，可单测）

```ts
/** 移交会话的首条用户消息：引用落盘文档为主，留档失败内联全文兜底。 */
export function buildPlanHandoffPrompt(input: { plan: string; planPath?: string; title: string }): string
```

产出文案（中文，约束实施纪律但不重写计划本身）：

```
【计划实施移交】「${title}」已在另一会话完成规划并经用户批准，由本会话负责实施。

${planPath
  ? `计划文档：${planPath}（请先完整阅读后再动手）`
  : `计划文档未能留档，全文如下（以此为准）：\n\n---\n${plan}\n---`}

实施要求：
1. 先通读计划与其中提到的关键文件，再开始动手；
2. 严格按计划步骤逐项实施，建议先建立任务清单跟踪进度；
3. 计划中已定的决策不要另行发挥；遇到计划未覆盖且影响结果的问题，先向用户提问再继续；
4. 全部完成后总结改动清单与验证结果。
```

### 6. 计划自包含指引强化（本需求的硬性要求）

- `PLAN_MODE_GUIDANCE_FULL` 第 2 条改写为：

  > 2. 产出计划：把实施方案写成一份完整的 Markdown 计划文档，至少包含：背景与目标、现状勘察结论（关键文件、模块与行为）、实施步骤（每步说明涉及的文件与改动）、验证方式、风险与假设。计划要决策完备且**自包含**——必须假设它会被交给一个没有任何本会话上下文的新会话、仅凭这份文档实施：所有结论、决策与理由都要写进文档，不要用「如前所述」「上面提到的」指代会话内讨论。用户将据此批准。

- `exit_plan_mode` 的 description 与 `plan` 参数描述同步补"必须自包含（实施可能由一个全新会话仅凭此文档完成）"。

## 六、编排层（`src/main/pi-runtime.ts`）

### 1. `buildPlanTools` 接线（现 :1930 处）

```ts
handoff: (input) => {
  // 规划会话自身的 record（闭包捕获 recordBox），不是 activeRuntime——
  // 用户可能在规划进行中把焦点切到了别的会话/格子。
  const source = recordBox;
  if (!source) throw new Error("规划会话运行记录不可用");
  return handoffPlanToNewSession({ source, ...input });
}
```

### 2. `handoffPlanToNewSession`（新函数，紧邻 `runAutomationTask` 的同款纪律）

```ts
async function handoffPlanToNewSession(input: {
  source: SessionRuntimeRecord;
  plan: string; planPath?: string; title: string;
  modelRef: { provider: string; id: string };
}): Promise<{ sessionId: string }>
```

步骤：

1. **快照守卫**（自动化同款）：`modelRuntime && currentAgent && workspace` 就绪；`source.agent.id === currentAgent.id` 且 `resolve(source.workspace) === resolve(workspace)`，不一致抛错（"规划会话与当前 Agent/工作区不一致，无法移交"）。分屏内的会话同属当前 Agent，正常路径必过；这是防 `createSession` 派生自全局 `workspace`/`currentAgent`（现 :1773-1774）与规划会话落位错位的唯一手段；
2. **模型校验**（自动化同款，`runAutomationTask` 现 :522 口径）：`modelRuntime.getModel(provider, id)` 存在且 `isModelEnabled(provider, id, settings?.providers)`，否则抛错（"所选模型不可用（已删除或未勾选）"）；
3. `const manager = SessionManager.create(source.workspace, workspaceSessionDir())`，`sessionId = manager.getSessionId()`；
4. `await createSession(manager, { modelOverride: modelRef })`——**默认激活**（与自动化相反）；不传 `unattended`/`noGenerationGuard`（有人值守：权限门、`ask_question`、代际竞争保护照常）。第 1 步守卫保证全局 agent/workspace 与规划会话一致，新会话与规划会话同 Agent、同工作区、同会话根目录；
5. 命名：`try { manager.appendSessionInfo(title); } catch { 记日志 }`（失败不阻塞——命名是锦上添花；对未持久化会话的 appendSessionInfo 行为需冒烟确认，见 §七-5）；
6. `await handleCommand({ type: "session.prompt", text: buildPlanHandoffPrompt({ plan, planPath, title }), sessionId })`——**复用完整命令语义**：模型就绪守卫、busy 守卫、todo 回合清空（新会话空表无副作用）、busy/runStatus/beginTurn/emitState、错误兜底（catch 分支的会话列表刷新）；
7. 返回 `{ sessionId }`。

### 3. 激活与收尾时序

```
渲染端（规划会话格子）              utility（规划会话 agent loop）        utility（运行时编排）
  │                                │                                    │
  │ ◀── question 推送（含 handoffOption）──│ broker.request 挂起          │
  │ 用户点「移交」→ 选模型 → 确认    │                                    │
  │ ── question.resolve{answers,model} ▶ │ broker.resolve 唤醒             │
  │ （面板从 store 移除，UI 关闭）    │ parsePlanReview → approved-handoff │
  │                                │ setEnabled(false) + savePlan       │
  │                                │ ─────── deps.handoff(...) ────────▶ │ 守卫/校验
  │                                │                                    │ createSession(modelOverride) 激活
  │ ◀══════ state 切到新会话（焦点跟随）═════════════════════════════════│ appendSessionInfo(标题)
  │                                │                                    │ session.prompt(移交指令)
  │ ◀── 工具结果「已移交，简短收尾」──│ ◀────────── { sessionId} ─────────│ （新会话开始实施）
  │ （规划会话 parked 后台收尾，侧栏黄点）│ 规划模型生成一两句总结            │
```

关键点：`createSession` 激活新会话时规划会话正在 agent loop 中等工具结果——park 不 dispose，record 原地保留；工具结果返回后规划模型继续生成收尾文本（后台）。侧栏状态、分屏格子、`session.state` 推送全部走现有通道，无新机制。

## 七、边界与风险

1. **新会话默认模型陷阱（已防）**：不显式 `modelOverride` 时新会话解析 Pi 持久化默认（= 规划强模型）。本设计在批准时刻强制选模型 + `createSession(modelOverride)` 双保险；模型无效在编排第 2 步抛错，绝不静默回落默认模型。
2. **自定义输入误判拒绝（已防）**：移交提交答案恒为选项原文，面板打开模型选择即清空自定义输入（§四）。
3. **提交时模型已失效**（面板渲染后服务商删除/取消勾选）：编排第 2 步校验拦截 → 工具 isError 降级文案，引导用户手动实施或重新提交计划。
4. **跨 Agent / 跨工作区规划会话**：v1 一律拒绝（守卫抛错）。实践中分屏会话同属当前 Agent，正常路径不触发；发生时计划已留档，手动移交的退路始终存在。
5. **未持久化会话的命名**：新会话 JSONL 在首条助手消息前不落盘（Pi `_persist` 门控），`appendSessionInfo` 对内存会话的行为需实施时确认；异常则推迟命名或放弃（失败不阻塞已在设计内）。侧栏标题是否即时生效列为冒烟项。
6. **规划会话后台收尾**：移交后规划会话仍会生成一段简短总结（工具结果约束"一两句话"），成本可忽略；侧栏黄点在用户查看后清除（现有 `runStatus` 语义）。
7. **计划自包含是质量前提**：指引已强化，但弱模型实施质量最终取决于文档自包含程度——首条 prompt 已强制"先通读计划与关键文件再动手"，实施中遇到未覆盖问题要求先 `ask_question`（有人值守会话具备该工具）。
8. **ask_question 不受影响**：`model` 是可选字段、`handoffOption` 只有计划审查设置；broker 对非法 model 形状一律按缺省处理（ask_question 流程无感知）。
9. **demo mock 同步**：`src/renderer/src/demo-api.ts` 的 `question.resolve` mock 需接受新字段（可选，不解析也不报错），并可选提供一条带 `handoffOption` 的计划审查样例供纯浏览器演示/手测。
10. **主题兼容**：新 UI 全部位于 `data-pane="question-panel"` 内，未新增/未改动任何主题结构钩子；自定义主题未覆盖新类时回落应用默认样式。

## 九、测试与验收

### 单元测试

- `parsePlanReview`：移交选项精确匹配；带/不带 model；其他文本仍拒绝。
- `exit_plan_mode` 移交分支：成功文案（含模型/标题/留档路径）、模型无效（计划模式保持开）、`handoff` 抛错降级（计划模式已关、不实施、留档路径在文案中）。
- `buildPlanHandoffPrompt`：planPath 有/无两版；标题注入。
- `QuestionBroker.resolve`：model 合法携带、非法形状忽略、answers 缺省仍 cancelled。
- `planHeading` 提取与 `planFileName` 回归。

### 手动冒烟（Windows 包或 dev）

1. **主链路**：强模型进入计划模式 → 产出计划 → `exit_plan_mode` → 审查面板出现三选项 → 点「移交新会话实施」→ 选弱模型 → 移交实施 → 焦点自动切到新会话（标题=计划标题、模型=所选弱模型）→ 新会话先读 `docs/plans/*.md` 再逐步实施 → 原会话后台生成一两句收尾（侧栏黄点，点开后清除）。
2. **两段式取消**：打开模型选择后「返回」/Esc → 回选项列表，问题仍挂起，再点普通批准 → 本会话实施（现状不变）。
3. **自定义输入互斥**：输入框写了文字后点移交选项 → 输入被清空，确认后答案仍为选项原文，正常移交（不误判拒绝）。
4. **降级路径**：选一个仅剩一个服务商可用的场景，提交前在设置里取消勾选该模型 → 移交失败文案出现、计划已留档、规划会话不实施。
5. **分屏**：规划会话在分屏格中批准移交 → 焦点格切到新会话，原格继续显示收尾流；侧栏两个会话状态点正确。
6. **自包含指引**：新开计划模式会话，注入的完整指引包含"自包含"要求；`exit_plan_mode` 工具描述同样包含。
7. 回归：普通 `ask_question`（多题、单选点选即提交、忽略）行为不变；主题（霓虹街区等）下审查面板无样式崩坏。
