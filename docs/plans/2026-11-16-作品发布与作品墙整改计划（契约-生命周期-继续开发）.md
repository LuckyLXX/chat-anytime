# 作品发布与作品墙整改计划（契约、生命周期、继续开发）

## 一、背景与目标

**需求来源**：对作品发布模块进行完整审查，重点检查内置 skill、`gallery_publish` 工具、作品墙运行链路、panel 跨域、后台服务生命周期，以及「继续开发」闭环。

**审查结论**：当前实现已经具备完整的发布、运行、继续开发主流程，`npm test` 与 `npm run build` 均通过；但存在若干会让模型“看起来完成、实际结果不对”的静默缺陷：

1. 工具 schema 接收的 `entry` 在真实发布实现中没有生效。
2. panel 本地服务的 `command` / `url` 是可选字段，但实际只有两者同时存在才会启动服务。
3. 已打开的 panel 再次运行不会 reload，继续开发后容易看到旧页面。
4. 启动器型命令退出码为 0 时，后台服务状态可能被错误标记为 stopped，进一步影响关窗回收和应用退出回收。
5. 服务启动、停止、重启、关窗和应用退出之间存在并发竞态。
6. 继续开发注入文本没有明确要求模型用同一作品身份重新发布，无法稳定闭合“修改 → 验证 → 更新作品墙”的循环。

**本次目标**：

- 让模型只依赖 skill、工具 schema 和工具回执，就能准确选择作品形态、处理 CORS、配置后台服务并完成发布。
- 让 panel 服务生命周期可解释、可观测、可回收：谁启动、谁拥有、何时停止必须明确。
- 让“继续开发”成为可重复的开发闭环，而不是仅仅把一段上下文塞进输入框。
- 保持既有作品清单、panel 固定 origin、旧版发布参数和现有用户操作兼容。
- 用行为测试覆盖关键时序，不只依赖源码字符串断言。

**本计划范围**：只处理作品发布、作品运行、panel 服务、作品墙和继续开发相关代码与文档；不扩展作品版本管理、自动扫描目录或远程发布能力。

## 二、已核实的现状与问题证据

### 2.1 现有正确设计

| 能力 | 当前实现 | 结论 |
|---|---|---|
| 三种作品形态 | `file`、`server`、`panel` | 形态划分合理，应继续保留 |
| panel 跨域 | `src/main/panel-cors.ts` 按 panel webContents 放宽响应 | 安全边界清楚，不改成全局 `webSecurity: false` |
| panel origin | `pidesktop-file://w-<作品 id>` | 固定 origin 能保留 localStorage / IndexedDB，应继续作为数据身份 |
| 后台服务 | `src/main/gallery-service-runner.ts` | 主进程托管、作品墙看板展示，方向正确 |
| 面板服务归属 | `ownerPanelId` + `stopByOwner()` | 适合表达“平台为该面板启动的服务” |
| 作品清单 | `<agentDir>/pidesktop-gallery` | 不进入 `settings.json`，避免 settings 镜像和迁移风险 |
| 跨工作区继续开发 | 目录预检 + `session.new` + composer 延迟注入 | 基本链路正确，需要补回执和失败反馈 |

### 2.2 需要修复的确定问题

#### P1：`entry` 参数被静默忽略

`src/main/runtime-gallery.ts` 的校验层会读取 `entry`，但 `src/main/pi-runtime.ts:3002` 只根据 `draft.path` 计算最终入口。工具 schema 又描述了 `entry` 可以指向目录内页面，导致模型可能正确传参，却发布错误入口或无法打开 panel。

**整改决策**：保留 `path + entry` 兼容形状，但统一定义如下：

- `file/panel`：
  - 没有 `entry` 时，`path` 就是最终入口文件；
  - 有 `entry` 时，`path` 是工作区内文件或目录，最终入口为 `resolve(path, entry)`；
  - 清单只保存最终相对工作区入口，不保存二义性的两段路径。
- `server`：`path` 必须是项目目录；`entry` 不适用，传入时拒绝并提示。
- 旧版只传 `path` 的作品行为不变。

#### P1：panel 本地服务的 command/url 条件不一致

`galleryRunPlan()` 只有在 `command && url && !serviceReachable` 时才返回 `start-panel-service`。因此：

- 只有 `command`：命令不会执行，面板直接打开；
- 只有 `url`：只会把它当探活地址，无法自动托管服务；
- UI 和工具 schema 允许不完整配置，用户不会立即知道配置没有生效。

**整改决策**：

- panel 本地服务采用“成对字段”规则：填写 command 必须填写 url，填写 url 必须填写 command。
- 两者都不填表示 panel 不依赖平台托管的本地服务。
- 服务地址只用于探活和面板自身请求，不自动作为 panel 页面地址打开。
- 地址已可达时，视为外部服务或已有服务，平台不启动、不停止；回执必须明确说明“外部服务未被平台接管”。

#### P1：已打开 panel 不 reload

`PanelWindowController.open()` 在发现已有窗口时只前置窗口和同步置顶状态，不重新加载入口页面。模型继续修改后，用户再次点击“运行”可能仍看到旧内存页面。

**整改决策**：将“运行”定义为“确保窗口打开并加载当前入口”。

- 已有窗口且本次操作来自作品墙“运行”：reload 后前置；
- 仅由 panel 页面内部请求 show/focus 时，不 reload；
- reload 不清除 localStorage / IndexedDB；
- 开发文档明确：页面内存状态可能因 reload 重置，持久数据应写入 localStorage / IndexedDB。

#### P1：启动器型命令造成服务状态失真

`waitForService()` 支持 shell 退出码为 0 后继续等待端口，但 `GalleryServiceRunner.settle()` 会先把记录标为 stopped。若之后端口变为可达，记录可能仍是 stopped，导致看板、关窗回收和应用退出回收都认为没有活服务。

**整改决策**：平台托管的服务命令必须是“前台、非交互、长期运行”的服务命令。`pythonw`、`start`、`cmd /c start` 等把真正服务脱离当前进程树的启动器不再作为可靠托管方式。

- 命令在服务就绪前退出：视为启动失败，回执说明“启动命令提前结束，不能建立可回收的服务所有权”；
- 命令在服务已就绪后退出：视为服务停止，保留退出码和日志；
- skill、工具 description、UI 提示统一要求命令本身保持前台运行；
- 保留 `waitForService()` 的通用退出判断，但不再把“退出后仍可能有脱离进程”作为成功路径。

#### P2：服务状态机存在并发竞态

需要处理的时序包括：

- 停止中的服务被下一次运行复用；
- 快速双击“运行”在探活和登记之间启动两个进程；
- `disposeAll()` 执行后，在途 `start()` 仍继续 spawn；
- 重启时旧进程只等待固定超时，可能尚未真正退出；
- panel 开窗 IPC 抛异常时，已启动的 owner 服务没有进入清理路径。

**整改决策**：以 `appId` 为粒度建立服务操作串行化；所有 start/stop/restart/close-owner 操作必须经过同一状态闸门。

#### P2：继续开发不能稳定闭环

当前 `composeGalleryDevMessage()` 包含作品信息，但没有明确说明：修改完成后要再次调用 `gallery_publish`，也没有说明保持同一 kind/path/entry 才会更新同一张卡片。对于 panel，作品 id 还决定固定 origin，换入口会导致数据分裂。

**整改决策**：继续开发文本增加稳定身份和回发布协议，并允许工具接收可选 `appId`：

- 同一作品上下文包含 `作品 ID`；
- 优先用同一 `appId` 更新原条目；
- 没有 id 时继续使用工作区 + 类型 + 最终入口的兼容匹配；
- 模型修改完成后必须重新验证，再用同一作品 id 发布；
- 除非明确要创建新作品，不得改变 kind 和最终入口；
- panel 作品说明保持 id 可避免 localStorage / IndexedDB origin 改变。

## 三、目标契约

### 3.1 `gallery_publish` 工具契约

工具保留 `path` 作为工作区边界检查字段，新增或调整以下字段：

| 字段 | 规则 |
|---|---|
| `appId` | 可选。来自“继续开发”的既有作品；存在且属于当前工作区时优先更新该条目 |
| `title` | 必填，作品墙展示名 |
| `kind` | 必填，只能是 `file` / `server` / `panel` |
| `path` | 必填，工作区内文件或目录；必须保留该字段名以接入 workspace 权限检查 |
| `entry` | file/panel 可选；用于从目录解析最终入口；server 禁止使用 |
| `command` | server 可选；panel 必须与 url 同时填写或同时省略 |
| `url` | server 可选；panel 必须与 command 同时填写或同时省略 |
| `runMode` | 只对 server 有效：page 或 background |
| `panel` | 只对 panel 有效：窗口形态、尺寸、贴边和置顶 |
| `cover` | 工作区内图片，可选 |
| `description/tags` | 可选 |

工具失败必须是显式错误，不再静默丢弃关键参数。非法的 `runMode`、panel 字段仍可采用缺省归一化；但 `entry` 语义错误和 panel command/url 不成对必须直接报错。

### 3.2 发布回执契约

成功回执至少包含：

- 发布还是更新；
- 作品 id；
- 最终入口；
- 作品类型；
- panel 的服务托管状态；
- 封面来源；
- 作品墙入口。

panel 服务相关回执要区分：

1. “已由平台启动并托管”；
2. “地址已可达，复用外部服务，平台不会在关窗时停止它”；
3. “没有配置本地服务，面板直接打开”。

### 3.3 skill 契约

更新 `resources/skills/gallery-publish/SKILL.md`：

- 明确 `path` 与 `entry` 的最终解析规则；
- 明确 panel 本地服务的 command/url 必须成对；
- 明确关窗语义为“异步停止平台为该面板启动的服务”，不是无条件停止所有同地址服务；
- 明确平台托管命令必须前台长期运行，不得使用 `start` / `pythonw` / `cmd /c start` 等脱离进程树的启动器；
- 明确继续开发完成后要用同一作品 id 或同一最终入口重新发布；
- 保留 panel CORS、内置浏览器正常 CORS、service worker 和连接 reset 边界；
- 增加 panel 作品代码等同受信任本地代码的安全提示；
- 发布前检查清单增加“确认回执不是外部服务复用”“确认 panel 已 reload/页面显示最新代码”。

### 4.4 后台服务状态机与并发控制

**涉及文件**：

- `src/main/gallery-service-runner.ts`
- `src/main/gallery-service.ts`
- `src/shared/gallery.ts`
- `src/main/gallery-service-runner.test.ts`
- `src/main/gallery-run-wiring.test.ts`
- `src/main/gallery-panel-service.test.ts`

**改动**：

1. 增加每个 appId 的操作锁或串行队列。
2. start/stop/restart/stopByOwner/disposeAll 共用取消和状态判断。
3. 停止中的 entry 不允许被复用；返回“正在停止，请稍后再运行”。
4. 应用退出设置 disposed 标记，在途 start 在 spawn 前检查并取消。
5. 旧进程未确认退出时，restart 不启动新进程；超时必须明确显示“旧进程可能仍在运行”，不得静默放行。

7. 平台托管服务命令在就绪前退出时明确失败；不再把退出码 0 的脱离式启动器当成可回收成功服务。
8. stopByOwner 只停止 `ownerPanelId` 对应的、由平台启动的记录；外部复用服务不创建记录，也不进入停止链路。
9. `disposeAll()` 关闭服务记录前，先阻止新的 start；验证所有已 spawn 进程均收到 killTree。
10. 保持日志尾部、服务看板和现有 250ms 推送合并策略。

## 五、测试与验收矩阵

### 5.1 单元测试

| 场景 | 验收标准 |
|---|---|
| path/entry 解析 | 输入不同组合得到唯一、正确的最终入口 |
| 越界路径 | file、server、panel、cover、entry 任一路径越界都被拒绝 |
| 发布更新 | 同 appId 或同最终入口更新原卡，id、createdAt、panel 数据身份不变 |
| panel 服务配置 | command/url 缺一项立即报错；两者都无表示无平台服务 |
| 外部服务复用 | 地址已可达时不 spawn、不创建 owner、不在关窗时 stop |
| panel reload | 作品墙运行 reload，panel 内部 show/focus 不 reload |
| 服务退出 | 就绪前退出必失败；就绪后退出变 stopped/failed 并保留日志 |
| 双事件 | error + exit 只结算一次 |
| 停止竞态 | stopping 期间不能复用，重启等待旧进程完成 |
| 退出竞态 | disposeAll 后在途 start 不得 spawn |
| 继续开发 | 同工作区、跨工作区、composer 未就绪、超时、session.new 失败均有明确结果 |

### 5.3 真机冒烟

在不重启现有宿主实例的前提下，使用隔离 user-data-dir 执行：

1. 发布 file 作品，修改后重新运行，确认浏览器页面为最新版本。
2. 发布 panel 作品，不带本地服务，确认固定 origin 数据跨关闭/重开保留。
3. 发布 panel + command + url，确认服务先启动、探活通过后开窗；关闭 panel 后服务停止。
4. panel + 只填 command，确认发布阶段明确报错，不再静默开窗。
5. panel 连接外部无 CORS API，确认 panel 可请求；内置浏览器同一请求仍保持正常 CORS 语义。
6. server + page，确认后台进程启动并打开页面；关闭页面后服务仍在看板运行。
7. server + background，确认只启动后台服务，不打开无意义页面。
8. 外部地址已可达时运行 panel，确认平台不接管、不在关窗时杀外部服务。
9. 快速连续运行、关闭后立即重开、应用退出时运行中，确认没有重复进程和孤儿进程。
10. 跨工作区继续开发，确认新话题、工作区、注入文本和失败提示均正确。

## 七、风险与回滚策略

| 风险 | 应对 |
|---|---|
| 旧作品没有显式 entry | 兼容“path 即最终入口”，读盘和运行行为不变 |
| appId 更新可能误覆盖作品 | 发布前校验 appId 存在、工作区一致、kind 兼容；不满足条件直接拒绝 |
| panel reload 破坏页面临时状态 | 只影响内存状态；持久数据契约明确使用 localStorage / IndexedDB；提供手动前置和重载语义区分 |
| 服务串行化导致按钮等待时间增加 | UI 显示“停止中/启动中”，不重复 spawn；超时必须可见并保留日志 |
| 禁止启动器命令影响旧用户 | 旧清单继续读取；仅在再次启动时给出迁移提示，建议改为前台长期运行命令 |
| CORS 放宽被误用于不可信作品 | skill 和首次运行提示明确 panel 是受信任本地代码；不扩大到普通浏览器窗口 |
| 协议镜像漏同步 | 每个新字段先更新 shared 类型，再同步 preload/main/utility/demo 和 wiring 测试 |
| 多会话并行改动同一文件 | 开始前检查 git status，按文件归属只 add 本次变更，不使用破坏性回退命令 |

回滚原则：

- 不删除旧的 gallery 清单字段；
- 不改变已有 panel origin 计算；
- 不把服务记录持久化到 settings；
- 若新状态机行为异常，优先回退运行编排层，保留 shared 数据归一化和文档测试；
- 任何回滚都必须保留旧作品可读取、可移除和可继续开发。

## 八、明确不做

1. 不自动扫描工作区或 outputs 目录登记作品。
2. 不实现作品版本历史、diff、回滚或多版本封面。
3. 不把作品清单迁移进 `settings.json`。
4. 不把普通内置浏览器窗口改成放宽 CORS。
5. 不为外部已运行服务建立虚假的 owner 或在关窗时强制停止它。
6. 不重新引入终端标签作为后台服务宿主。
7. 不在本轮扩展远程作品发布、云端部署或跨设备同步。
8. 不修改 package.json 版本号、不打 tag、不 push；发布动作另按发版流程执行。

## 九、完成定义

整改完成后，模型应能在以下典型请求中得到确定结果：

- “把 `panels/status/index.html` 发布成 panel”：明确入口，不误解析目录；
- “这个 panel 需要 `node bridge.mjs` 提供数据”：模型知道必须同时提供探活 url，运行时先启动服务再开窗；
- “我已经在外面启动了服务”：模型知道这是外部服务，平台不会在关窗时杀掉它；
- “继续优化刚才的作品”：模型知道目标工作区、作品 id、固定 origin 和完成后要重新发布更新；
- “把纯 API 服务放到后台”：模型会使用 server + background，不弹无意义页面；
- “页面改完后再运行”：panel 会加载最新代码，server 页面会重新进入作品地址；
- “关掉面板”：平台启动的本地服务最终停止，并在看板中反映状态；外部服务保持不变。

最终验收以代码行为、工具回执、skill 文档和作品墙 UI 四者一致为准，而不是只检查某一处提示词或某一条源码断言。
