# SSH SFTP 文件上传/下载实现计划

## 一、背景与目标

PiDesktop 已有完整的 SSH 远程终端能力（人工 xterm + AI `ssh_*` 工具共享同一 shell 流），但**完全没有文件传输能力**。本计划为 SSH 标签页加人工的上传/下载 + 文件浏览，并给 AI 加两个文件传输工具。

### 现状核实（本轮探索结论，均有证据）

1. **全仓库 `sftp` 零命中**（`src/` 下 grep 无结果）。当前 SSH 只用了 ssh2 的 `Client + shell channel`。
   - `src/main/ssh-connections.ts:31-33` — `SshClientLike` 只声明 `connect/end/on/shell`。
   - `src/main/runtime-ssh.ts:72-192` — 工具仅 6 个：`ssh_hosts / ssh_connect / ssh_exec / ssh_write / ssh_read / ssh_close`。
   - `src/shared/protocol.ts:929-938` — `SshCommand` 仅 connect/input/resize/kill/host.save/host.delete/group.save/group.delete/hosts。
   - 渲染端无上传下载按钮、无拖拽、无 `writeFile/readFile` 字样。
2. **底座现成，无需新依赖**：`ssh2@1.17.0`（已装）自带 `SFTPWrapper`——`client.sftp(cb)`（`node_modules/ssh2/lib/client.js:1555`）、`readdir/stat/lstat/realpath/mkdir/unlink/rename/createReadStream/createWriteStream/fastPut/fastGet`（`@types/ssh2/index.d.ts:1718+`）。
3. **连接生命周期归标签页所有**：`src/renderer/src/App.tsx:2130-2132` 关闭 ssh-terminal 标签时发 `ssh({type:"kill", terminalId})`；`ssh-connections.ts:641` 的 `kill()` 会 `end()` 整个 client。**这正是用户拍板"不能离开终端单独传文件"的技术含义**——文件能力必须寄生在 ssh-terminal 标签的生命周期内，反之不成立（不做独立连接、因此连接生命周期代码一行不改）。
4. **`.pidesktop/downloads/` 约定已存在**：`src/main/browser-downloads.ts:20` `DOWNLOAD_DIR_SEGMENTS = [".pidesktop","downloads"]`，配 `downloadDirFor(workspace)`、`downloadRelativePath(filename)`、`sanitizeDownloadName(raw)`（同一个模块 60-95 行，含路径分量剥离、Windows 保留名转义、超长截断保扩展名）。
5. **工作区边界既有判据**：`src/main/attachments.ts:8` `workspaceRelativeAttachment`；`src/main/pi-runtime.ts:1445` `pathIsWithin`；`src/main/pi-runtime.ts:1461` `resolveWorkspaceUploadFiles`（绝对路径直接抛错）。`browser_upload` 正是用这套锁死 AI 的本地读范围。
6. **AI 操作通道已就绪**：`ssh-automation.request/.result` 绕过串行命令队列，外层超时 `SSH_RPC_TIMEOUT_MS = 120_000`（`src/main/pi-runtime.ts:399`）。`ssh_exec` 已有"工具传 timeoutMs、外层按需放宽"的先例需要复用（见步骤 5）。
7. **权限轴已就绪**：`src/main/permissions.ts:43` 把 `ssh_connect/exec/write/close` 标 `ssh` 风险；`permissionAction` 对 ssh 轴是 read-only 拒 / workspace 逐次问 / full 放（`permissions.ts:55-58`）。
8. **SFTP 并发安全（更正上一轮的口头结论）**：ssh2 的 SFTP 按 reqid 多路复用（`SFTP.js:2847/2878/2938` 以 `_requests[reqID]` 派发），并发请求在协议层**是安全的**，不存在"响应乱序"。真实约束只有服务器 open-handle 上限（`maxOpenHandles`，`SFTP.js:2813`，来自 openssh `limits@openssh.com` 扩展）与进度可读性。计划据此不引入不必要的串行锁，只做单连接单传输的进度约束（见步骤 2）。
9. **主题钩子是公开 API，需五处镜像**：`AGENTS.md`、`docs/theme-guide.md`、`~/.agents/skills/pidesktop-theme-creator/SKILL.md`、同 skill 的 `references/variables.md`、同 skill 的 `scripts/check_theme.py`（已验证 `ssh-*` 系列在上述 5 处均有条目）。
10. **测试基线**：`npm test` = 131 文件 / 1593 例，其中 `src/main/browser-static-server.test.ts` 的 1 例（`fetch failed / bad port`）是**本机网络环境导致的偶发失败**，单独跑该文件 9/9 全绿，与本改动无关。

### 已确认的用户决策（本轮 ask_question）

| 项 | 决策 |
|---|---|
| 范围 | **只做单文件**，不做文件夹递归（v1） |
| 单次大小上限 | **500 MB**，流式写盘（不整包进内存） |
| 人工下载落点 | 默认 `.pidesktop/downloads/`，完成后给"在文件夹中打开" |
| AI 上传源路径 | **只能工作区相对路径，越界直接拒**（与 `browser_upload` 一致） |
| 能否离开终端传文件 | **不能**——文件能力寄生在 ssh-terminal 标签内 |

### 目标产物

1. **人工**：ssh-terminal 标签内一个可开关的文件抽屉——远端目录列表（面包屑导航）+ 上传（系统对话框选文件，可选工作区外）+ 下载（落 `.pidesktop/downloads/` + 打开文件夹）+ 传输进度与取消。
2. **AI**：`ssh_upload`、`ssh_download` 两个工具。

## 二、设计

### 架构

```
渲染端                                    主进程                                   utility(Pi)
SshTerminalPanel                                                          runtime-ssh.ts
  └ SshFilesPanel(抽屉)                    ssh-connections.ts               ssh_upload
      sftp.list/upload/download  ──IPC──▶    ├ handle(command)              ssh_download
      ssh:data:<id> 传进度      ◀─────────   └ handleSftp(command)
                                            ssh-sftp.ts(新)
                                              SshSftpTransferService
                                              (每连接一个，流式 + 进度 + 取消)
                                            browser-downloads.ts(复用)
                                              downloadDirFor / sanitizeDownloadName
```

- **传输放主进程**：对齐 ssh2 连接持有者（utility 无 Electron API，也无 `ssh2` 连接）、对齐 `browser-downloads` / `browser-save-image` 的落盘先例。
- **不新增依赖**，不动连接生命周期，不动连接上限（`SSH_MAX_CONNECTIONS = 5`）。

### 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | SFTP 通道**懒开**（首次文件操作时 `client.sftp()`），连接 `disposeRecord` 时一并销毁 | 不用文件功能的用户零额外开销；通道随连接死，不会泄漏 |
| D2 | 传输用 `createReadStream`/`createWriteStream` 手工 pipe + 字节计数，**不用** `fastPut/fastGet` | fastXfer 内置 64 并发（`SFTP.js:2186`）使取消与"部分文件"清理语义模糊、进度粒度粗；手工流可精确计字节、可中断、可清理 |
| D3 | 下载先写 `name.part`，成功后 `rename`，失败 `unlink` | 避免半截文件长得像完整文件；上传失败则尽力 `unlink` 远端半成品（远端 unlink 失败只记警告，不掩盖原始错误） |
| D4 | 单连接同时**只允许一个传输**，第二个请求明确拒绝并提示等待 | 避免服务器 open-handle 压力与进度条互相打架；协议层本可并发（现状 8），但 v1 不需要 |
| D5 | 本地落盘名经 `sanitizeDownloadName` 清洗 + 同名递增序号（`photo.png` → `photo-1.png`），**绝不覆盖** | 远端返回的文件名是不可信输入；与 `browser-save-image.ts:164-181` 同口径 |
| D6 | 远端同名文件冲突：**自动递增序号，不覆盖**，最终名写进回执 | 不静默覆盖远端数据，也不为冲突再拉一套确认 UI |
| D7 | 500 MB 上限为模块常量 `SSH_TRANSFER_MAX_BYTES`，**不做设置项** | 对齐 `MAX_UPLOAD_FILE_BYTES`（`browser-automation.ts:74`）做法；先给硬约束，需要再加 |
| D8 | 人工上传走**系统对话框**（`dialog.showOpenDialog`，多选，不限工作区）；AI 上传锁工作区 | 人工是从桌面/下载目录挑文件，锁工作区没法用；AI 是不可信调用方，必须锁。这个不对称是有意的 |
| D9 | 新增 `data-pane="ssh-files"` + 4 个 `data-control`，五处主题钩子文档镜像同步 | 主题钩子是公开 API（`AGENTS.md:38`），漏一处即契约破损 |
| D10 | `ssh_upload` / `ssh_download` 都标 **`ssh` 风险轴** | 两者都要先有 SSH 会话（用户主动授权的能力），且 `ssh_download` 是把不可信远端字节落进本地磁盘——与 `ssh_exec` 同级别**待确认**。**这是本计划里最容易被你否掉的一条**，改成"download 免门（对齐 browser 下载的观察产物口径）"只需去掉 `permissions.ts` 一行 |

## 三、实施步骤

### 步骤 1：协议与主进程 SFTP 服务

**新建 `src/main/ssh-sftp.ts`**（纯逻辑 + 注入依赖，可单测）：

- 最小接口视图（对齐 `SshClientLike` 的"结构视图 + 测试注入 fake"模式）：
  ```ts
  export interface SshSftpLike {
    readdir(path: string, cb: (err?: Error, list?: RemoteDirEntry[]) => void): void;
    stat(path: string, cb: (err?: Error, stats?: RemoteStats) => void): void;
    realpath(path: string, cb: (err?: Error, resolved?: string) => void): void;
    createReadStream(path: string): NodeJS.ReadableStream;
    createWriteStream(path: string): NodeJS.WritableStream;
    unlink(path: string, cb: (err?: Error) => void): void;
    end(): void;
  }
  ```
- 导出常量：`SSH_TRANSFER_MAX_BYTES = 500 * 1024 * 1024`。
- 导出的**纯函数**（测试主战场）：
  - `sortRemoteEntries(list)` — 目录优先、同类按名 `localeCompare`（对齐 `workspace-preview.ts:402` 口径）。
  - `remoteJoin(dir, name)` — POSIX 拼接，不引入 `node:path` 的 Windows 语义。
  - `remoteParent(dir)` — 面包屑"上一级"，根目录返回自身。
  - `formatRemoteSize(bytes)` / `formatRemoteTime(mtimeMs)` — 列表展示。
- `SshSftpTransferService` 类：
  - `constructor(deps: { sftp: SshSftpLike; publish(event: SshEventData): void; terminalId: string; schedule?(): () => void })`
  - `list(path)` → 目录列表（含 `realpath` 归一化）。
  - `upload({ localPath, remoteDir, remoteName?, timeoutMs })` → 流式 + 进度 + 结束回执。
  - `download({ remotePath, localDir, timeoutMs })` → `.part` → rename。
  - `cancel(transferId)` / `dispose()`（销毁流、清 `.part`、`sftp.end()`）。
  - 进度节流（对齐 `FLUSH_INTERVAL_MS = 10` 量级，约 100ms 推一次，避免刷爆 IPC）。
  - 失败/超时一律清理半成品，且**原始错误不被清理错误掩盖**。

**修改 `src/main/ssh-connections.ts`**：
- `SshClientLike` 增加 `sftp(cb: (err: Error | undefined, sftp: SshSftpLike) => void): void`。
- `ConnectionRecord` 增加 `sftp?: SshSftpLike`、`transfer?: SshSftpTransferService`。
- 新增私有 `ensureSftp(record): Promise<SshSftpLike>`（懒开 + 缓存 + 连接已关则明确报错）。
- `handle` 返回类型放宽为 `SshCommandResult | Promise<SshCommandResult>`（现有 case 全同步，测试不受影响），或新增 `handleSftp(command): Promise<SshCommandResult>`（实施时取改动面更小者；倾向后者 + `index.ts` 分派）。
- `disposeRecord` / `kill` 增加：取消在途传输、`sftp.end()`、`transfer.dispose()`。

**修改 `src/shared/protocol.ts`**：
- `SshCommand` 增加：`{type:"sftp.list", terminalId, path?}`、`{type:"sftp.upload", terminalId, transferId, remoteDir, localPaths: string[]}`、`{type:"sftp.download", terminalId, transferId, remotePaths: string[], localDir?}`、`{type:"sftp.cancel", terminalId, transferId}`。

## 五、风险与假设

| 风险 | 处置 |
|---|---|
| **RPC 外层 120s 超时会误杀长传输** | 步骤 3 已列为必做：按 `request.timeoutMs` 放宽外层；并有反向验证用例覆盖超时清理 |
| 服务器不支持 SFTP 子系统（`client.sftp()` 失败） | 明确报错文案（"服务器未启用 SFTP"），不静默失败；文件抽屉显示错误态而非空列表 |
| 服务器 open-handle 上限低 | D4 单传输约束 + 上传下载各只开 1 个 handle，压力可控 |
| 500MB 传输时长与用户等待的体感 | 进度事件让用户看到在动；取消随时可用；不做断点续传（v1 明确不做） |
| 远端文件名导致本地非法名 | `sanitizeDownloadName` 复用（已覆盖 Windows 保留名/控制字符/超长） |
| 远端路径注入（名字里带 `../`） | 上传时远端目录只接受用户/模型给的目录，文件名**只取 basename**；下载本地名同样只取 basename 并清洗 |
| 修改 `ssh-connections.ts` 影响既有 6 工具 | `handle` 现有 case 保持同步返回语义；sftp 走独立分派；既有测试用例不动（除工具名清单断言） |
| 主题钩子漏镜像 | 步骤 6 列全 5 处，验证第 8 条逐项核对 |

### 假设

- 用户机器上的 `dialog.showOpenDialog` / `revealInExplorer` 可用（既有功能，已在用）。
- 工作区已选定（`workspace` 非空）；为空时下载落点退化为报错提示"请先选择工作区"，不静默写到安装目录（这正是迭代记录 2026-09-16 修复过的同类坑，必须避免重犯）。
- 用户接受 D10（两个工具都走 `ssh` 风险轴、workspace 模式逐次确认）。

### 明确不做（v1）

- 文件夹递归上传/下载
- 断点续传 / 限速 / 拖拽上传
- 远端文件编辑、重命名、删除、新建目录（**只读浏览**）
- `ssh_list` 工具（AI 已有 `ssh_exec ls`，无需新增）
- 独立于终端的 SFTP 连接
- 大小上限做成设置项
