# Project Conventions

- Keep Pi runtime objects behind `src/shared/protocol.ts`; the renderer consumes only the desktop protocol.
- Keep Electron main focused on native lifecycle, dialogs, persistence, and process supervision.
- Run Pi sessions and tools in the utility process, not in the renderer or main process.
- Pi is used only as the Agent runtime core. Its third-party extension access (loading, approval, binding, `pi-mcp-adapter`, subagent CLI shim) has been removed; do not reintroduce it. The only retained extension hooks are app-owned inline extensions: the permission gate, the tool-audit logger, the user-hooks interpreter, the plan-mode narration injector, and the checkpoint snapshotter.
- Tool pipeline (`src/main/tool-audit.ts`, `src/main/tool-delta.ts`): every tool execution is appended to `chatanytime-sessions/<agentId>/tool-audit.jsonl` (best-effort), and MCP `callTool` is bounded by a 120s `AbortSignal` timeout. MCP tool additions/replacements hot-apply to the live session via `pi.registerTool()` on the captured `ExtensionAPI` (no session rebuild); removals still rebuild the session because Pi has no tool-removal API.
- Builtin tool toggles (`BUILTIN_TOOLS` in `settings.ts` → `AgentProfile.tools` → `session.setActiveToolsByName` after creation): Pi builds all builtin tool definitions unconditionally, so per-agent enablement is pure name filtering (subagents inherit the parent agent's set the same way in `subagent.ts`). New tools default to OFF through `defaultToolEnabled` (absent keys in stored agent profiles stay off, everything else keeps absent=on) so an upgrade never changes an existing agent's toolset or request prefix; `powershell` (Pi 0.84.3, Windows-native shell tool sharing bash's `{command}` schema and infra) is the first opt-in tool. Every bash special-case recognizes it: permission `command` risk + `summarizeArgs` command summaries, hook deny-regex matching (`hookMatchText` — matchers still filter by tool name in user config), background-process command extraction (`bashCommandsFromMessages`), and checkpoint/artifact output candidates.
- Hooks (`src/main/runtime-hooks.ts` + `src/main/hooks-config.ts`): the third app-owned inline extension (`pidesktop-hooks`, between the permission gate and the tool-audit logger in `extensionFactories`). Events: `session_start` (commands awaited in order), `tool_call` (blocking — `block` deny-regex actions evaluate in-process against the bash/powershell command line / other tools' args JSON; `blocking` command actions deny via exit code 2 or stdout `{"block":true,"reason"}`, same `{block,reason}` contract as the permission gate, both gates stack), `tool_execution_end`, `agent_end` (whole reply finished — fires once per agent run with summed usage, total duration, and a failure flag that EXCLUDES user aborts (`stopReason === "aborted"`, same source as the sidebar dot; the per-tool `tool_execution_end` `isError` stays raw — a killed tool really did return an error result); this is the notification/stats event), and `turn_end` (per model-call cycle — fires multiple times per reply; users almost always want `agent_end`). Actions: `notify` (desktop notification via `hook-notify` push — carrying the triggering `sessionId` — executed by the main process: Electron `Notification`, click focuses the window, chat-app do-not-disturb semantics suppress it when the notification is about the currently-viewed session and the window is focused and not minimized; the utility process has no Electron API), `http` (POST event JSON, 10s timeout), `block`, `command`. Config is dual-scope JSONC (`<workspace>/.pidesktop-hooks.json` overriding global `<agentDir>/pidesktop-hooks.json`, merged by rule name, mcp-config-style atomic writes); handlers read a module-level cache at fire time, so `hooks.save/toggle/delete` only refresh the cache + re-emit the resource catalog — no session rebuild and no busy rejection (a user may want to disable a dangerous hook mid-run). Hook commands are user-authored config with terminal-grade trust: they bypass the agent permission gate, run via `spawn({shell:true})` in the utility process (timeout 1–120s, default 10s, `taskkill /T` tree-kill on Windows), and receive context only via stdin JSON + `HOOK_*` env vars — never via system-prompt or per-turn injection (cache discipline; `before_agent_start`/`context` injection is deliberately not exposed). Hook failures warn and allow. Master toggle `settings.hooks.enabled` (absent = enabled) is read live. Panel: settings-dialog 钩子 tab (`src/renderer/src/HooksSettings.tsx`) with per-rule test runs (`hooks.run` → `hook-run` push). Subagents do not get hooks.
- Capability clusters extracted from `pi-runtime.ts` live in `src/main/runtime-*.ts` (todo-tools / skills / vision / permissions / mcp) as pure builders over explicit inputs; session lifecycle and command dispatch stay in `pi-runtime.ts`.
- Multi-session runtime: `pi-runtime.ts` keeps several sessions alive concurrently as `SessionRuntimeRecord`s (session/busy/status/executions/todos/permission-gate/customTools are per-record) in `liveSessions`, with `activeRuntime` selecting the record that feeds `RuntimeSnapshot`. Switching or creating a session parks the previous one (it keeps executing in the background and can be reactivated as the same live record); only same-session rebuilds, workspace removal, or idle-LRU eviction (`MAX_PARKED_SESSIONS`) dispose records. Sidebar status dots (`SessionSummary.runStatus`): running=yellow is live state; completed=green / failed=red / aborted=grey are unseen-outcome notifications that clear on activation (`setTerminalRunStatus`/`activate`) and are never set for the session the user is already viewing. Terminal outcomes come from ONE place (`main/run-outcome.ts`: `resolveRunOutcomeStatus` reads Pi's `stopReason === "aborted"`, never the SDK-specific English abort text — undici's "This operation was aborted", anthropic's "Request was aborted" …), shared with the message pipeline and the hooks audit so a user stop is never reported as a failure. Aborted turns render neutrally instead of the red error row: `message-normalize.ts` strips the SDK abort text once and sets `ChatMessage.aborted` (historical sessions in the JSONL carry `stopReason`, so reopening them is clean too), the bubble shows a muted「已停止生成」 line, `ToolExecution.status === "aborted"` renders 「已中止」 with a neutral icon (never the failure styling), and aborted executions are excluded from 交付产物 (no rollback entry). The sidebar session list is agent-scoped: `refreshSessions` lists only `chatanytime-sessions/<agentId>/` and stamps `currentSessionsAgentId`; `createSession`'s "list already loaded" shortcut (`sessionListReadyFor`) requires the cached list to belong to the current agent, so an agent switch always re-lists instead of showing the previous agent's topics. Workspace grouping (`session-groups.ts`): sessions group by their own workspace, and a session-less workspace only shows as a group while it is the ACTIVE workspace — recent-workspace history (`<agentDir>/pidesktop-recent-workspaces.json`) is shared across assistants, so merging it wholesale would surface every historical workspace as an empty group for a fresh assistant. Workspace memory is per-assistant (`DesktopSettings.agentWorkspaces`, agentId → resolved absolute path; deliberately NOT on AgentProfile because agent.save overwrites whole objects and a stale form snapshot would clobber the runtime field — settings page never renders it). Main-side `updateSettings` persists it and the utility mirrors it in memory (双写对称) through the same pure functions in `main/settings.ts`: `recordAgentWorkspace` (record on `workspace.open`/`session.new`/`session.open` with explicit workspace/`activate` when the focus crosses workspaces; a split-focus on another workspace counts as that assistant's last-used workspace), `forgetAgentWorkspace` (resolve+lowercase match only), `resolveInitialWorkspace`/`resolveDefaultWorkspace`. `settings.workspace` is retired: never written after this change, consumed exactly once at `initialize` as a migration fallback for the CURRENT active assistant (promoted into the in-memory map so in-session agent switches restore it) and cleared when a removed workspace matches it — no restart resurrection (the e42c139 lesson). A `defaultWorkspace` (settings 通用 tab, custom folder or built-in `<agentDir>/workspace-default`, idempotent mkdir) closes the no-workspace dead zone: assistants with no mapping fall back to it on `agent.select`/`workspace.remove`/`initialize` (directly chatable, never the landing page; mkdir failure keeps the landing path as an extreme fallback). `agent.select` restores the target assistant's mapped workspace or the default and touches recents (so the empty group can render); changing `defaultWorkspace` while the active workspace is the old default switches immediately to the new default with a fresh session. `workspace.remove` is assistant-scoped: deletes only the current assistant's session files and its map key, disposes live records only when `record.agent.id` is the current agent (another assistant's background sessions in the same workspace survive), never touches global recents, and when the removed workspace is the active one the assistant falls back to the default workspace with a fresh session (removing the default-workspace group just clears that assistant's sessions there — the default keeps acting as fallback). Session JSONL files are not written until their first assistant message (Pi `_persist` gates on `hasAssistant`), so `refreshSessions` backfills live-but-unpersisted sessions from `liveSessions` (`backfillUnpersistedSessions` in session-scope.ts, preferring the pre-refresh entry to preserve renames/pins and overlaying the live runStatus) — otherwise any delayed full refresh (the 500ms post-turn debounce, pin/rename/delete handlers) erases a freshly created empty topic from the sidebar until its first reply lands.
- Split view (`src/renderer/src/ConversationPane.tsx` + `SplitLayout.tsx` + `lib/split-layout.ts` + store `paneStates`): the conversation area (timeline + question panel + full composer) is one reusable `ConversationPane` used by BOTH single-window mode and split panes — never fork a second composer implementation. Panes address sessions by id: run commands (`session.prompt/skill/regenerate/compact/planMode/abort/queue.*`, `model.select`, `thinking.select`) take an optional `sessionId` routed via `resolveTargetRecord` in `pi-runtime.ts` (default = activeRuntime, back-compat). The focused pane IS the active session (focus switch = `session.open` live fast-path `activate`); global mirrors (topbar workspace/PanelDock/access mode) follow the focused pane. Non-active panes subscribe to `session.state` pushes (`SessionPaneSnapshot`, per-record 50ms throttle, uuid-identity merge in store `paneStates`) driven by `session.watch` registration (`renderedSessions` in main: watched records keep streaming, are exempt from idle eviction, get no terminal dots, and late watches for not-yet-live sessions queue in `pendingWatchSessions` until `createSession` attaches them). Layout is a recursive binary tree (`SplitNode` leaf/split, max 4 panes) persisted in localStorage `pidesktop.split-layout` and pruned when sessions disappear or the agent switches; right-click a sidebar session adds 「分屏到右侧/下方」. Per-session composer drafts live in App's `draftStore` map; App→pane composer writes (browser-pick, html-action) route through `composerBridge` to the focused pane. Permission/question surfacing is pane-set-scoped (`panePermissionRequest`/`paneQuestionRequest`, focused first; permission dialog shows the source session title). The plan-approval QuestionPanel renders inside its own pane.
- Self-built capabilities (MCP / Skill / Subagent / Todo) live in the utility process and are exposed to Pi as `customTools` (`ToolDefinition[]`) on `createAgentSession`, plus system-prompt injection for Skills. Do not run them in the renderer or main.
  - MCP: `src/main/mcp-client.ts` (`McpClientManager`) connects via `@modelcontextprotocol/sdk`; each tool becomes `mcp__<server>__<tool>`. Config in `.mcp.json` (project) / `mcp.json` (global). `McpServerSummary` carries the config projection (scope/transport/command/args/url/auth/bearerTokenEnv/env, plaintext = file content) so the settings panel can prefill an edit form. Edits go through `planMcpServerSave` (`runtime-mcp.ts`, pure): the name is the config key (locked while editing), a scope switch migrates the entry (remove from the old file, write the new one — a stale duplicate would shadow the edit since project wins), and `disabled` travels with the entry so editing never re-enables a paused server; `mcp.server.save` carries `original {name, scope}`, and `mcp.server.delete` falls back to the other scope's file when the declared one has no such entry. OAuth (`src/main/mcp-oauth.ts`, utility process): HTTP servers without `bearerTokenEnv` (bearer wins) get an SDK `OAuthClientProvider` on their transport — the SDK's `auth()` orchestration does RFC 9728 discovery + dynamic client registration + PKCE, `redirectToAuthorization` rides the `open-external` up-message to main's `shell.openExternal`, and `UnauthorizedError` maps to status `needs-auth` (not `failed`) so the 资源 tab can offer 认证/重新打开授权页/清除凭据 per `McpAuthState` (`idle/pending/authorized/failed` rides the summary; `pending` waits 10min then expires). Credentials persist in `<agentDir>/pidesktop-mcp-auth.json` — a deliberate, user-approved plaintext exception (same level as `mcp-cache.json`) so refresh tokens survive restarts; the loopback callback server prefers port 1456 (persisted; drift invalidates the DCR registration and re-registers) and is `unref`'d, with `dispose()` riding `parentPort`'s `close` event. `mcp.server.auth` has three branches (a pending URL is just reopened; explicit `auth: "oauth"` calls `beginAuthorization` without waiting for a 401; otherwise force-reconnect and let the 401 drive the flow); authorization completion (`onAuthorized`), pending expiry, and callback failures all re-push the resource catalog — `applyMcpToolChanges`' hot path (registerTool without rebuild) does NOT emit on its own, the `onAuthorized` wrapper compensates — so the panel never sticks on 等待浏览器授权. Renderer dev: `npm run demo` serves the renderer standalone in a plain browser via `.vite.demo.config.mjs` (port 5199); `main.tsx` falls back to `createDemoApi` (demo-api.ts) when no preload injected `window.piDesktop`, which mocks the OAuth round trip (认证 → 2.5s → connected).
  - Skill: `src/main/skill-catalog.ts` scans `pidesktop-skills/` (global) and `.pidesktop-skills/` (project) for `SKILL.md`; enable state in `pidesktop-skill-state.json`.
  - Subagent: `src/main/subagent.ts` `delegate_agent` creates a single-level child `AgentSession` under `chatanytime-sessions/<agentId>/delegations/`. It also resolves a custom subagent definition (`subagent` param, id or name) from `subagents-store.ts`——a dual-scope (global `<agentDir>/pidesktop-subagents.json` / project `<workspace>/.pidesktop-subagents.json`, project wins by id) JSON store surfaced in `ResourceCatalog.subagents`; a matched definition overrides the child's system prompt / model / tool set (`"inherit"` keeps the parent's enabled builtin tools), and `main`-session system prompt lists available subagents (`buildSubagentPromptBlock`).
  - Question: `src/main/runtime-question-tool.ts` exposes `ask_question` as a customTool; its execution blocks on `QuestionBroker` until the user answers in the renderer's question panel (`question`/`question.dismiss` pushes, `question.resolve` command — mirrors the permission round trip). The panel is paged (one question at a time) and auto-marks the first option of a choice question as（推荐）— the tool description tells models to put their recommended option first; no protocol change carries the recommendation. Pending questions cancel on session dispose; the tool is never permission-gated.
  - Todo: dsh-style single-owner semantics (`src/main/runtime-todo-tools.ts`): the single `todo_write` customTool whole-list-replaces the store (`src/main/todo-store.ts` atomic JSON, session-scoped at `chatanytime-sessions/<agentId>/todos/<sessionId>.json`, rebuilt in `createSession` so the task panel follows the active session; reads normalize the legacy `{id,title,notes}` shape). Todo state reaches the model only through tool-call args appended at the conversation tail — never via per-turn system-prompt or user-message injection (either would break the provider prefix cache); the renderer's task panel is read-only and there are no `todo.*` user commands. Anti-batching nudges stay tail-only too: the audit extension's `tool_execution_start` hook feeds a per-session pace tracker (`createTodoPaceTracker`), and `todo_write`'s result appends a batching reminder once ≥ `PACE_REMINDER_THRESHOLD` calls elapsed since the previous write. Turn-boundary lifetime follows dsh's todo-plan-clears-on-next-turn note: an explicit `session.prompt` clears the session's list (write-through + broadcast) so stale checklists never span turns — queued followUp/steering injections and regenerate are not boundaries.
  - Memory: long-term memory per assistant, cross-session (`src/main/memory-store.ts` markdown topics + derived `MEMORY.md` index under `pidesktop-memory/<agentId>/`; store rebuilt in `createSession`). Same cache discipline as todo: the governance block + a byte-frozen index snapshot join `systemPromptOverride` once per session (global topics + topics bound to the record's workspace), and all later changes flow through `memory_*` tool calls at the conversation tail (`src/main/runtime-memory-tools.ts`: write/read/list/search/delete; never permission-gated; live `settings.memory.enabled` check, no session rebuild). Panel edits go over `memory.*` commands directly to the store (never through the model's context) and take effect in the next session's snapshot; the memory panel (`data-pane="memory-panel"`) is the user's governance view with the master toggle, and clicking a topic opens its markdown body in the preview pane (renderer-local `PreviewTarget "memory"`; the shared MarkdownEditor persists through its `persistContent` override, which issues `memory.update` with title/description intact — no protocol change).
- Vision (`src/main/vision.ts` + `src/main/runtime-vision.ts`) is exposed as the `recognize_images` customTool injected per session. Attached images always stay in the session transcript (the user's bubble renders them and the JSONL persists them) regardless of model type; what changes for text-only conversation models is the transport: the shared `ModelRuntime` is wrapped once in `initialize` (`wrapModelRuntimeForVision`, `streamSimple` choke point — main sessions and subagents all pass through) so image parts are stripped from every LLM request whose model lacks image input, and the prompt text gets a trailing hint telling the model to call the tool (`visionHintText`; stripped again for display and regenerate matching via `stripVisionHint`). The tool recognizes the current turn's user images by scanning the live transcript at call time (`currentTurnUserImages` — everything since the last assistant message that concluded a previous run: Pi appends the tool-calling assistant message before executing the call, so mid-run `toolUse` steps do not end the scan; no inbox to stage or leak) through a user-selected multimodal model from the configured provider catalog (`settings.vision` `{ enabled, provider, model }`, resolved via the shared `ModelRuntime`); the model may also pass workspace image file paths (e.g. its own screenshots) via the `files` argument — workspace-bounded, size-capped, and format byte-sniffed via Pi's exported `detectSupportedImageMimeTypeFromFile` (the extension map in `runtime-vision.ts` is only a fast pre-gate; the sniffed MIME is authoritative, so renamed or non-image files are rejected instead of fed to the vision model) — or a `prompt` argument carrying per-call recognition guidance that overrides the settings-level custom prompt (blank/absent falls back to it, then the built-in default). The tool is registered for every session but activated only when the conversation model lacks image input (recomputed at session creation or model switch via `reconcileVisionTool`/`switchSessionModel`, never mid-turn). Image-input judgment is overridable per model: `settings.providers[].models[].imageInput` (user-checked in the settings dialog — the checkbox is editable for built-in providers too, covering models freshly fetched from `/models` endpoints whose catalog metadata carries no input types) wins over the catalog's `input` field everywhere — catalog push (`buildCatalogModels`, so the renderer attach/vision-dropdown logic follows), the transport strip guard, tool activation, and vision-model eligibility (`resolveVisionModel`'s predicate; `imageInputOverride` in model-catalog.ts is the shared lookup). Cache discipline: the tool schema is byte-stable (no dynamic state) and image counts/prompt hints live only in the trailing user text.
- Browser automation (`src/main/browser-automation.ts` + `src/main/runtime-browser.ts`): the `browser_*` customTools (navigate/snapshot/click/type/press/scroll/eval/screenshot/wait/get/tabs) drive the user-visible preview tabs. Tools live in the utility process and forward every operation over a request/response RPC (`browser-automation.request` RuntimeMessage up, `browser-automation.result` RuntimeCommand back — results bypass the serial command queue in `parentPort.on("message")`); the main-process `BrowserAutomationController` executes them over Electron's built-in `webContents.debugger` (CDP `Runtime.evaluate` / `Input.dispatchMouseEvent` / `Input.insertText` / `Page.captureScreenshot`; no Playwright dependency) against `BrowserPreviewController` tabs. Sessions bind to a tab on first use (foreground tab, or a created `pi-browser-<uuid>` tab pushed to the renderer via the `browser-preview:tabs` event so the preview panel shows and activates it); per-tab busy locks serialize concurrent operations. Snapshot refs (`@e1..@eN`) are NOT stable handles: the registry only remembers per-ref element signatures, every click/type re-locates the element and verifies the signature, and mismatches fail with a "re-snapshot" error (agent-browser ref-lifecycle semantics). The element collector pierces open shadow roots recursively and descends into same-origin iframes (stable depth-first walk keeps ref indexes reproducible); cross-frame coordinates are converted to top-level viewport coordinates for CDP input events and obstruction checks run in each element's own root space (cross-origin frames are unreachable from DOM script). Snapshot output is capped (200 elements, 3000 page-text chars) and wrapped in untrusted-page-content markers; screenshots return image parts (multimodal models see them directly, text-only models get the existing `stripContextImages` placeholder pointing at `recognize_images`); every capture is also persisted to the record workspace's `.pidesktop/screenshots/` (timestamped name, keep-last-20 cap, `saveBrowserScreenshot` returns the workspace-relative path) and the tool result text carries that path so text-only models can feed it to `recognize_images` instead of inventing a filename. Permissions (`permissions.ts`): `browser_navigate` and write-mode `browser_eval` carry the `browse` risk through the permission gate (read-only mode denies); all in-page operations are trusted. Local-file navigation (`src/main/browser-static-server.ts`): `browser_navigate` accepts `file:///` URLs and Windows absolute paths and maps them onto a loopback-only static server (`BrowserStaticServer` — per-run random token path segment, mounts the record workspace passed as the navigate request's `workspace` field, else the file's own directory, `..`/absolute/symlink escapes rejected, directory → index.html), so a file page never gets a local-file origin and relative assets/scripts work. Every in-tab operation is bounded by a main-side 110s timeout (`withOpTimeout`, just under the utility's 120s RPC watchdog): on timeout the per-tab busy lock is released with a retryable error while the op continues detached (its late outcome is swallowed); the utility side complements this with `runWithBusyRetry` — a busy-tab rejection (stable marker 标签页正忙) is retried with a 1.5/3/4.5s backoff instead of burning an LLM round trip. Screenshots have a visibility precondition: `Page.captureScreenshot {fromSurface}` only answers when the surface produces frames, and a bound tab keeps accepting evaluate/input ops while hidden (panel closed, another preview tab foreground, dialog `browserSuspended`, minimized window) — so a screenshot on a hidden tab used to hang until the 110s watchdog. `screenshot` now runs `ensureTabRenderable` first (`isTabRendered` + `isWindowRenderable` on the preview controller): already rendered → no-op; otherwise it re-fires `automation-started` (the ONE deliberate non-bind-time reveal — a screenshot is the moment the user wants to see the tab) and polls up to 8s for the reveal round trip, then fails fast with the actionable cause (tab invisible vs window minimized) instead of a 110s hang; the capture call itself has a dedicated 30s timeout (`withOpTimeout` custom message) so an occluded-but-"visible" window still surfaces guidance quickly. Automation-tab lifecycle: tabs used to outlive every session that ever bound them (the only destruction paths were user close and app quit — `disposeRecord` never touched the controller), leaving hidden `pi-browser-*` tabs each holding a live renderer process. Now session disposal posts `browser-automation.session-disposed` (utility → main) which calls `releaseSession`: drop the binding and close the tab — ONLY `pi-browser-*` automation-created tabs (a session bound to the user's own foreground tab never closes it), deferred while another session still binds it (tabs new/switch rebind) or an op is in flight; same-id rebuilds pass `keepBrowserTab` (the successor record inherits the binding — closing would drop page state). A 5-min idle sweep (`sweepIdleAutomationTabs`, unref'd interval cleared in dispose) collects what a release deferred: `pi-browser-*` tabs with no binding, 30min idle, not busy, and NOT currently rendered (never close what the user is looking at); parked sessions keep their bindings by design. Read-mode `browser_eval` enforces its denial via CDP `throwOnSideEffect`, whose V8 detector false-positives on nearly every DOM method call (`querySelectorAll`, `getComputedStyle`, …); such rejections (`isSideEffectRejection`) return an actionable "escalate to mode=write" error (which goes through the gate) instead of a bare script failure, and the tool description teaches that path. Master switch `settings.browser.enabled` (absent = enabled) is read live per call — tools stay registered, no session rebuild. The preview UI shows an `automating` banner during operations (`BrowserPreviewState.automating`), and `browser-preview:tabs` `automation-started` events reveal the preview panel when a session binds to a tab. Preview viewport controls (`src/renderer/src/lib/preview-device.ts`, one shared preset/scale module behind BOTH the browser tab toolbar and the artifact/html-file tab bar): device presets 自适应 / 桌面 1440 / 平板 768 / 手机 390 plus 适应窗口 (fit) vs 原始尺寸 (1:1). Fit scales by MEASURED content width, not just the preset: browser-side the main process measures `scrollWidth` via privileged `executeJavaScript` (after did-stop-loading / zoom / debounced bounds, 1px deadband) and pushes `BrowserPreviewState.contentWidth`; html-side `buildArtifactPreviewSource` injects a reporter script that postMessages `pidesktop-preview-size` from the allow-scripts sandbox (pure fragments fall back to parent-side `contentDocument` reads — full-doc sandboxes throw SecurityError and are skipped). Fit then widens the viewport to max(preset/panel, contentWidth) and scales by container/viewport so multi-artboard exports (~2000px wide) are fully visible; the renderer gates zoom sends with a 0.2% deadband (lastZoomRef, reset per tabId) so the measure→zoom loop converges instead of oscillating. `zoom` command (`webContents.setZoomFactor`, clamped 0.25–3 main-side); 1:1 ignores the measurement (honest overflow — browser clamps the frame to container width since native views cannot h-scroll, html stage scrolls). HTML side: the iframe is wrapped in a tree-stable `.artifact-device-stage` (device switch never remounts, dynamic previews keep running). The device dropdown temporarily sends `visible:false` while open (the WebContentsView floats above all DOM — same precedent as the "+" menu). Panel-level fullscreen: `previewFullscreen` in App toggled from preview-tab-actions (all tab types), Esc exits instead of closing the tab, panel gets `position:fixed; inset:0` at z-46 (below dialogs/toasts), and themes see `data-ui-preview-fullscreen`. Subagents do not get browser tools.
- Design Studio (`src/shared/design-schema.ts` + `src/shared/design-export.ts` + `src/main/design-store.ts` + `src/main/runtime-design.ts` + `src/renderer/src/design/`): the `design_*` customTools (list/create/open/read/update/export) let the model read/write a structured design document (Design-as-Code: JSON node tree persisted at `<workspace>/designs/<name>.design.json`, atomic tmp+rename, name-sanitized against traversal) — pure data-level ops through `applyDesignOps` (atomic: one bad op rejects the whole batch; create/update/move/delete/replace), no CDP. The renderer canvas (`DesignStudio`/`DesignCanvas`/`DesignLayers`/`DesignInspector`) and the AI tools share the same shared-layer pure functions; user edits apply optimistic-local and ride a convergence pipeline (mouseup flush for drags, 300ms debounce for property inputs) as `design.edit` commands; AI-side and command-side changes push `design.state` with a monotonic `revision` (renderer drops revision ≤ seen per doc — echo consumption counts pending edits so the model's own round-trip never re-renders over in-flight user input, last-write-wins v1); pushes carry `sessionId` and the renderer adopts only the ACTIVE session's (background/parked `design_*` pushes never clobber the focused canvas), unbound pushes (`design.query` with no doc, `design.close`) clear the canvas, and closing a doc drops its seen-revision entry so reopening the same doc re-renders even without a revision bump. Undo/redo is a renderer snapshot stack (cap 50, AI pushes included) replayed as `replace` ops — AI changes are undoable too, and delete/duplicate/toggleVisible pass `preDoc` snapshots so they are undoable as well.
