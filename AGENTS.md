# Project Conventions

- Keep Pi runtime objects behind `src/shared/protocol.ts`; the renderer consumes only the desktop protocol.
- Keep Electron main focused on native lifecycle, dialogs, persistence, and process supervision.
- Run Pi sessions and tools in the utility process, not in the renderer or main process.
- Pi is used only as the Agent runtime core. Its third-party extension access (loading, approval, binding, `pi-mcp-adapter`, subagent CLI shim) has been removed; do not reintroduce it. The only retained extension hooks are app-owned inline extensions: the permission gate, the tool-audit logger, the user-hooks interpreter, the plan-mode narration injector, and the checkpoint snapshotter.
- Tool pipeline (`src/main/tool-audit.ts`, `src/main/tool-delta.ts`): every tool execution is appended to `chatanytime-sessions/<agentId>/tool-audit.jsonl` (best-effort), and MCP `callTool` is bounded by a 120s `AbortSignal` timeout. MCP tool additions/replacements hot-apply to the live session via `pi.registerTool()` on the captured `ExtensionAPI` (no session rebuild); removals still rebuild the session because Pi has no tool-removal API.
- Builtin tool toggles (`BUILTIN_TOOLS` in `settings.ts` → `AgentProfile.tools` → `session.setActiveToolsByName` after creation): Pi builds all builtin tool definitions unconditionally, so per-agent enablement is pure name filtering (subagents inherit the parent agent's set the same way in `subagent.ts`). New tools default to OFF through `defaultToolEnabled` (absent keys in stored agent profiles stay off, everything else keeps absent=on) so an upgrade never changes an existing agent's toolset or request prefix; `powershell` (Pi 0.84.3, Windows-native shell tool sharing bash's `{command}` schema and infra) is the first opt-in tool. Every bash special-case recognizes it: permission `command` risk + `summarizeArgs` command summaries, hook deny-regex matching (`hookMatchText` — matchers still filter by tool name in user config), background-process command extraction (`bashCommandsFromMessages`), and checkpoint/artifact output candidates.
- Hooks (`src/main/runtime-hooks.ts` + `src/main/hooks-config.ts`): the third app-owned inline extension (`pidesktop-hooks`, between the permission gate and the tool-audit logger in `extensionFactories`). Events: `session_start` (commands awaited in order), `tool_call` (blocking — `block` deny-regex actions evaluate in-process against the bash/powershell command line / other tools' args JSON; `blocking` command actions deny via exit code 2 or stdout `{"block":true,"reason"}`, same `{block,reason}` contract as the permission gate, both gates stack), `tool_execution_end`, `agent_end` (whole reply finished — fires once per agent run with summed usage, total duration, and a failure flag; this is the notification/stats event), and `turn_end` (per model-call cycle — fires multiple times per reply; users almost always want `agent_end`). Actions: `notify` (desktop notification via `hook-notify` push — carrying the triggering `sessionId` — executed by the main process: Electron `Notification`, click focuses the window, chat-app do-not-disturb semantics suppress it when the notification is about the currently-viewed session and the window is focused and not minimized; the utility process has no Electron API), `http` (POST event JSON, 10s timeout), `block`, `command`. Config is dual-scope JSONC (`<workspace>/.pidesktop-hooks.json` overriding global `<agentDir>/pidesktop-hooks.json`, merged by rule name, mcp-config-style atomic writes); handlers read a module-level cache at fire time, so `hooks.save/toggle/delete` only refresh the cache + re-emit the resource catalog — no session rebuild and no busy rejection (a user may want to disable a dangerous hook mid-run). Hook commands are user-authored config with terminal-grade trust: they bypass the agent permission gate, run via `spawn({shell:true})` in the utility process (timeout 1–120s, default 10s, `taskkill /T` tree-kill on Windows), and receive context only via stdin JSON + `HOOK_*` env vars — never via system-prompt or per-turn injection (cache discipline; `before_agent_start`/`context` injection is deliberately not exposed). Hook failures warn and allow. Master toggle `settings.hooks.enabled` (absent = enabled) is read live. Panel: settings-dialog 钩子 tab (`src/renderer/src/HooksSettings.tsx`) with per-rule test runs (`hooks.run` → `hook-run` push). Subagents do not get hooks.
- Capability clusters extracted from `pi-runtime.ts` live in `src/main/runtime-*.ts` (todo-tools / skills / vision / permissions / mcp) as pure builders over explicit inputs; session lifecycle and command dispatch stay in `pi-runtime.ts`.
- Multi-session runtime: `pi-runtime.ts` keeps several sessions alive concurrently as `SessionRuntimeRecord`s (session/busy/status/executions/todos/permission-gate/customTools are per-record) in `liveSessions`, with `activeRuntime` selecting the record that feeds `RuntimeSnapshot`. Switching or creating a session parks the previous one (it keeps executing in the background and can be reactivated as the same live record); only same-session rebuilds, workspace removal, or idle-LRU eviction (`MAX_PARKED_SESSIONS`) dispose records. Sidebar status dots (`SessionSummary.runStatus`): running=yellow is live state; completed=green / failed=red are unseen-outcome notifications that clear on activation (`setTerminalRunStatus`/`activate`) and are never set for the session the user is already viewing. The sidebar session list is agent-scoped: `refreshSessions` lists only `chatanytime-sessions/<agentId>/` and stamps `currentSessionsAgentId`; `createSession`'s "list already loaded" shortcut (`sessionListReadyFor`) requires the cached list to belong to the current agent, so an agent switch always re-lists instead of showing the previous agent's topics. Session JSONL files are not written until their first assistant message (Pi `_persist` gates on `hasAssistant`), so `refreshSessions` backfills live-but-unpersisted sessions from `liveSessions` (`backfillUnpersistedSessions` in session-scope.ts, preferring the pre-refresh entry to preserve renames/pins and overlaying the live runStatus) — otherwise any delayed full refresh (the 500ms post-turn debounce, pin/rename/delete handlers) erases a freshly created empty topic from the sidebar until its first reply lands.
- Split view (`src/renderer/src/ConversationPane.tsx` + `SplitLayout.tsx` + `lib/split-layout.ts` + store `paneStates`): the conversation area (timeline + question panel + full composer) is one reusable `ConversationPane` used by BOTH single-window mode and split panes — never fork a second composer implementation. Panes address sessions by id: run commands (`session.prompt/skill/regenerate/compact/planMode/abort/queue.*`, `model.select`, `thinking.select`) take an optional `sessionId` routed via `resolveTargetRecord` in `pi-runtime.ts` (default = activeRuntime, back-compat). The focused pane IS the active session (focus switch = `session.open` live fast-path `activate`); global mirrors (topbar workspace/PanelDock/access mode) follow the focused pane. Non-active panes subscribe to `session.state` pushes (`SessionPaneSnapshot`, per-record 50ms throttle, uuid-identity merge in store `paneStates`) driven by `session.watch` registration (`renderedSessions` in main: watched records keep streaming, are exempt from idle eviction, get no terminal dots, and late watches for not-yet-live sessions queue in `pendingWatchSessions` until `createSession` attaches them). Layout is a recursive binary tree (`SplitNode` leaf/split, max 4 panes) persisted in localStorage `pidesktop.split-layout` and pruned when sessions disappear or the agent switches; right-click a sidebar session adds 「分屏到右侧/下方」. Per-session composer drafts live in App's `draftStore` map; App→pane composer writes (browser-pick, html-action) route through `composerBridge` to the focused pane. Permission/question surfacing is pane-set-scoped (`panePermissionRequest`/`paneQuestionRequest`, focused first; permission dialog shows the source session title). The plan-approval QuestionPanel renders inside its own pane.
- Self-built capabilities (MCP / Skill / Subagent / Todo) live in the utility process and are exposed to Pi as `customTools` (`ToolDefinition[]`) on `createAgentSession`, plus system-prompt injection for Skills. Do not run them in the renderer or main.
  - MCP: `src/main/mcp-client.ts` (`McpClientManager`) connects via `@modelcontextprotocol/sdk`; each tool becomes `mcp__<server>__<tool>`. Config in `.mcp.json` (project) / `mcp.json` (global).
  - Skill: `src/main/skill-catalog.ts` scans `pidesktop-skills/` (global) and `.pidesktop-skills/` (project) for `SKILL.md`; enable state in `pidesktop-skill-state.json`.
  - Subagent: `src/main/subagent.ts` `delegate_agent` creates a single-level child `AgentSession` under `chatanytime-sessions/<agentId>/delegations/`. It also resolves a custom subagent definition (`subagent` param, id or name) from `subagents-store.ts`——a dual-scope (global `<agentDir>/pidesktop-subagents.json` / project `<workspace>/.pidesktop-subagents.json`, project wins by id) JSON store surfaced in `ResourceCatalog.subagents`; a matched definition overrides the child's system prompt / model / tool set (`"inherit"` keeps the parent's enabled builtin tools), and `main`-session system prompt lists available subagents (`buildSubagentPromptBlock`).
  - Question: `src/main/runtime-question-tool.ts` exposes `ask_question` as a customTool; its execution blocks on `QuestionBroker` until the user answers in the renderer's question panel (`question`/`question.dismiss` pushes, `question.resolve` command — mirrors the permission round trip). The panel is paged (one question at a time) and auto-marks the first option of a choice question as（推荐）— the tool description tells models to put their recommended option first; no protocol change carries the recommendation. Pending questions cancel on session dispose; the tool is never permission-gated.
  - Todo: dsh-style single-owner semantics (`src/main/runtime-todo-tools.ts`): the single `todo_write` customTool whole-list-replaces the store (`src/main/todo-store.ts` atomic JSON, session-scoped at `chatanytime-sessions/<agentId>/todos/<sessionId>.json`, rebuilt in `createSession` so the task panel follows the active session; reads normalize the legacy `{id,title,notes}` shape). Todo state reaches the model only through tool-call args appended at the conversation tail — never via per-turn system-prompt or user-message injection (either would break the provider prefix cache); the renderer's task panel is read-only and there are no `todo.*` user commands. Anti-batching nudges stay tail-only too: the audit extension's `tool_execution_start` hook feeds a per-session pace tracker (`createTodoPaceTracker`), and `todo_write`'s result appends a batching reminder once ≥ `PACE_REMINDER_THRESHOLD` calls elapsed since the previous write. Turn-boundary lifetime follows dsh's todo-plan-clears-on-next-turn note: an explicit `session.prompt` clears the session's list (write-through + broadcast) so stale checklists never span turns — queued followUp/steering injections and regenerate are not boundaries.
  - Memory: long-term memory per assistant, cross-session (`src/main/memory-store.ts` markdown topics + derived `MEMORY.md` index under `pidesktop-memory/<agentId>/`; store rebuilt in `createSession`). Same cache discipline as todo: the governance block + a byte-frozen index snapshot join `systemPromptOverride` once per session (global topics + topics bound to the record's workspace), and all later changes flow through `memory_*` tool calls at the conversation tail (`src/main/runtime-memory-tools.ts`: write/read/list/search/delete; never permission-gated; live `settings.memory.enabled` check, no session rebuild). Panel edits go over `memory.*` commands directly to the store (never through the model's context) and take effect in the next session's snapshot; the memory panel (`data-pane="memory-panel"`) is the user's governance view with the master toggle.
- Vision (`src/main/vision.ts` + `src/main/runtime-vision.ts`) is exposed as the `recognize_images` customTool injected per session. Attached images always stay in the session transcript (the user's bubble renders them and the JSONL persists them) regardless of model type; what changes for text-only conversation models is the transport: the shared `ModelRuntime` is wrapped once in `initialize` (`wrapModelRuntimeForVision`, `streamSimple` choke point — main sessions and subagents all pass through) so image parts are stripped from every LLM request whose model lacks image input, and the prompt text gets a trailing hint telling the model to call the tool (`visionHintText`; stripped again for display and regenerate matching via `stripVisionHint`). The tool recognizes the current turn's user images by scanning the live transcript at call time (`currentTurnUserImages` — everything since the last assistant message that concluded a previous run: Pi appends the tool-calling assistant message before executing the call, so mid-run `toolUse` steps do not end the scan; no inbox to stage or leak) through a user-selected multimodal model from the configured provider catalog (`settings.vision` `{ enabled, provider, model }`, resolved via the shared `ModelRuntime`); the model may also pass workspace image file paths (e.g. its own screenshots) via the `files` argument — workspace-bounded, size-capped, and format byte-sniffed via Pi's exported `detectSupportedImageMimeTypeFromFile` (the extension map in `runtime-vision.ts` is only a fast pre-gate; the sniffed MIME is authoritative, so renamed or non-image files are rejected instead of fed to the vision model) — or a `prompt` argument carrying per-call recognition guidance that overrides the settings-level custom prompt (blank/absent falls back to it, then the built-in default). The tool is registered for every session but activated only when the conversation model lacks image input (recomputed at session creation or model switch via `reconcileVisionTool`/`switchSessionModel`, never mid-turn). Image-input judgment is overridable per model: `settings.providers[].models[].imageInput` (user-checked in the settings dialog — the checkbox is editable for built-in providers too, covering models freshly fetched from `/models` endpoints whose catalog metadata carries no input types) wins over the catalog's `input` field everywhere — catalog push (`buildCatalogModels`, so the renderer attach/vision-dropdown logic follows), the transport strip guard, tool activation, and vision-model eligibility (`resolveVisionModel`'s predicate; `imageInputOverride` in model-catalog.ts is the shared lookup). Cache discipline: the tool schema is byte-stable (no dynamic state) and image counts/prompt hints live only in the trailing user text.
- Browser automation (`src/main/browser-automation.ts` + `src/main/runtime-browser.ts`): the `browser_*` customTools (navigate/snapshot/click/type/press/scroll/eval/screenshot/wait/get/tabs) drive the user-visible preview tabs. Tools live in the utility process and forward every operation over a request/response RPC (`browser-automation.request` RuntimeMessage up, `browser-automation.result` RuntimeCommand back — results bypass the serial command queue in `parentPort.on("message")`); the main-process `BrowserAutomationController` executes them over Electron's built-in `webContents.debugger` (CDP `Runtime.evaluate` / `Input.dispatchMouseEvent` / `Input.insertText` / `Page.captureScreenshot`; no Playwright dependency) against `BrowserPreviewController` tabs. Sessions bind to a tab on first use (foreground tab, or a created `pi-browser-<uuid>` tab pushed to the renderer via the `browser-preview:tabs` event so the preview panel shows and activates it); per-tab busy locks serialize concurrent operations. Snapshot refs (`@e1..@eN`) are NOT stable handles: the registry only remembers per-ref element signatures, every click/type re-locates the element and verifies the signature, and mismatches fail with a "re-snapshot" error (agent-browser ref-lifecycle semantics). The element collector pierces open shadow roots recursively and descends into same-origin iframes (stable depth-first walk keeps ref indexes reproducible); cross-frame coordinates are converted to top-level viewport coordinates for CDP input events and obstruction checks run in each element's own root space (cross-origin frames are unreachable from DOM script). Snapshot output is capped (200 elements, 3000 page-text chars) and wrapped in untrusted-page-content markers; screenshots return image parts (multimodal models see them directly, text-only models get the existing `stripContextImages` placeholder pointing at `recognize_images`). Permissions (`permissions.ts`): `browser_navigate` and write-mode `browser_eval` carry the `browse` risk through the permission gate (read-only mode denies); all in-page operations are trusted. Master switch `settings.browser.enabled` (absent = enabled) is read live per call — tools stay registered, no session rebuild. The preview UI shows an `automating` banner during operations (`BrowserPreviewState.automating`), and `browser-preview:tabs` `automation-started` events reveal the preview panel when a session binds to a tab. Subagents do not get browser tools.
- Plan mode (`src/main/runtime-plan-tools.ts` + `src/main/plan-store.ts`): a per-session collaboration stance — produce a plan, cross an explicit approval gate, then implement. State is a session-scoped flag persisted at `chatanytime-sessions/<agentId>/plans/<sessionId>.json` (atomic, restored in `createSession`; `narrate` starts empty so a restored session gets only per-turn reminders, never the full entry guidance) and mirrored in `RuntimeSnapshot.planMode`. Entry points: `session.planMode` command (the /plan slash command and the 访问模式 dropdown's plan-toggle item), or the model's own `enter_plan_mode` customTool (self-entering when the task clearly needs planning first). The mode is deliberately soft — no tool filtering, no permission-axis change (dsh discipline: restraint = guidance + exit review; hard floors stay the user's access mode). Narration rides the per-session `context` extension event (fourth app-owned inline extension `pidesktop-plan-mode`): full guidance appended to the last user message's text once on entry, a short reminder scheduled per `agent_start` while enabled, never in the system prompt or transcript (cache discipline) — the `context` event returns replaced messages for that request only. `exit_plan_mode` is always registered; outside plan mode it rejects. Its single `plan` argument is the reviewable artifact (reconstructable from the log — no separate plan store), carried as `QuestionItem.detail` (markdown) through the existing QuestionBroker/panel; only the exact 「批准计划，开始实施」 answer consents — approval switches the mode off via the shared setter, archives the plan to `<workspace>/docs/plans/YYYY-MM-DD-<title>.md` main-process-side (`saveApprovedPlan`, failure never blocks approval), and returns implementation instructions; rejection keeps the mode and returns the user's verbatim feedback as a corrective `isError`; an ignored review keeps the mode. Subagents do not inherit plan mode.
- Checkpoint rollback (`src/main/runtime-checkpoint.ts` + `src/main/checkpoint-store.ts`): the fifth app-owned inline extension (`pidesktop-checkpoint`) snapshots a target file's pre-change content in the utility process at `tool_execution_start` — Pi awaits all extension handlers, so the snapshot completes before the tool runs (no race). Scope: `write`/`edit` via `changedWorkspaceFile` (exact target), plus bash/powershell commands' explicit output candidates (`artifactCandidatesFromBashCommand`: shared `>`/`>>` redirect, `-o`/`--output` flags, copy targets, and PowerShell `Out-File`/`Set-Content`/`Add-Content` cmdlets) — shell candidates only snapshot files that already exist, so a rollback never deletes a user file the command never touched; vague output-text artifacts are not snapshotted. Entries append to `chatanytime-sessions/<agentId>/checkpoints/<sessionId>.jsonl` (path computed from `record.agent.id` — the parked-session agent-switch lesson from plan-store applies). Rollback is a user action (renderer command `checkpoint.rollback { sessionId?, targets: [{ relativePath, toolCallIds }] }`), never AI-permission-gated, at SINGLE-FILE granularity: each 交付产物 row carries its own rollback action (hidden while the pane is busy) opening a per-file confirm dialog; the target carries the file plus every tool-call id that touched it in that reply, and the runtime filters the JSONL by that pair, taking the EARLIEST matching snapshot (pre-reply state), restoring content through `writeWorkspaceFile` (realpath escape checks), deleting files whose snapshot recorded `existed:false` (AI-created), and skipping oversize entries (content over `CHECKPOINT_FILE_LIMIT` 5MB stored as `truncated`) — results stream back as the `checkpoint-result` message (renderer toast + workspace-tree refresh). The conversation transcript is NOT rewound; the model re-reads the restored files on its next turn. Cleanup is three-layer, and read paths never filter by age: session/workspace deletion unlinks the JSONL (todos/plans precedent), lazy compression rewrites a file once it exceeds `COMPRESS_THRESHOLD_LINES` (drops entries older than `RETAIN_DAYS` 14d, then trims to `COMPRESS_KEEP_LINES` 500), and the startup sweep deletes checkpoint files with mtime older than 30 days and enforces a global byte budget (`sweepCheckpoints`, async, non-blocking). Master toggle `settings.checkpoint.enabled` (absent = enabled) is read live per event. Subagents do not get the extension.
- Manual element pick (`src/preload/browser-pick.ts` + `src/main/browser-preview-pick.ts` + `src/renderer/src/lib/browser-pick.ts`): the preview toolbar's crosshair button toggles pick mode (`BrowserPreviewCommand "pick-mode"` forwarded to the tab's WebContentsView preload — a second electron-vite preload entry, built as `out/preload/browser-pick.cjs`). While active, real user hovers are outlined and the next trusted click opens a compact in-page confirm card AT THE CLICK POSITION — a closed shadow DOM injected by the preload (page CSS/JS cannot reach inside; a page can at most remove the host), roughly 320×84px with a one-line element description and an input row (Enter submits — IME composition Enter excluded —「发送」button, Esc/× cancels; card also closes on pick-mode toggles and document unload; elements picked inside a same-origin iframe show the card in that iframe with the iframe's own URL). Submitting sends `{url, element, note}` where `element` carries `tag`, a CSS selector `path` from the document root or nearest id anchor (pierces shadow roots via `getRootNode().host`, `elementPath`), role/type/name/text/href/src — parsed in main by `parseElementPickMessage` (shape-validated — a past bug treated the whole payload as the element and silently dropped every pick; note capped at 2000 chars). The `isTrusted` check in the preload only filters page-script synthetic events: CDP `Input.dispatchMouseEvent` from browser automation is `isTrusted: true` in Electron and indistinguishable from real input, so main additionally drops pick-results while the tab's `automating` banner is set. Picks are pushed to the renderer (`browser-preview:pick`); `BrowserPreview` has no card of its own — it forwards straight to `onPickSend(pick, note)` (App → ArtifactPreview → BrowserPreview prop chain), which appends `composePickMessage` (【来自内置浏览器】block: 页面/元素/路径/链接/图片/内容 lines + the typed note) directly into the composer textarea and focuses it with the caret at the end. A blank note sends the element block alone; multiple picks append sequentially.
- Custom slash commands (`src/main/command-catalog.ts`): user-authored md prompt templates discovered from dual-scope dirs — project `<workspace>/.pidesktop-commands/` overrides global `<agentDir>/pidesktop-commands/`; filename minus `.md` is the command name (letters/digits/`_`/`-`/CJK; `:` excluded so it can never collide with the `/skill:` prefix). Optional frontmatter `description` feeds the menu subtitle; the body is the template, with `$ARGUMENTS`/`${ARGUMENTS}` placeholders replaced by the composer argument text (no placeholder + args → args appended after a blank line). The flow mirrors skills end-to-end: summaries ride `ResourceCatalog.commands` (`syncCommands` beside `syncSkills` — no enable toggles, zero system-prompt cost), the renderer's slash menu gets a third group 「自定义命令」 (`/name` prefix matching; exact match closes the menu exactly like builtins, and `/名字 参数` + Enter submits through `session.command { name, arguments }`), `runtimeCommandPrompt` re-reads the template file at send time (edits apply to the next send without a resource reload), and the expanded prompt carries a base64url display marker (`pidesktop-command-display`) that message-normalize parses into the `ChatMessage.command` badge + an args-only bubble (the template body stays in the file, skill-style). `session.queue.add`/`session.regenerate` rebuild through the same path via `commandName`; editing a command message refills the args and re-selects the command. The settings 资源 tab lists discovered commands with their scope + path and manages them end-to-end: `command.save { name, description?, template, scope }` (validated by `validateCommandDraft`, written atomically temp+rename via `writeCommandFile` — frontmatter only when a description exists, so the file round-trips with hand-edited ones; `CommandSummary.template` carries the body back for the edit form, name locked while editing) and `command.delete { name, scope }`, both following the hooks.save light pattern — file write + `syncCommands` + catalog re-emit, no session rebuild and no busy rejection (the next send re-reads the file anyway). Project scope without an open workspace errors instead of silently writing the global dir (the discovery path's no-workspace fallback is scan-only).
- Automation scheduled tasks (`src/main/automation-store.ts` + `automation-cron.ts` + `automation-scheduler.ts` + `automation-tools.ts`): the automation-module's first capability — cron-scheduled Agent runs. Storage is agent-scoped and atomic at `<agentDir>/pidesktop-automation/<agentId>.json` (`pidesktop-automation/<agentId>.json`; normalizers drop invalid entries, the id is generated when missing). A zero-dependency 5-field cron matcher (`parseCron`/`cronMatches`: `*`/`,`/`-`/step; day-of-week 0-7 where 0 and 7 are Sunday; optional IANA `timezone` via `Intl` — 5 fields match with pure AND, no Vixie dom/dow OR) drives the scheduler (`automation-scheduler.ts`): a per-minute `setInterval` tick in the utility process reads the CURRENT agent's tasks live (`getTasks` callback follows `agent.select`), fires any enabled task whose cron matches and hasn't fired this minute (per-task minute-key guard), and drains a serial queue — one background run at a time so automation never races the active session. Execution (`runAutomationTask` in `pi-runtime.ts`) creates a FRESH background session per fire (`SessionManager.create` + `createSession(..., { skipActivate: true, modelOverride })` — `skipActivate` keeps the user's active view, the run appears in the sidebar; `createSession` gained an optional `modelOverride` that wins over `defaultModel()` in the model-resolution chain), runs `session.prompt(task.prompt)`, and records `lastRun` (sessionId/status/preview) back to the store + a `automation-run` push. v1 runs in the current agent + current workspace context; the task's `model` IS honored (modelOverride), but `workspace`/`skillName`/`subagentName` are stored metadata only, and restricted `accessMode` can hang unattended runs (so tasks default to `full` and log a warning). The `automation.*` customTools (create/list/delete/toggle/run) are registered per session and added to `customTools`/`record.automationTools`, wired into both `toolNamesFor` and the MCP hot-reload `buildRecordTools` path; they bind to the session's agent store. Conversation-based creation is a dedicated skill (`.pidesktop-skills/automation/SKILL.md`) teaching the model the task DSL + cron mapping and instructing it to call `automation.create`. UI: a settings tab 「自动化任务」 (`AutomationSettings.tsx` — 全部/进行中/已暂停 filter + search + create/edit modal with name/timezone/cron/model-grouped/space/access-mode) and a sidebar entry (`data-control="automation-open"`, below the 「新建话题」 button, with a rail icon in collapsed mode) that opens the settings tab; the dialog itself is `data-pane="automation-dialog"`.
- Keep provider secrets process-local unless a dedicated secure-storage design is added.
- Render complete HTML/SVG documents only inside the sandboxed Artifact preview.
- Theme system: custom theme CSS is applied verbatim (only legacy alias mapping and mode-selector rescoping, `src/renderer/src/lib/theme-presets.ts`). The stable theme-hook contract for structural themes is: `data-pane` on major regions (sidebar / topbar / workspace / work-area / conversation / timeline / composer / task-panel / memory-panel / preview / terminal / question-panel / settings-dialog / permission-dialog / landing / turn-minimap), `data-role` on message articles (user / assistant / extension), `data-control` on key controls (new-session / settings / workspace-open / preview-toggle / task-panel-toggle / memory-toggle / send / stop / attach / queue-edit / queue-send-now / queue-remove / access-mode / plan-toggle / model-select / thinking-select / thinking-expand / context-usage / browser-pick / copy / edit / regenerate / share), row hooks on sidebar list rows (`data-row-kind` workspace/session/agent + boolean `data-row-active` / `data-row-expanded`), node hooks on timeline segments (`data-node-kind` thinking/tool-call/text + `data-node-state` running/completed/error), composer sub-region hooks (`data-composer-zone` queue/attachments/error/input/footer/popup/plan — the `popup` zone is absolute-positioned; themes must not change its `position`), boolean `data-ui-*` state attributes on `<html>` (settings-open / workspace-open / chat-empty / generating / preview-open / permission-pending / question-pending / attachments / split-open) plus value-carrying states `data-ui-sidebar-view` (topics/files/agents), `data-ui-density` (compact/comfortable/relaxed), `data-ui-radius` (square/small/medium/round) and boolean `data-ui-sidebar-collapsed` (sidebar folded to the icon rail), and viewport decoration layers declared as `--pi-layer-<name>` (above wallpaper, below UI) / `--pi-overlay-<name>` (above UI, below dialogs) background-shorthand variables that the shell renders as `pointer-events:none` divs carrying `data-theme-layer` / `data-layer-kind` attributes (`collectThemeLayers`; both the variables and the element attributes are public API). Public layout/panel tokens: `--layout-sidebar-width` (sidebar column width — themes offset art with it instead of hardcoding), `--layout-sidebar-collapsed-width` (collapsed rail width, 48px — themes offset art against the rail too), `--panel-bg-sidebar/topbar/composer/dialog/preview` (each defaults to `var(--panel-bg)`; the var() resolves at use point, so mode blocks only need to override `--panel-bg`). Wallpaper-mode base rules are (0,2,0) specificity — themes win with equal-specificity attribute selectors, no `html` prefix. These attributes, variables and tokens are public theme API — do not rename or remove them without a migration note. Under split view `conversation`/`timeline`/`composer`/`question-panel` render once per pane; `data-pane-active` marks the focused pane's conversation region and the root `data-ui-generating`/`chat-empty`/`attachments` booleans reflect the focused pane (see the split-view migration note in `docs/theme-guide.md`). Themes own every color token; the only renderer-side overrides are the wallpaper/bubble/panel-opacity sliders and the interface-tuning layer (`data-ui-density`/`data-ui-radius` → `--ui-density-scale`/`--ui-control-radius`/`--ui-container-radius`, defaults equal current visuals; themes may override the tokens or ignore the attributes). Theme assets may be image or font data URLs. Authoring guide: `docs/theme-guide.md`; the `pidesktop-theme-creator` skill's checker validates hook names.
- User terminal (`src/main/terminal-pty.ts`): preview-tab terminals are real PTYs (node-pty) hosted in the main process and rendered with xterm.js in the sandboxed renderer, mirroring the BrowserPreview IPC shape (`terminal:command` invoke + per-terminal `terminal:data:<id>` push). The PTY outlives tab switches (main-process scrollback replay on `create` reconnect); closing the tab, changing the workspace, or quitting kills it. It is user-typed input and bypasses the agent permission gate — keep it separate from the Pi `bash` tool pipeline in the utility process.
- Per-model token limits are user-correctable: `settings.providers[].models[].contextWindow`/`maxTokens` (the settings dialog's pencil edit per model row; fetched models carry no limits upstream, and custom providers register with conservative placeholders in custom-provider.ts) win over catalog/template values everywhere. They flow through `settings.ts` normalization (only positive ints survive), `mergeProviderModels` (user values survive upstream refreshes), and `buildCatalogModels` (catalog push shows effective values). At runtime `pi-runtime.ts`'s `applyModelOverrides` rides every model→session handoff (`switchSessionModel`, `createAgentSession`'s initial model, the restored-session model resolved in `createSession` via `resolveRestoredSessionModel` in model-catalog.ts — registry lookup + Pi's restore-branch auth gate + overrides; Pi's own default restore branch fetches the raw registry model and would drop every correction after a restart, the 2026-08-30 glm-5.3-flash template-clone lesson; the new-session default chain also resolves Pi's own persisted default (`~/.pi/agent/settings.json`, rewritten by every switchSessionModel via Pi's setModel — effectively "last used model") app-side with the same gate instead of letting findInitialModel fetch it raw, and sessions created with `model: undefined` get a metadata-only post-correction `agent.state.model = applyModelOverrides(...)` mirroring Pi's `_refreshCurrentModelFromRegistry`, the subagent `transformModel` hook — shallow clone, never mutating shared runtime objects), and `provider.models.save` re-switches idle live sessions on that provider so corrections take effect immediately without a rebuild.
- Prefer focused changes. Do not copy ChatAnyTime plugin runtime code into this project.
- Before handoff, run `npm test`, `npm run build`, and a packaged Windows smoke test when packaging behavior changes.
