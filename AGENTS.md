# Project Conventions

- Keep Pi runtime objects behind `src/shared/protocol.ts`; the renderer consumes only the desktop protocol.
- Keep Electron main focused on native lifecycle, dialogs, persistence, and process supervision.
- Run Pi sessions and tools in the utility process, not in the renderer or main process.
- Pi is used only as the Agent runtime core. Its third-party extension access (loading, approval, binding, `pi-mcp-adapter`, subagent CLI shim) has been removed; do not reintroduce it. The only retained extension hooks are app-owned inline extensions: the permission gate, the tool-audit logger, the user-hooks interpreter, the plan-mode narration injector, and the checkpoint snapshotter.
- Tool pipeline (`src/main/tool-audit.ts`, `src/main/tool-delta.ts`): every tool execution is appended to `chatanytime-sessions/<agentId>/tool-audit.jsonl` (best-effort), and MCP `callTool` is bounded by a 120s `AbortSignal` timeout. MCP tool additions/replacements hot-apply to the live session via `pi.registerTool()` on the captured `ExtensionAPI` (no session rebuild); removals still rebuild the session because Pi has no tool-removal API.
- Builtin tool toggles (`BUILTIN_TOOLS` in `settings.ts` → `AgentProfile.tools` → `session.setActiveToolsByName` after creation): Pi builds all builtin tool definitions unconditionally, so per-agent enablement is pure name filtering (subagents inherit the parent agent's set the same way in `subagent.ts`). New tools default to OFF through `defaultToolEnabled` (absent keys in stored agent profiles stay off, everything else keeps absent=on) so an upgrade never changes an existing agent's toolset or request prefix; `powershell` (Pi 0.84.3, Windows-native shell tool sharing bash's `{command}` schema and infra) is the first opt-in tool. Every bash special-case recognizes it: permission `command` risk + `summarizeArgs` command summaries, hook deny-regex matching (`hookMatchText` — matchers still filter by tool name in user config), background-process command extraction (`bashCommandsFromMessages`), and checkpoint/artifact output candidates.
- Killable shell tools (`src/main/runtime-shell-kill.ts`, record field `shellKill`): every main session's `bash`/`powershell` builtin definitions are REPLACED by same-name customTools wrappers (Pi's `_refreshToolRegistry` lets customTools override builtins by name; the wrappers call the same `createBashToolDefinition`/`createPowerShellToolDefinition` factories with the same SettingsManager options, so schema/description bytes — and the request prefix cache — are unchanged). Each execute bridges the run's abort signal into a per-call AbortController; the task panel's per-command stop (`session.killExecution { executionId }`, only rendered for shell tools) aborts just that call — Pi's exec layer kills the process tree, the tool throws `…\n\nCommand aborted`, and the wrapper rewrites the status line into a user-kill notice so the agent loop CONTINUES the turn with an error tool result (session never aborts — the old panel button sent `session.abort` and killed the whole reply). The kill command marks the execution `aborted` up front; `tool_execution_end`'s aborted-preservation check keeps it neutral instead of flipping it to error. Subagent child sessions keep the stock builtin bash (the panel never shows their inner tool calls).
- Hooks (`src/main/runtime-hooks.ts` + `src/main/hooks-config.ts`): the third app-owned inline extension (`pidesktop-hooks`, between the permission gate and the tool-audit logger in `extensionFactories`). Events: `session_start` (commands awaited in order), `tool_call` (blocking — `block` deny-regex actions evaluate in-process against the bash/powershell command line / other tools' args JSON; `blocking` command actions deny via exit code 2 or stdout `{"block":true,"reason"}`, same `{block,reason}` contract as the permission gate, both gates stack), `tool_execution_end`, `agent_end` (whole reply finished — fires once per agent run with summed usage, total duration, and a failure flag that EXCLUDES user aborts (`stopReason === "aborted"`, same source as the sidebar dot; the per-tool `tool_execution_end` `isError` stays raw — a killed tool really did return an error result); this is the notification/stats event), and `turn_end` (per model-call cycle — fires multiple times per reply; users almost always want `agent_end`). Actions: `notify` (desktop notification via `hook-notify` push — carrying the triggering `sessionId` — executed by the main process: Electron `Notification`, click focuses the window, chat-app do-not-disturb semantics suppress it when the notification is about the currently-viewed session and the window is focused and not minimized; the utility process has no Electron API), `http` (POST event JSON, 10s timeout), `block`, `command`. Config is dual-scope JSONC (`<workspace>/.pidesktop-hooks.json` overriding global `<agentDir>/pidesktop-hooks.json`, merged by rule name, mcp-config-style atomic writes); handlers read a module-level cache at fire time, so `hooks.save/toggle/delete` only refresh the cache + re-emit the resource catalog — no session rebuild and no busy rejection (a user may want to disable a dangerous hook mid-run). Hook commands are user-authored config with terminal-grade trust: they bypass the agent permission gate, run via `spawn({shell:true})` in the utility process (timeout 1–120s, default 10s, `taskkill /T` tree-kill on Windows), and receive context only via stdin JSON + `HOOK_*` env vars — never via system-prompt or per-turn injection (cache discipline; `before_agent_start`/`context` injection is deliberately not exposed). Hook failures warn and allow. Master toggle `settings.hooks.enabled` (absent = enabled) is read live. Panel: settings-dialog 钩子 tab (`src/renderer/src/HooksSettings.tsx`) with per-rule test runs (`hooks.run` → `hook-run` push). Subagents do not get hooks.
- Capability clusters extracted from `pi-runtime.ts` live in `src/main/runtime-*.ts` (todo-tools / skills / vision / permissions / mcp) as pure builders over explicit inputs; session lifecycle and command dispatch stay in `pi-runtime.ts`.
- Multi-session runtime: `pi-runtime.ts` keeps several sessions alive concurrently as `SessionRuntimeRecord`s (session/busy/status/executions/todos/permission-gate/customTools are per-record) in `liveSessions`, with `activeRuntime` selecting the record that feeds `RuntimeSnapshot`. Switching or creating a session parks the previous one (it keeps executing in the background and can be reactivated as the same live record); only same-session rebuilds, workspace removal, or idle-LRU eviction (`MAX_PARKED_SESSIONS`) dispose records. Sidebar status dots (`SessionSummary.runStatus`): running=yellow is live state; completed=green / failed=red / aborted=grey are unseen-outcome notifications that clear on activation (`setTerminalRunStatus`/`activate`) and are never set for the session the user is already viewing. Terminal outcomes come from ONE place (`main/run-outcome.ts`: `resolveRunOutcomeStatus` reads Pi's `stopReason === "aborted"`, never the SDK-specific English abort text — undici's "This operation was aborted", anthropic's "Request was aborted" …), shared with the message pipeline and the hooks audit so a user stop is never reported as a failure. Aborted turns render neutrally instead of the red error row: `message-normalize.ts` strips the SDK abort text once and sets `ChatMessage.aborted` (historical sessions in the JSONL carry `stopReason`, so reopening them is clean too), the bubble shows a muted「已停止生成」 line, `ToolExecution.status === "aborted"` renders 「已中止」 with a neutral icon (never the failure styling), and aborted executions are excluded from 交付产物 (no rollback entry). The sidebar session list is agent-scoped: `refreshSessions` lists only `chatanytime-sessions/<agentId>/` and stamps `currentSessionsAgentId`; `createSession`'s "list already loaded" shortcut (`sessionListReadyFor`) requires the cached list to belong to the current agent, so an agent switch always re-lists instead of showing the previous agent's topics. Workspace grouping (`session-groups.ts`): sessions group by their own workspace, and a session-less workspace only shows as a group while it is the ACTIVE workspace — recent-workspace history (`<agentDir>/pidesktop-recent-workspaces.json`) is shared across assistants, so merging it wholesale would surface every historical workspace as an empty group for a fresh assistant. Workspace memory is per-assistant (`DesktopSettings.agentWorkspaces`, agentId → resolved absolute path; deliberately NOT on AgentProfile because agent.save overwrites whole objects and a stale form snapshot would clobber the runtime field — settings page never renders it). Main-side `updateSettings` persists it and the utility mirrors it in memory (双写对称) through the same pure functions in `main/settings.ts`: `recordAgentWorkspace` (record on `workspace.open`/`session.new`/`session.open` with explicit workspace/`activate` when the focus crosses workspaces; a split-focus on another workspace counts as that assistant's last-used workspace), `forgetAgentWorkspace` (resolve+lowercase match only), `resolveInitialWorkspace`/`resolveDefaultWorkspace`. `settings.workspace` is retired: never written after this change, consumed exactly once at `initialize` as a migration fallback for the CURRENT active assistant (promoted into the in-memory map so in-session agent switches restore it) and cleared when a removed workspace matches it — no restart resurrection (the e42c139 lesson). A `defaultWorkspace` (settings 通用 tab, custom folder or built-in `<agentDir>/workspace-default`, idempotent mkdir) closes the no-workspace dead zone: assistants with no mapping fall back to it on `agent.select`/`workspace.remove`/`initialize` (directly chatable, never the landing page; mkdir failure keeps the landing path as an extreme fallback). `agent.select` restores the target assistant's mapped workspace or the default and touches recents (so the empty group can render); changing `defaultWorkspace` while the active workspace is the old default switches immediately to the new default with a fresh session. `workspace.remove` is assistant-scoped: deletes only the current assistant's session files and its map key, disposes live records only when `record.agent.id` is the current agent (another assistant's background sessions in the same workspace survive), never touches global recents, and when the removed workspace is the active one the assistant falls back to the default workspace with a fresh session (removing the default-workspace group just clears that assistant's sessions there — the default keeps acting as fallback). Session JSONL files are not written until their first assistant message (Pi `_persist` gates on `hasAssistant`), so `refreshSessions` backfills live-but-unpersisted sessions from `liveSessions` (`backfillUnpersistedSessions` in session-scope.ts, preferring the pre-refresh entry to preserve renames/pins and overlaying the live runStatus) — otherwise any delayed full refresh (the 500ms post-turn debounce, pin/rename/delete handlers) erases a freshly created empty topic from the sidebar until its first reply lands.
- Split view (`src/renderer/src/ConversationPane.tsx` + `SplitLayout.tsx` + `lib/split-layout.ts` + store `paneStates`): the conversation area (timeline + question panel + full composer) is one reusable `ConversationPane` used by BOTH single-window mode and split panes — never fork a second composer implementation. Panes address sessions by id: run commands (`session.prompt/skill/regenerate/compact/planMode/abort/queue.*`, `model.select`, `thinking.select`) take an optional `sessionId` routed via `resolveTargetRecord` in `pi-runtime.ts` (default = activeRuntime, back-compat). The focused pane IS the active session (focus switch = `session.open` live fast-path `activate`); global mirrors (topbar workspace/PanelDock/access mode) follow the focused pane. Non-active panes subscribe to `session.state` pushes (`SessionPaneSnapshot`, per-record 50ms throttle, uuid-identity merge in store `paneStates`) driven by `session.watch` registration (`renderedSessions` in main: watched records keep streaming, are exempt from idle eviction, get no terminal dots, and late watches for not-yet-live sessions queue in `pendingWatchSessions` until `createSession` attaches them). Layout is a recursive binary tree (`SplitNode` leaf/split, max 4 panes) persisted in localStorage `pidesktop.split-layout` and pruned when sessions disappear or the agent switches; right-click a sidebar session adds 「分屏到右侧/下方」. Per-session composer drafts live in App's `draftStore` map; App→pane composer writes (browser-pick, html-action) route through `composerBridge` to the focused pane. Permission/question surfacing is pane-set-scoped (`panePermissionRequest`/`paneQuestionRequest`, focused first; permission dialog shows the source session title). The plan-approval QuestionPanel renders inside its own pane.
- Self-built capabilities (MCP / Skill / Subagent / Todo) live in the utility process and are exposed to Pi as `customTools` (`ToolDefinition[]`) on `createAgentSession`, plus system-prompt injection for Skills. Do not run them in the renderer or main.
  - MCP: `src/main/mcp-client.ts` (`McpClientManager`) connects via `@modelcontextprotocol/sdk`; each tool becomes `mcp__<server>__<tool>`. Config in `.mcp.json` (project) / `mcp.json` (global). `McpServerSummary` carries the config projection (scope/transport/command/args/url/auth/bearerTokenEnv/env, plaintext = file content) so the settings panel can prefill an edit form. Edits go through `planMcpServerSave` (`runtime-mcp.ts`, pure): the name is the config key (locked while editing), a scope switch migrates the entry (remove from the old file, write the new one — a stale duplicate would shadow the edit since project wins), and `disabled` travels with the entry so editing never re-enables a paused server; `mcp.server.save` carries `original {name, scope}`, and `mcp.server.delete` falls back to the other scope's file when the declared one has no such entry. OAuth (`src/main/mcp-oauth.ts`, utility process): HTTP servers without `bearerTokenEnv` (bearer wins) get an SDK `OAuthClientProvider` on their transport — the SDK's `auth()` orchestration does RFC 9728 discovery + dynamic client registration + PKCE, `redirectToAuthorization` rides the `open-external` up-message to main's `shell.openExternal`, and `UnauthorizedError` maps to status `needs-auth` (not `failed`) so the 资源 tab can offer 认证/重新打开授权页/清除凭据 per `McpAuthState` (`idle/pending/authorized/failed` rides the summary; `pending` waits 10min then expires). Credentials persist in `<agentDir>/pidesktop-mcp-auth.json` — a deliberate, user-approved plaintext exception (same level as `mcp-cache.json`) so refresh tokens survive restarts; the loopback callback server prefers port 1456 (persisted; drift invalidates the DCR registration and re-registers) and is `unref`'d, with `dispose()` riding `parentPort`'s `close` event. **Refresh-token safety (2026-09-15, a real "every restart demands re-login" incident)**: rotating authorization servers (Exa et al.) revoke the whole token family when one refresh_token is used twice, and the upstream SDK (1.30) has NO concurrency dedup — `StreamableHTTPClientTransport` calls `auth()` itself on a 401, and `authInternal`'s InvalidGrantError branch retries once. The old provider answered `invalidateCredentials('tokens')` by DELETING `tokens`, so a single race wiped the credential and every restart looked like "it was never saved". Fix = one per-server lock (`McpOAuthController.runExclusiveAuth`/`runExclusive`) held by **every** network-touching OAuth path — `syncOne`'s connect/listTools段, `callTool`'s send (`sendWithOAuthGate`, needed because an opaque token has no readable `exp`, so the pre-send expiry check cannot see it), `beginAuthorization`, and `handleCallback`'s `finishAuth`; plus `refreshIfExpiredLocked` (pre-send proactive refresh when the JWT `exp` is within 60s; must be called holding the lock — the self-locking wrapper was deliberately NOT kept, `runExclusive` is not reentrant). Credential semantics: a rejected refresh now only writes `McpAuthStore.refreshFailed {reason, at}` and KEEPS `tokens` (marked tokens read as `undefined` so the SDK never loops on a dead token); a fingerprint guard (`tokens()` records what it handed out; `invalidateCredentials('tokens')` refuses when the stored pair no longer matches — the concurrent winner already wrote fresh credentials) prevents the loser from deleting the winner's tokens; only `saveTokens`/`clear`/`invalidate('all')`/user-initiated re-auth clear the marker, and a user-initiated re-auth (`authorizeInteractive`/`runUserInitiated`) clears it once so the kept refresh_token gets a retry. `redirectToAuthorization` only auto-opens the browser for user-initiated flows or a first-ever authorization — during a sync or after a judged-dead credential it records the reason instead (`onAuthorizationSuppressed`), so startup no longer pops a browser window. `handleCallback` matches the callback by state **snapshot** taken at `onAuthorizationUrl` and restores that flow's `codeVerifier` INSIDE the lock (its predecessors rewrite both, which used to turn a waiting authorization page into a dead one); `mcp.server.auth`'s oauth branch returns early on `pending` for the same reason. `authErrorOf` surfaces the real reason (invalid_grant text) plus the token-endpoint error captured by `callWithDiagnostics`, instead of a bare `Unauthorized`. End-to-end regression: `src/main/mcp-oauth-rotation.test.ts` runs a local rotating/PKCE-verifying fake AS asserting "the same refresh_token is never sent twice" across concurrent sync, parallel `callTool` (JWT and opaque), and sync-overlapping-callTool.

`mcp.server.auth` has three branches (a pending URL is just reopened; explicit `auth: "oauth"` calls `authorizeInteractive` without waiting for a 401; otherwise force-reconnect and let the 401 drive the flow); authorization completion (`onAuthorized`), pending expiry, and callback failures all re-push the resource catalog — `applyMcpToolChanges`' hot path (registerTool without rebuild) does NOT emit on its own, the `onAuthorized` wrapper compensates — so the panel never sticks on 等待浏览器授权. Renderer dev: `npm run demo` serves the renderer standalone in a plain browser via `.vite.demo.config.mjs` (port 5199); `main.tsx` falls back to `createDemoApi` (demo-api.ts) when no preload injected `window.piDesktop`, which mocks the OAuth round trip (认证 → 2.5s → connected).
  - Skill: `src/main/skill-catalog.ts` scans an ORDERED source list (`SkillSourceDir[]`, lowest precedence first, later entries overwrite earlier ones on a slug clash) for `SKILL.md`: shared `~/.agents/skills` → BUNDLED app skills (`resources/skills/` in the repo, `<install dir>/resources/skills` when packaged — electron-builder `extraResources` copies it next to `app.asar`) → user global `<agentDir>/pidesktop-skills` → project `<workspace>/.pidesktop-skills`. The bundled dir is the app's built-in skill directory: read directly at runtime, never copied into user dirs (a user overrides a built-in skill by dropping a same-slug copy in the global or project dir). Main resolves it (`resolveBundledSkillsDir` in `src/main/bundled-skills.ts`: packaged → `dirname(app.getAppPath())/skills`, dev → `<repo>/resources/skills`, `existsSync`-guarded) and hands it to the utility process via the optional `initialize.bundledSkillsDir` field (the utility process has no Electron API). `runtime-skills.ts` assembles `skillPathsFor(workspace, agentDir, bundledDir)`; with no workspace the project source is simply ABSENT (it used to fall back to the global dir, mislabelling global skills as 「当前项目」). Each summary carries `scope: "bundled"|"global"|"project"` (renders as 内置/全局/当前项目) plus a display `source` string (随应用分发/用户资源/共享目录/当前项目); enable state in `pidesktop-skill-state.json`. `runtime-computer.ts`'s `locateLjqCtrlDir` follows the SAME precedence (project → global → bundled → shared) since the computer_* tools and the computer-use skill share one `ljqCtrl.py`. Skill assets are versionless by convention here (bundled skills ship with the installer version) — no version gate/copy step, unlike Proma's seeded `default-skills`. User override precedence is for BEHAVIOUR, not for hardening: the bundled tree is the one the app guarantees, so the `extraResources` filter excludes Python bytecode (`!**/__pycache__/**`, `!**/*.pyc`) — importing a skill module writes `__pycache__` next to it in whatever dir the skill lives in, and an unfiltered `**/*` packed those into the installer (locked by a test that asserts the FILTER, not the disk state).
  - Computer use (`src/main/runtime-computer.ts` + `resources/skills/computer-use/`): the `computer_*` customTools (windows/screenshot/click/type/press) spawn short-lived Python that imports `ljqCtrl.py` from the same `computer-use` skill dir (one implementation shared by tools and skill); arguments ride base64 in `-c`, results come back on a `__CU__<json>` line, and `ljqCtrl` diagnostics are collected as notes — the prefixes in `NOTE_PREFIXES` (`[Click check]` / `[TIPS]` / `[Activate]` / `[GrabWindow]`) are the model's only feedback on what actually happened on screen, so new prefixes must be added there or silently dropped. `computer_click`/`type`/`press` are `desktop` risk (read-only denies / ask confirms per call / workspace+ allows); windows/screenshot are ungated observation. Three invariants learned by measurement (2026-09-15) and encoded in the code + `test/selfcheck.py` — do not regress them: **(1) PrintWindow needs `PW_RENDERFULLCONTENT`**: with `PW_CLIENTONLY` alone every DWM-composited window (Chromium/Electron/browser/UWP) returns an ALL-BLACK frame while `PrintWindow` still returns 1, so the return value is not a success criterion; the bitmap starts at the CLIENT origin (no `GetWindowRect` offset crop — measured MAD 19.97 with the offset, 0.000 without). **(2) A click receipt must carry three signals, not one**: hit test (`WindowFromPoint` + `GetAncestor(GA_ROOT)` vs the target hwnd; same-process windows pass so popup menus/dialogs stay clickable), pixel change (client-area `diff_ratio` over `CLICK_CHANGE_RATIO` 0.001 — measured idle noise is ~0.0001 — plus a cursor-neighbourhood probe), and foreground check; 「no pixel change」 degrades to `warn_static` advice and is NEVER a failure (a real button click can legitimately produce zero change, and animation makes 「changed」 always true). **(3) Refuse a mis-aimed click instead of performing it**: when the coordinate is not over the target window (nor a same-process window) `Click(hwnd=…)` returns `verdict='refused_hit'` WITHOUT clicking — the old behaviour really did click the user's browser once coordinates were off-screen. Related: `GrabWindow` reports `cu_fg_ok`/`cu_fg_title` in `img.info` (it only grabs that screen REGION and cannot tell what covers it — an occluded target yields the occluder's pixels), `Activate` verifies the foreground and warns, `dpi_scale` is structurally 1.0 in a DPI-aware process (it converts FOREIGN logical coordinates only; dividing screenshot coordinates by it is a no-op), and `ui_detect.detect()` accepts path/PIL/ndarray/bytes by converting to ndarray internally (rapidocr 1.3.24 raises `LoadImageError` on PIL) while cleaning up its temp files. **Tool activation (2026-09-15)**: the 5 `computer_*` definitions are NOT always active — measured ≈580 tokens of per-request PREFIX (windows 64 / screenshot 111 / click 205 / type 97 / press 101), so they follow the DESIGN discipline, not the browser one: `shouldActivateComputerTools({ sessionEnabled, globalEnabled })` gates `toolNamesFor`, both halves must hold. `sessionEnabled` is the session-scoped computer mode (`SessionRuntimeRecord.computerMode`, persisted atomically at `chatanytime-sessions/<agentId>/computer-mode/<sessionId>.json` by `computer-mode-store.ts` — design-mode-store shape), toggled by the `session.computerMode` command (topbar `data-control="computer-toggle"` button, or the `/computer` slash command in the composer) and read back in `createSession`; it DEFAULTS OFF (a coding/document chat must not pay for desktop driving) and is inherited by `session.new` only (`inheritComputerMode`, written to disk too) — workspace/agent switches, unattended automation runs and plan hand-offs do not carry it. `globalEnabled` is `settings.computer.enabled` (absent = enabled; the settings 通用 tab checkbox). The master switch is a CAPABILITY toggle (下架), not a per-call gate: with it off, no session injects the tools AND the live `enabled` check inside every `execute` still throws (second line of defence for in-flight calls). Do not copy the browser policy here (`browser_*` stays permanently active with a live master switch — different tool, different tradeoff). Two long-standing holes in that master switch were fixed in the same change and are pinned by tests: `migrateSettings` dropped the `computer` field entirely (writing `{enabled:false}` to settings.json was silently discarded on restart, so the switch was decorative) and the main-process `settings.save` mirror omitted `computer` while the utility one carried it.
  - Subagent: `src/main/subagent.ts` `delegate_agent` creates a single-level child `AgentSession` under `chatanytime-sessions/<agentId>/delegations/`, resolving a custom subagent definition from `subagents-store.ts`——a **three-tier** (bundled `<install>/subagents` / global `<agentDir>/pidesktop-subagents.json` / project `<workspace>/.pidesktop-subagents.json`) JSON store surfaced in `ResourceCatalog.subagents`; a matched definition supplies the child's system prompt / model / tool set (`"inherit"` keeps the parent's enabled builtin tools). **Built-in definitions ship with the installer (2026-09-15)**: `resources/subagents/{code-reviewer,explorer,general-purpose}.json` are copied by `extraResources` (`to: "subagents"`), resolved by `resolveBundledSubagentsDir` (packaged → `dirname(app.getAppPath())/subagents`, dev → `<repo>/resources/subagents`) in the MAIN process (the utility process has no Electron API) and handed over via `initialize.bundledSubagentsDir` — the same discipline as bundled skills (read directly, never seeded into user dirs). `readBundledSubagents` reads one definition per `.json` file, forces `scope: "bundled"` + `builtin: true` (a config file CANNOT claim the bundled scope — `normalizeSubagent` normalizes it to `global`, so a hand-edited JSON can never forge a read-only entry), and skips only a broken file instead of losing the whole set. Merge order is bundled < global < project, and a user definition replaces a built-in one by **id OR name** (`upsert` in `readSubagents`) — the name half exists because the delegation entry point is the NAME: a user whose legacy definition is named `code-reviewer` under a random id (`subagent-xxxx`) would otherwise leave two same-named entries in the catalogue and make name resolution ambiguous. **Built-ins are read-only with exactly ONE writable knob: the execution model.** `subagent.model { id, model? }` writes `<agentDir>/pidesktop-subagent-models.json` (`saveSubagentModelOverride`, omitted model = back to inheriting the session model), which `readSubagents` layers over the built-in default; `saveSubagent`/`deleteSubagent` reject `scope === "bundled"` outright (the renderer additionally shows only the model selector on those rows, `data-subagent-scope="bundled"` + dashed border for themes). No built-in declares a `model` on purpose — providers differ per user, so a hardcoded one would make a fresh install immediately report 「子代理模型不可用」. The three built-ins are tool-differentiated by role: `code-reviewer`/`explorer` are read-only (read/bash/grep/find/ls, no edit/write — an auditor that can edit code is not an auditor), `general-purpose` may write. **A custom subagent definition is the ONLY delegation target (converged 2026-09-15): `subagent` is REQUIRED and must match a definition by id or name, otherwise the call is rejected with the available names listed (`buildSubagentReferenceError`).** Before the convergence, `subagent` was optional and the `role` enum was a second, independent execution path, so the model freely invented subagents: of 36 real `delegate_agent` calls in the session store, 19 (53%) passed no `subagent` at all and all 6 of the most recent ones did. This is exactly why the built-ins now exist: with the old optional behaviour an empty catalogue degraded to a generic role prompt, whereas after the convergence an empty catalogue means the capability is visibly absent (the v1 plan had deliberately shipped no built-ins — that tradeoff no longer holds). `role` is display-only (it rides `DelegationProgress.role` for the node label and never shapes the child prompt/tools), and `buildSubagentPromptBlock` states the hard constraint (the catalogue is the only target, `subagent` is mandatory, never invent a name, never fall back to `role`). Two robustness fixes ride along: (1) the catalogue reaches the tool through `getSubagentCatalog()` — a READER, not an array snapshot — because `refreshSubagents()` swaps the module-level array reference, so a session that captured the old array could never reference a definition added later in the settings panel (the settings panel's `subagent.save` now also rebuilds the active session, falling back to 「saved, effective on the next session rebuild」 while the session is busy, since the catalogue in the system prompt is written at session-creation time); (2) an empty child output is an explicit `isError` (`buildEmptyDelegationOutputError`) instead of the old `(子代理未返回文本)` placeholder returned as a successful result — measured 4 times, every one a bare empty model response (steps=0), which the UI happily rendered as a completed delegation. The tool stays registered even with an empty catalogue (registration ≠ activation; a session keeps one byte-stable prefix) and simply reports a clear error.
  - Question: `src/main/runtime-question-tool.ts` exposes `ask_question` as a customTool; its execution blocks on `QuestionBroker` until the user answers in the renderer's question panel (`question`/`question.dismiss` pushes, `question.resolve` command — mirrors the permission round trip). Question shape is decided by `normalizeQuestionItem` on the OPTIONS, not on the declared `type`: `options.length >= 2` makes it a choice question (`type: "multiple"` keeps multi-select, anything else — omitted/`text`/unknown — becomes `single`), fewer than two options falls back to a text question. `type` is an optional schema field, and real models routinely send `options` without it (2026-09-11 tool-audit: every question in 3 consecutive calls had 2-4 options and no `type`); keying the choice decision off `type` therefore silently DISCARDED the options and rendered a bare input — the panel now never loses options a model actually sent. The panel is paged (one question at a time) and auto-marks the first option of a choice question as（推荐）— the tool description tells models to put their recommended option first; no protocol change carries the recommendation. Pending questions cancel on session dispose; the tool is never permission-gated.

BEL`) appended as a POSIX `printf` — the command's own ECHO carries the literal backslash-033 text while the printf OUTPUT carries real ESC bytes, so `stripAnsi`-level spoofing cannot fake a completion; `aiExec` waits for the marker (default 60s, tool-tunable 1–600s) and on timeout KEEPS the connection (the command may still run remotely; partial output + guidance returned). The earlier line-regex version never matched that shape and silently left the probe visible while its unit tests — built from an idealized single-line sample — stayed green. The state machine treats CRLF + repeated boundary char as fold noise, holds the candidate text until it either completes (drop) or mismatches (emit it verbatim, so no character is lost), caps the candidate at `MARKER_ECHO_CANDIDATE_LIMIT` (256) as a hang guard, and shares its literal fragments with `markerPrintfCommand` (exported) so test samples are generated by the producer and cannot drift from the real echo.
